# Rich message types (location, contact card, poll, emoji and stickers, file preview, formatting, link card)

> Applies: read this file when the PRD involves sending a location and live location sharing, contact cards, group polls, sticker packs and custom emoji and animated images, file message preview and states, text formatting, and link cards. For the minimum set of message types see SEND-01, for link preview default and turning it off see MISC-31, for file size and dangerous files see MEDIA-01 and MEDIA-06, for the fallback for unsupported types see MISC-17, for forwarding restrictions see ACT-03, and for location permission see DISC-05. Interactive mini-game messages get no entries in this library. Evidence is in evidence/16-rich-messages.md.

## Baseline (follow by default, high confidence)
- **[RICH-01] Static location and live location are separate**: a static location keeps its coordinates unchanged once sent; when live location is offered, it has its own entry and message type separate from static location. Whether to offer live location is covered in RICH-37. Must define: whether a static location lets the user pick a point (current location, nearby places, search a place); the fields the message contains (coordinates, place name, address); the view page after tap and "Open in another map app"; the copy for location failure and map load failure (for reference: one product prompts them separately); the chat list summary copy. | Magnitude: not applicable | Confidence: High
- **[RICH-02] A contact card leads directly to a chat or adding**: a contact card message shows identity information such as the name of the shared subject, and the recipient can message or add as a contact directly from the card. For card fields and control by the person being shared, see RICH-44. Must define: where tapping the card goes (profile page); the buttons and copy when the subject is already a contact, is oneself, is blocked or has blocked me, or has deleted their account; whether to offer "Invite" when the subject is not registered (for reference: two products give only an invite entry for unregistered people); the chat list summary copy. | Magnitude: not applicable | Confidence: High
- **[RICH-03] Single or multiple choice is decided by the creator at creation**: a poll's single or multiple choice is chosen at creation, and is marked on the message after sending. Must define: whether the default is single or multiple choice; whether multiple choice takes effect on tap or after ticking and tapping "Submit"; whether changing a choice in single choice automatically replaces the original option (consistent with RICH-46). | Magnitude: not applicable | Confidence: High
- **[RICH-04] Polls have caps on option count and text length**: caps are set on the number of options and on the length of the question and option text, validated at creation. Must define: each cap and the over-limit prompt (whether it says how many more can be added); the minimum number of options needed to start a poll (for reference: two products require at least two); whether options can be reordered by dragging; handling of empty and duplicate options. | Magnitude: about 10 to 12 options; question about 100 to 255 characters, option about 100 characters | Confidence: High
- **[RICH-05] No more votes after a poll ends**: a poll has an ended state; after it ends, no more votes can be cast and results are frozen. Must define: how it ends (manual, timed, see RICH-47); who can end it manually (for reference: in two products only the creator; whether the group owner and admins can end a poll started by others must be stated and kept consistent with whether they can unsend the whole poll, and after the creator leaves the group there must not be a poll nobody can end); the end confirmation copy (for reference: two products state it cannot be undone); the label on the message after ending; whether the chat leaves a "{nickname} ended the poll" system message; the copy for a failed end when offline; whether it can still be ended after the creator deletes the poll. | Magnitude: not applicable | Confidence: High
- **[RICH-06] The creator can learn of new votes**: after someone votes, the creator can learn that there is a new vote (either a notification reminder or an unread count on the poll message). Must define: reminder or count; the default switch for the reminder and the entry to turn it off; whether reminders are aggregated; reminders for anonymous polls do not include the voter (follows RICH-45); whether other members are also reminded. | Magnitude: not applicable | Confidence: High
- **[RICH-07] A link preview failure does not block sending**: when the preview fetch fails or there is no preview, the message is sent as usual and shown as a tappable plain link. Must define: how the input bar preview strip appears while loading and on failure; what to do when the preview has not yet been retrieved at the moment of tapping send (wait, or send the plain link directly); which URL is previewed when a message contains several (for reference: one product previews only the first, and in one the sender can specify). | Magnitude: not applicable | Confidence: High
- **[RICH-08] Sticker packs can be added and removed**: a sticker pack can be added and removed as a whole, and can be added again after removal. Must define: whether stickers from that pack already sent still display as usual in chats after removal; the add entries (open a sticker someone sent to view the whole pack, sticker store); the removal confirmation; the sort method (for reference: two products support manual sorting); whether those who already added a pack that has been taken down can continue to use it. | Magnitude: not applicable | Confidence: High
- **[RICH-09] Custom emoji have a size cap**: added or uploaded emoji have a size cap, and over-limit is blocked with the reason explained. Must define: the separate caps for static and animated; the duration cap for animated emoji (for reference: two products use 3 seconds); the over-limit copy; the copy when a batch add partially fails. | Magnitude: static in the hundreds of KB, animated in the several hundreds of KB | Confidence: High
- **[RICH-10] The emoji panel offers search**: the emoji panel can search emoji by keyword. Must define: the search scope (added ones, ones in the store); the no-results copy; whether there is a "Recently used" group (two products). | Magnitude: not applicable | Confidence: High

## Conventions (default-OK, mark as suggested)
- **[RICH-11] Live location expiry and manual stop**: sharing runs from the duration the sender selected, ends automatically on expiry, and the sender can stop manually at any time while sharing; the other party sees the sender's position on a map. For duration tiers see RICH-38. Must define: the stop entries (on the message, on the location page) and confirmation copy; how both sides' messages appear after expiry and after stopping (see RICH-40); the update-time copy (for reference: one product shows "Updated N minutes ago" at minute granularity); whether it can be extended before expiry (one product can extend); the sender-side sharing-in-progress indicator; what the other party sees when the sender goes offline or location fails. | Magnitude: not applicable | Confidence: Medium (direct evidence from two products)
- **[RICH-12] Unified view and stop-all for multi-chat sharing**: when live location is shared in several chats at once, provide one place to view them all and a "Stop all" entry. Must define: the entry location (privacy settings, a prompt at the top of the chat page); the list content (chat name, remaining duration); the stop-all confirmation copy. | Magnitude: not applicable | Confidence: Medium (direct evidence from two products)
- **[RICH-13] Polls are offered only in group chats and channels**: the poll entry appears only in group chats (and channels) and is not offered in one-on-one chats. Must define: whether channels offer it and whether subscribers can vote; whether starting a poll is a group permission item (see RICH-27); whether the entry is hidden or grayed out in the one-on-one attachment panel. | Magnitude: not applicable | Confidence: Medium (direct evidence from two products; the third is the first sentence of a help center)
- **[RICH-14] A poll cannot be edited after creation**: after a poll is sent, its options and settings cannot be modified, and it must be deleted and resent. Must define: whether to allow changing only the question within a short time after sending (one product allows 15 minutes); how votes already cast are handled after the poll is deleted; editability is consistent with ACT-28. | Magnitude: not applicable | Confidence: Medium (direct evidence from two products)
- **[RICH-15] Poll submission is pending first, rolled back on failure**: after a tap, show pending locally first, and take effect after server confirmation; on failure, revoke the local selection and prompt. Must define: how pending appears; the failure prompt copy; the copy when a vote is rejected because I have left the group or the group is dissolved; whether to queue while offline. | Magnitude: not applicable | Confidence: Medium (direct evidence from two products)
- **[RICH-16] A failed emoji add prompts by reason**: when adding an emoji fails, prompt separately by reason, and do not cover everything with one "Add failed". Must define: the reason list and copy (identical emoji already exists, size over limit, format unsupported, video unsupported, taken down, unavailable in the region, favorites cap reached). | Magnitude: not applicable | Confidence: Medium (direct evidence from two products)
- **[RICH-17] Emoji sync with the account**: added sticker packs and favorited emoji sync to other devices with the account. Must define: the sync scope (sticker packs, favorites, order, recently used); when a new device first syncs; when other devices update after removal on one device. | Magnitude: not applicable | Confidence: Medium (direct evidence from two products)
- **[RICH-18] Emoji suggestions while typing**: when typing an emoji or keyword in the input box, matching emoji appear above the input bar for one-tap sending. Must define: the trigger condition; whether the suggestion strip can be turned off in settings; nothing appears when there is no match. | Magnitude: not applicable | Confidence: Medium (direct evidence from two products)
- **[RICH-19] Define the file message state by state**: a file message has four states, not downloaded, downloading, downloaded, and expired; the tap result and available actions of each state are defined separately; a download in progress can be canceled. Must define: the tap result of each state; the download interruption and copy when the file is unsent or deleted during download; whether a file already downloaded to the device can still be opened after it expires on the server (one product distinguishes "downloaded before expiry"); for the expiry placeholder see RICH-31. | Magnitude: not applicable | Confidence: Medium (direct evidence from two products)
- **[RICH-20] URLs in text are auto-detected**: URLs in text messages are automatically recognized as tappable links. Must define: the recognition scope (URLs, phone numbers, emails); the tap behavior (for the risk prompt see RICH-36); the long-press menu (copy link, open). | Magnitude: not applicable | Confidence: Medium (direct evidence from two products)
- **[RICH-21] How formatting is applied (if offered)**: when text formatting is offered, on mobile the user selects text and picks a style from the pop-up menu, desktop additionally has shortcuts; styles are WYSIWYG before sending. For the style scope see RICH-53. Must define: the shortcut table (for reference: two products use the same "⌘⇧X" for strikethrough, while the monospace and spoiler keys differ); how a spoiler is revealed; whether older versions that do not support it degrade to plain text; whether formatting is kept when copying a formatted message. | Magnitude: not applicable | Confidence: Medium (direct evidence from two products)
- **[RICH-22] Link card composition**: a link card is composed of the site name, title, summary, and thumbnail, and the whole card is tappable to open the link. Must define: how it appears when an item is missing (for reference: omit that item without leaving a gap); whether both large-image and small-image forms are offered (one product lets the user choose); whether the card sits above or below the text (one product lets the user choose); whether it updates as the web page changes after sending (one product sends the preview as an attachment with the message, which is a snapshot at send time); whether the card is kept when forwarding and quoting. | Magnitude: not applicable | Confidence: Medium (direct evidence from two products)

## Divergences (ask Box on must-ask; write default-OK per recommendation and list it)
- **[RICH-37] Whether to offer live location, and its form**: Option A: not offered, static location only (one product) / Option B: one-way sharing: the creator sends their live location to the chat for a selected duration (two products) / Option C: multi-person shared map: chat members each join the same map and can leave at any time (one product). Recommended: B. Rationale: user understanding: who is sharing and with whom is clear at a glance; A has the smallest scope, so choose A if live location is not built in the first release. | Level: Must-ask | Framing: yes
- **[RICH-38] Duration tiers for live location**: Option A: fixed finite tiers, no indefinite option, extendable before expiry / Option B: finite tiers plus "Until I stop it manually" / Option C: finite tiers, not extendable. Recommended: A. Rationale: privacy: indefinite sharing is easily forgotten and exposes whereabouts for a long time, while extension covers long trips; the recommendation is already the most conservative option, and only one product offers indefinite. | Magnitude: about three tiers from 15 minutes to 8 hours | Level: Default-OK
- **[RICH-39] Live location updates in the background**: Option A: update only while the app is in the foreground / Option B: continue updating in the background (while-in-use authorization is enough, and the system shows a location indicator), and after the app is terminated by the system, sharing stops and both sides see it has stopped / Option C: keep updating after the app is closed (requires always authorization, stated before sharing starts). Recommended: B. Rationale: privacy: sharing in transit is covered without requesting always authorization; platform fact: on iOS with "while using" authorization, sharing started in the foreground with background location mode enabled can keep updating in the background, with the system showing a location indicator (not rechecked online). Background: one product states on the duration selection page that sharing continues when the app is closed (C), and one allows both always and while-in-use authorization. The location authorization scope for the live location scenario (while using or always, precise or approximate) is asked only in this entry and is not asked again under DISC-05; for the authorization request flow see DISC-05. | Level: Must-ask
- **[RICH-40] What the sharing counterpart sees during sharing, after it ends, and after leaving the group**: in-group visibility scope and post-end retention are combined into one question. Option A: only members already in the group when sharing started can see it, and when the creator leaves or is removed, sharing to that group stops; after it ends, only "Location sharing ended" and the end time are shown, and the location is no longer shown / Option B: all group members during sharing can see it (including members who join later); after it ends, a static snapshot of the last location is kept with the end time marked (one product states this explicitly, and one implies it in copy). Box may change only half of it (for example, take A for visibility scope and B for post-end). Recommended: A. Rationale: privacy: the creator authorizes only those who could see at the time of starting, for the selected duration, and a long-visible last location should not be left behind after ending; every product states only that in-group members can see it, and evidence for whether people joining later can see it was not obtained, so this is inference; not retaining after ending is the opposite of two products' practice, a privacy tradeoff. | Level: Must-ask
- **[RICH-41] Retention of the location after sharing ends**: See RICH-40 (merged with in-group visibility scope into one question).
- **[RICH-42] Proximity alerts**: Option A: not offered / Option B: offered, the creator sets a radius, and when the other party enters the radius, all members of the chat are alerted in the chat (one product). Recommended: A. Rationale: only one product offers it and it depends on continuous live location, so it is out of scope. | Level: Default-OK
- **[RICH-43] Subject scope of contact cards**: Option A: in-app account cards (individual, group, service account), where tapping goes to the profile page (one product) / Option B: phone address-book contacts (including fields such as phone number, with unregistered people invitable) (three products) / Option C: both. Recommended: A. Rationale: privacy: do not send a third person's address-book fields such as phone number into a chat; opposite to three products' practice, a privacy tradeoff. | Level: Must-ask
- **[RICH-44] Information about the shared person in a contact card, and the shared person's control**: Option A: contains only avatar, nickname, and account identifier, without a phone number; the shared person can turn off "Allow others to add me via contact cards" in privacy settings, and once it is off, when the recipient taps "Add" they are told the other party has turned it off / Option B: contains the fields about that person from the sender's address book (phone, email, address), and fields can be trimmed before sending (one product) / Option C: the whole card is sent as is (two products). Recommended: A. Rationale: privacy: the shared person has control over whom their information is passed to; for how a contact card is shown as an add source see DISC-15. | Level: Must-ask
- **[RICH-45] Poll anonymity and visibility of vote details**: Option A: named, all members can see who voted for which option (one product, and the default in another) / Option B: the creator chooses anonymous or named at creation, and when anonymous nobody, including the creator, can see the voters (one product) / Option C: named, but the results page can hide voter names so everyone sees only vote counts (one product). Recommended: B, default anonymous, and for named polls state in the poll area "Named poll, members can see your choice". Rationale: privacy: a voter must know before voting who will see their choice. | Level: Must-ask
- **[RICH-46] Changing and withdrawing a vote**: Option A: votes can be changed and withdrawn at any time before the poll ends (two products) / Option B: the creator decides at creation whether changing votes is allowed (one product) / Option C: cannot be changed. Recommended: A. Rationale: recoverability: a mistaken tap can be corrected. | Level: Default-OK
- **[RICH-47] Poll deadline**: Option A: can only be ended manually (one product) / Option B: a deadline can be set and the poll ends automatically at that time, and the creator can also end it early (two products). Recommended: B. Rationale: user understanding: gathering opinions in a group usually has a time limit. | Magnitude: hour level to about 30 days | Level: Default-OK
- **[RICH-48] When results become visible**: Option A: visible in real time after voting (two products) / Option B: the creator can set results to be published only after the poll ends (one product). Also needs deciding: whether people who have not voted can see the results first. Recommended: A. Rationale: fewest states; publishing only after ending is left as a later option. | Level: Default-OK
- **[RICH-49] Extended poll features**: Option A: not offered / Option B: offered: quizzes (standard answers), members adding options, restricting voting eligibility (time in the group, region), options with attached images (each in one product). Recommended: A. Rationale: offered by one product each, so no extension in the first release. | Level: Default-OK
- **[RICH-50] Sources of custom emoji**: Option A: long-press another person's emoji in a chat to add, import from the photo library (two products) / Option B: whole packs only (one product) / Option C: A plus video-to-emoji (one product). Recommended: A. Rationale: user understanding: covers the most common collection paths. | Level: Default-OK
- **[RICH-51] Sources of animated images**: Option A: only the user's own animated images (favorites, photo library, added sticker packs) / Option B: integrate third-party animated image search (the search term is sent to the third party) (one product). Recommended: A. Rationale: privacy: search terms are not sent out. | Level: Default-OK
- **[RICH-52] Paid or membership emoji**: Option A: no paid or membership threshold / Option B: paid sticker packs, or membership that raises the favorites cap and unlocks special emoji (three products, each in a different form). Recommended: A. Rationale: consistent with the no-tiering recommendation in MEDIA-15. If B is chosen, for favorites and membership emoji beyond the free cap after membership expires see PTS-25. | Level: Default-OK
- **[RICH-53] Scope of text formatting**: Option A: not offered (two products) / Option B: basic styles: bold, italic, strikethrough, monospace (three products) / Option C: B plus spoiler, block quote, custom text links (spoiler in two products, the rest in one). Recommended: B. Rationale: three products offer the basic styles; custom text links hide the real address and carry a spoofing risk. | Level: Default-OK
- **[RICH-54] Auto-converting typed markers into formatting**: Option A: apply only via the menu and shortcuts / Option B: typing paired markers (such as asterisks on both sides) automatically converts to a style (two products). Recommended: A. Rationale: user understanding: asterisks and underscores in ordinary text are not mistakenly converted; opposite to two products' practice, a false-conversion tradeoff. | Level: Default-OK
- **[RICH-55] File preview method**: Option A: only open with the system preview or another app after download / Option B: built-in preview of common documents and images, with unsupported types and files inside archives prompting "Download to view" (one product) / Option C: before download, convert on the server and preview online. Recommended: B. Rationale: user understanding, and the preview is done on the device, so file content is not converted on the server. | Level: Default-OK
- **[RICH-56] Sending folders**: Option A: not supported, prompting "Sending folders is not supported yet" (one product) / Option B: automatically packaged into an archive and sent (one product) / Option C: converted to a cloud link and sent (one product, see MEDIA-14). - **[RICH-58] Address validation for preview fetching**: Option A: generate only for https URLs, reject internal-network and local addresses and spoofed domains that mix different character sets, and validate the same way after redirects (one product) / Option B: no validation. Recommended: A. Rationale: user understanding: before opening, it is clear what it is and whether it is still valid; expiry copy follows GRP-07. | Level: Default-OK

## Must-ask states (specific to this module, supplementing the general state matrix)
- Location: locating, location failure, map load failure, no network; the precision sent and the prompt the other party sees when only approximate location is authorized; the selected place has no name or address.
- Live location: the update time the other party sees when the sender goes offline, location fails, powers off, or the app is terminated during sharing; the creator leaves the group, is removed, or is blocked, and the other party has blocked the creator; repeatedly starting in the same chat; whether another device can see and stop the sharing; the message state at the instant of expiry; whether unsending the live location message or deleting the chat also stops sharing.
- Contact card: the shared subject has deleted their account, has blocked me or is blocked by me, is oneself, is already a contact, or has turned off adding via contact cards; the group behind a group card has been dissolved, is full, or I have been removed.
- Poll: whether a voter's vote is kept after they leave the group; who can end the poll after the creator leaves or is removed; votes already cast after the poll message is unsent or deleted; submission at the instant of the deadline; voting on several devices at once; how a poll appears after the group is dissolved; anonymity of an anonymous poll after it is forwarded.
- Poll, encryption and platforms: when a group is end-to-end encrypted the server cannot tally votes, so whether polls are usable in encrypted groups must go into a ruling or be stated as not offered; whether desktop and web can vote and see results; the degraded display when a lower version receives a poll and the end system message; whether automatic end at the deadline inserts a system message (list under "Defaulted to recommendation"); in a large group results refresh in real time only for polls visible on screen, and the named list loads in pages; display of 0 votes and a tie for first after ending.
- Emoji: an added sticker pack is taken down or unavailable in the region; the original file of a favorited emoji has expired; the other party's version does not support a new type of emoji (see MISC-17).
- File: unsent, deleted, or disconnected during download, and whether to resume; opening again after the local file is deleted; one device has downloaded, and the state on the other device.
- Formatting: how spoiler content appears in notification previews, chat list summaries, quote blocks, and forwarding (it must not leak in notifications); editing a formatted message; pasting formatted text from another app.
- Link card: tapping send while fetching; fetch timeout; web page with no title or no image; short links and redirects; the web page going offline or its content changing after sending; encrypted chats; whether the card is kept when forwarding and quoting.

## Anti-patterns
| Vague or wrong | Correct | Reason |
|---|---|---|
| "Supports sending location" | Write static location and live location separately: entry, message form, location failure, and permission denied | The privacy impact of the two kinds of location is entirely different |
| "Can share live location" | Write the duration tiers, stop entry, what the other party sees after expiry and after stopping, background updates, and in-group visibility scope | Location is highly sensitive data, and unclear boundaries are a privacy incident |
| Live location offers "share indefinitely" with no unified stop entry | A finite duration, plus one "Stop all" that lists all chats currently sharing | Users forget which chats they are sharing in |
| A contact card directly carries a third person's phone number | Carry only avatar, nickname, and account identifier, and let the shared person turn off adding via contact cards | A third person's information is spread without their consent |
| "Supports polls" | Write single or multiple choice, anonymity and who sees vote details, deadline, changing votes, ended state, and reminders | A poll is a shared state in the group with many settings |
| A named poll gives no hint in the poll area | State before voting "Named poll, members can see your choice" | Voters think it is anonymous and expose their position |
| A message cannot be sent or spins forever when the link preview cannot be fetched | When the preview fails, degrade to a plain link and send as usual | A preview is an add-on capability and cannot block the main flow |
| Spoiler text shown in plain in notifications and chat summaries | Use a placeholder in notifications and summaries and do not show spoiler content | The point of a spoiler is to cover it first |
| Emoji described only as "Add to emoji" | Write the size cap, failure reason copy, favorites cap, and multi-device sync | There are many reasons an add can fail, and writing it vaguely yields one "Add failed" |

## Calibration sample
The feature most easily written vaguely: sharing live location. Tapping "Start sharing" has three preconditions, "location permission", "network", and "whether this chat is already sharing", so start a decision chain, none of which depend on a server response. The form was fixed at product framing as one-way sharing (the creator sends their live location to the chat for a selected duration); the selectable durations, the unified stop entry, and the update-time copy are written as body text per recommendation and convention, with values in the card illustrative; background updates and what the sharing counterpart sees in groups and after it ends are privacy must-asks, so leave placeholders in the card.

Description:
1. Entry: the chat page attachment panel "Location", and "Share live location" at the bottom of the location page; after one of "15 minutes" / "1 hour" / "8 hours" is selected, the "Start sharing" button lights up, and it is grayed out when none is selected; no indefinite option is offered
2. On tap, check in order:
   a. 1-Location permission check: whether this app has obtained location permission
      i. Authorized: go to the next check
      i. Never requested and allowed in the system authorization dialog: go to the next check
      i. Never requested and denied in the system authorization dialog: stay on the location page
      i. Previously denied: dialog prompt: "Location permission is required to share live location, and can be enabled in system settings", buttons "Go to settings" / "Cancel"; tapping "Go to settings" jumps to this app's permission page in system settings, and tapping "Cancel" closes the dialog and stays on the location page
   a. 2-Network check: whether there is a network now
      i. No network: toast prompt: "Network unavailable, check your network and try again", stay on the location page
      i. Has network: go to the next check
   a. 3-Duplicate sharing check: whether I am already sharing live location in this chat
      i. Already sharing: toast prompt: "You are already sharing live location in this chat", return to the chat page and locate that location message
      i. Not sharing: send the live location message and return to the chat page
3. While sharing: my side's message shows "Sharing live location", the remaining duration, "Extend" and "Stop sharing"; tapping "Extend" picks one more tier from the same three, timed afresh from the tap; the other party's side shows "{nickname}'s live location" and "Updated {N} minutes ago", and "Just updated" when under 1 minute
4. Background: {TBD: whether updates continue after the app goes to the background or is closed, recommended: continue updating in the background, and stop sharing after the app is terminated}
