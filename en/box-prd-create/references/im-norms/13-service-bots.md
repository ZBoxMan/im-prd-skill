# Service accounts, bots, card messages and official accounts

> Applies to: read this file when a PRD involves service accounts (follow-to-subscribe, menus, push, notifications, auto-reply and customer service), chat bots (commands, buttons, in-group bots), card messages and mini-program cards, official verification, and platform system chats. When the product already has a service account PRD, for service account requirements check that source of truth first, and on conflict the source of truth prevails. For evidence see evidence/13-service-bots.md.

## Baseline (follow by default, high confidence)
- **[BOT-01] No proactive outreach without an established relationship**: before the user follows, adds or starts, a service account or bot cannot initiate a message to that user; the user must first establish the relationship or give explicit consent (consent may be obtained outside the app). Must define: how the relationship is established (follow, add, tap "Start", authorize); what the chat bottom shows when no relationship exists (e.g. a "Follow" or "Start" button in place of the input box); the first message after the relationship is established see BOT-13; notification rules outside the window see BOT-11. | Magnitude: n/a | Confidence: High
- **[BOT-02] The user can deactivate unilaterally**: the user can unfollow, delete or deactivate a service account or bot at any time, after which that account cannot send the user any message; the operator receives an event that the user deactivated. Must define: entry location (profile page, chat settings, left swipe in the list); confirmation dialog copy (a dangerous action needs a second confirmation stating the consequence of deactivation); what happens to the chat and history after deactivation see BOT-25; which level of user identity the deactivation event carries see BOT-26; whether outreach can resume immediately after re-following; whether the person's own multiple devices sync. | Magnitude: n/a | Confidence: High
- **[BOT-03] Explicit identity marker**: service accounts and bots carry a type marker on the profile page and in the chat, distinguishable from human accounts. Must define: the marker form and where it appears (profile page, chat title, search results, group member list); whether the type marker replaces online status and last seen; the official verification marker see BOT-17; the distinction between auto-reply and human support see BOT-29; the marker when a bot sends AI-generated content see AI-03. | Magnitude: n/a | Confidence: High
- **[BOT-04] The chat has a menu or command entry**: service account and bot chats provide a fixed menu or command list in the input area, where a tap triggers the corresponding action. Must define: menu levels and the per-level item cap; menu name length limit and truncation of over-long names; how the menu and the input box switch; how long until a menu change takes effect for users who already follow; the input area form when there is no menu; whether tapping a menu item leaves a user message in the chat see BOT-30. | Magnitude: about 3 at the first level, about 5 under each first-level item; dozens to about a hundred commands | Confidence: High
- **[BOT-05] Button types are explicitly distinguished**: buttons attached to a card or message fall into at least two types, "open a page or link" and "post back to the service account", and the type determines where a tap goes. Must define: the button count cap and layout per card; button copy length limit; the feedback after a post-back see BOT-14; who can tap in a group (everyone, only specified members, only admins); the prompt when the current client does not support the button type. | Magnitude: single digits to about 25 per card | Confidence: High
- **[BOT-06] Fixed card structure**: a card message consists of a title, a cover or body, and a tap area or buttons, and tapping enters the corresponding page. Must define: whether each field is required and its default (e.g. the title defaults to the source name); field length limits; the source marker (service account name or mini-program name) and where tapping it goes; the chat list summary placeholder see LIST-06; whether it can be forwarded, supplementing the non-forwardable list in ACT-03. | Magnitude: title and body from dozens to around a thousand characters | Confidence: High
- **[BOT-07] Confirm or authorize before opening third-party content**: before opening a mini-program or external page from a card, menu or button, show a confirmation or authorization dialog stating what will be opened. Must define: confirm every time or only the first time; authorization items (identity information, phone number, location, camera, etc.) item by item or as a whole, identity information scope see BOT-26; where a refusal goes; where authorization can be revoked, and how already obtained data is handled after revocation (within the scope of data deletion, treat as must-ask); risky link interception see SAFE-14. | Magnitude: n/a | Confidence: High
- **[BOT-08] Expired cards are kept with the reason stated**: when the content a card points to has expired, been taken down or does not exist, the card stays in the chat and a tap gives the reason, never disappearing silently. Must define: the copy for each reason (expired, taken down, does not exist, no permission); whether an expired card changes to an expired style; whether an expired card can be forwarded or saved to favorites. | Magnitude: n/a | Confidence: High
- **[BOT-09] The platform system chat is separate**: the platform's own system notifications (security alerts, login alerts, service notices) go into a separate official chat, distinguished from service accounts and ordinary chats. Must define: whether the system chat can be replied to (read-only or replyable); whether it can be deleted, muted, or blocked see BOT-28; whether security notifications still alert under mute; the anti-forwarding hint for verification-code content see SAFE-15; how new notifications reappear after the system chat is deleted. | Magnitude: n/a | Confidence: High
- **[BOT-10] Report entry on the profile page**: the profile page of a service account or bot provides a report entry. Must define: the report form see SAFE-09; whether chat content is attached see SAFE-28; whether report and unfollow or block can be done together see SAFE-10; entry coverage for the reported object see SAFE-11; handling when the reported account has been deleted or taken down. | Magnitude: n/a | Confidence: High

## Conventions (default-OK, mark as suggested)
- **[BOT-11] Two tiers of outreach**: within a short window after the user interacts, the service account may reply freely; outside the window it can only send platform-reviewed notification templates, subject to frequency limits. Must define: which actions open the window (sending a message, tapping a menu, following, scanning a code) and each one's window duration and message count; whether a user message after the window expires resets it; template review and categories (transaction, reminder, marketing); push frequency see BOT-23; what the operator and the user each see when blocked for exceeding the frequency or the window. | Magnitude: window from minutes to 48 hours, single-digit replies within the window | Confidence: Medium (windows have direct evidence from three products, templates and frequency from two products each, and one product has no window as a counterexample)
- **[BOT-12] Opt out without unfollowing, and recoverable**: the user can refuse a service account's proactive pushes without unfollowing and can resume receiving later. Must define: opt-out granularity see BOT-24; opt-out entry (profile page switch, long-press menu on a notification message); the difference between opt-out and mute (mute only silences alerts while messages still arrive, see LIST-02); whether the operator receives a send failure after opt-out (what the other party can perceive, treat as must-ask); whether pushes during the opt-out period are backfilled after resuming. | Magnitude: n/a | Confidence: Medium (opt-out has direct evidence from three products, recoverability from two, and one product can only deactivate as a whole as a counterexample)
- **[BOT-13] Welcome message after following**: after the user follows or adds, the service account or bot may send a welcome message immediately without the user speaking first. Must define: whether the welcome message is mandatory and its default content; whether it is sent again on re-follow; whether the welcome message uses up the in-window message count. | Magnitude: n/a | Confidence: Medium (direct evidence from two products; another product uses the user tapping "Start" to trigger the first message instead)
- **[BOT-14] Immediate feedback on button taps**: after tapping a post-back button, give a toast, a dialog or a change in button state; buttons that cannot be tapped show a disabled state. Must define: the timeout prompt when the service account does not respond; whether repeated taps are ignored; whether a tapped button changes to a tapped state and its copy; the prompt copy when the client does not support it. | Magnitude: n/a | Confidence: Medium (direct evidence from two products)
- **[BOT-15] Processing state**: while the bot or service account processes a request, the chat shows a state such as "typing" or "generating". Must define: the state copy; the maximum display duration; the prompt after timeout (e.g. service temporarily unavailable); whether the user can stop generation midway. | Magnitude: n/a | Confidence: Medium (direct evidence from two products)
- **[BOT-16] Adding a bot to a group requires permission**: adding a bot to a group needs group owner or admin permission, or the group setting opens it to members. Must define: whether it is merged into the same permission item as inviting human members (GRP-06); whether joining and removal leave system messages in the group (the trace rules for group profile changes see GRP-29); the per-group bot count cap and the over-limit prompt; the prompt when a bot declares it does not support joining groups; the in-group read scope see BOT-22. | Magnitude: n/a | Confidence: Medium (direct evidence from two products)
- **[BOT-17] Verification marker is granted by the platform and revocable**: the official verification marker can only be granted through platform review, and an account cannot set it itself; it can be revoked when conditions are no longer met. Must define: verification conditions; where the marker is shown (profile page, chat title, search results); whether followers are notified after revocation; whether unverified accounts can be found in search. | Magnitude: n/a | Confidence: Medium (direct evidence from two products)
- **[BOT-18] Stateful card (if provided)**: the service account can update the state on the original card (e.g. "In progress" becomes "Ended") without sending a new message. Must define: the state list and allowed transitions; whether a final state can roll back; the duration before automatically entering the final state on timeout; how the display refreshes when the state changes while the user is viewing. | Magnitude: auto-end at hours to days | Confidence: Medium (direct evidence from two products, with one product's non-editable templates as a counterexample)
- **[BOT-19] Sharing requires user confirmation**: a share initiated by a service account or mini-program is confirmed by the user after choosing the target and seeing a preview, and is never sent automatically. Must define: the preview content; the target selection cap (see ACT-19); for reference: do not make sharing a condition for unlocking features (one product, a platform operations rule). | Magnitude: n/a | Confidence: Medium (direct evidence from two products)
- **[BOT-20] Unsupported clients guide to a capable client**: when the current client (e.g. desktop) cannot open a type of card, show a prompt and guide the user to a client that can; the fallback copy for too-old versions see MISC-17. Must define: what each client can do; the guidance copy; the summary of that card in this client's chat list. | Magnitude: n/a | Confidence: Medium (direct evidence from two products; another product only states that desktop cannot view)
- **[BOT-21] Mute for service account chats**: See LIST-02; silencing and unread accumulation during mute follow NOTI-04, and this entry only states that it also applies to service account chats.

## Divergences (ask Box on must-ask; write default-OK per recommendation and list it)
- **[BOT-22] Scope of messages a bot can read in a group**: Option A: by default receives only messages related to it (@ it, commands sent to it, replies to it), the group owner or admin can open it up to read all, and after opening up members can see the read scope on the bot's profile page / Option B: reads all group messages by default, with a prompt in the group when it joins / Option C: receives only messages that @ it, cannot be opened up. Whether a bot that is an AI can read in an encrypted group see AI-14. Recommended: A. Rationale: privacy minimization while keeping the ability of management bots. Background: one product has direct evidence of receiving only related messages by default with admin identity able to read all, and another controls a bot's proactive push by a group switch with no direct evidence on read scope. | Level: Must-ask
- **[BOT-23] Service account proactive push frequency**: Option A: monthly broadcast count (account level), each service account broadcasts a single-digit number of times per calendar month, with replies triggered by user interaction and transaction notices not counted / Option B: 1 broadcast per day, which may contain multiple articles / Option C: dynamic rate limiting, no fixed count, adjusted by opt-out and report rates. Recommended: A. Rationale: disturbance is predictable, and the recommendation is already the more conservative option. Background: monthly single digits at two products (one of which has deactivated proactive push), once per day is another account type at one of them, dynamic rate limiting at one product; the monthly and daily values come from community posts. | Level: Default-OK
- **[BOT-24] Opt-out granularity**: Option A: a whole-service-account switch, not unfollowing, just no longer receiving proactive pushes / Option B: opt out per notification category, recoverable per category / Option C: only the marketing category can be opted out, transaction and security cannot. Recommended: follow ZYMIX's existing rules (the service account profile page already has a "Receive notifications" switch); if that switch only controls alerts and is equivalent to mute, take A for opt-out. Rationale: fewest entries and lowest user comprehension cost. Background: A, B and C at one product each. | Level: Must-ask
- **[BOT-25] Chat, history and operator data after unfollowing**: Option A: the chat and history are kept on this device, can be deleted manually, and continue in the original chat after re-following / Option B: unfollowing deletes the chat and local history / Option C: the chat is removed from the list but history is kept, and restored after re-following. The operator side is decided separately: whether the operator must delete that user's profile and records after unfollowing (one product's developer documentation explicitly requires deletion). Recommended: A, with the operator side required to delete. Rationale: recoverable on the user side, privacy and data minimization on the operator side. | Level: Must-ask
- **[BOT-26] User identity information a service account or bot can obtain**: Option A: only gets an anonymous identifier isolated per service account, with nickname, avatar, phone number etc. requiring the user's item-by-item consent in an authorization dialog, and deactivation and opt-out events also carry only that identifier / Option B: gets the public nickname and avatar by default, the rest authorized item by item / Option C: gets the account identifier (including phone number) by default. Recommended: A. Rationale: privacy minimization, the same user cannot be linked across different service accounts. Background: A at two products, B at one (inferred), C at one (phone number visibility inferred). | Level: Must-ask
- **[BOT-27] Where service account chats land in the list**: Option A: each service account enters the main list as an ordinary chat / Option B: all collected into a collapsed "Service accounts" entry that shows the latest summary (the data and entry rules of the collection area see LIST-03) / Option C: notification-type (transaction, booking) ones gathered into one "Service notifications" chat, with the other service accounts collected into the collapsed entry. Recommended: follow ZYMIX's existing rules; if none, take B. Rationale: user comprehension, service account messages do not crowd out one-on-one and group chats. Background: A at one product, B at two, C at two (coexisting with B). | Level: Default-OK
- **[BOT-28] Whether service accounts, bots and system chats can be blocked**: Option A: service accounts and bots use "Unfollow" or "Delete" instead of block, with no separate block; the system chat cannot be blocked or unfollowed, only muted / Option B: service accounts and bots can be blocked (behavior after blocking see REL-07, block list management see REL-09), the system chat cannot be blocked / Option C: all, including the system chat, can be blocked. Recommended: A. Rationale: user comprehension, a service account has no human counterpart, unfollowing already fully stops outreach and a separate block is a duplicate entry; the system chat carries security alerts and must not be silenced. Background: blockable at two products, unfollow or delete at two, and whether the system chat can be blocked has no direct evidence at any product. | Level: Default-OK
- **[BOT-29] Distinguishing auto-reply from human support**: Option A: no distinction / Option B: auto-reply messages carry an "Auto-reply" marker, and the chat offers a "Transfer to human" entry / Option C: only state in the profile page that it includes auto-reply. Recommended: B. Rationale: the user understands who they are talking to; one platform's policy requires automated replies to provide a direct path to a human. Triggering, handover and converting to a message-leaving ticket for transfer to human see SUP-15. | Level: Default-OK
- **[BOT-30] Whether tapping a button or menu leaves a user message in the chat**: Option A: none, only immediate feedback and the card may be updated in place / Option B: the button copy is sent in the chat as the user / Option C: distinguished by button type, quick-reply types leave a message and action types do not. Recommended: C. Rationale: user comprehension, a quick reply is essentially speaking on the user's behalf, and leaving messages for action types would flood the chat; a message left in a group is visible to everyone, which must be reflected on quick-reply buttons. Background: both coexist at one product, the button speaks on the user's behalf at one product, and another product only has post-back events. | Level: Default-OK
- **[BOT-31] Impersonation and scam risk marking**: Option A: not provided / Option B: service accounts and bots reported in large numbers as impersonation or scams show a risk marker and warning on the profile page and at the top of the chat (the general rule for in-place risk prompts see SAFE-14). Recommended: B. Rationale: service accounts can be registered by any entity, and impersonating an official account is the main risk. Background: direct evidence from one product. | Level: Default-OK

## Must-ask states (module-specific, supplements the general state matrix)
- Relationship state: not followed, followed, unfollowed, opted out, muted; what the chat bottom, profile page button and push each are in every state.
- Service account side anomalies: when a service account is banned, taken down, deleted, renamed or changes its verified entity, how the follower's chat, historical cards and profile page appear and whether followers are notified.
- Window and quota: a user message after the window expires; what the operator and the user each see when a push is blocked for exceeding frequency; pushes already in flight when the user opts out or unfollows.
- Cards: pointed-to content expired, taken down, nonexistent, no permission; unsupported on the current client; version too old; card state updates while the user is viewing; whether identity and authorization are re-run when opening a card that was forwarded into someone else's chat.
- Buttons: service account not responding or timed out; repeated taps; tap by a member without permission in a group; the card holding the button has been updated or unsent.
- In-group bots: what members can perceive when a bot is removed, muted, the group is dissolved or the read scope changes; whether bots can trigger each other into a loop.
- Authorization: refusing authorization on first open; the entry to revoke after authorization; how already obtained data is handled after revocation.
- Multi-device: when other devices sync after one device unfollows, opts out or authorizes; cards the desktop cannot open.
- System chat: whether security notifications still alert under mute; how new notifications appear after the system chat is deleted.

## Anti-patterns
| Generic/wrong | Correct | Reason |
|---|---|---|
| "Users can receive service account messages after following" | Write the relationship-establishing action, the chat bottom when not following, the welcome message, the unfollow confirmation and what happens to history | Following is the precondition for outreach, and the states before and after on both sides must be defined |
| "Service accounts can push messages to users" | Write the in-window reply and out-of-window notification tiers separately, with the frequency cap, over-limit handling and the opt-out entry | Uncapped push turns a service account into a source of harassment |
| Mute, opt-out and unfollow conflated | Keep the three separate: mute only silences alerts; opt-out stops proactive pushes but keeps the follow; unfollow stops all outreach | Users think they turned off alerts but are still pushed, or the reverse |
| "Bots can join group chats" | State who can add, which messages it can read, whether members can see the read scope, and whether joining and removal leave a trace | The in-group read scope directly concerns the privacy of all members |
| Cards drawn only in the normal state | Add the cards and tap prompts for expired, taken down, nonexistent, client unsupported and version too old | Expired cards are the most frequent edge case of card messages |
| "Tapping a card opens a mini-program" | State the confirmation or authorization dialog, the authorization items, where a refusal goes and the revocation entry | Leaving the chat for third-party content must be made known to the user |
| "Service accounts can get user information" | State which level of identifier is obtained by default, which need item-by-item authorization, and what happens to data after deactivation | Leaking identity information is irreversible |
| A bot with exactly the same avatar and nickname as a human | The profile page and chat carry a type marker, with auto-reply marked separately | Users need to know whether the other side is human |

## Calibration sample
The feature easiest to write too generically: unfollowing a service account. After the tap there are only two steps, "confirm or not" and "whether the request succeeded", so no decision chain. The confirmation copy, failure prompt and multi-device sync are written into the body per recommendation, and the copy in the card is illustrative; what happens to the chat and history after unfollowing falls under data deletion scope, and which user identity the operator can recognize falls under what the other party can perceive, both must-ask, so the card leaves placeholders.

Description:
1. Entry: "Unfollow" at the bottom of the service account profile page; when not followed, the same position shows "Follow"
2. After the tap, a dialog prompt: "Unfollow {service account name}? You will no longer receive its messages and notifications", buttons "Unfollow" / "Keep following"
3. Tap "Keep following": close the dialog, the follow state is unchanged
4. Tap "Unfollow" with no network: toast prompt: "Network unavailable. Check your network and try again"; request failed: toast prompt: "Network error. Please try again"; the follow state is unchanged in both cases
5. Unfollow succeeds: toast prompt: "Unfollowed"; the profile page button becomes "Follow"; from then on this service account cannot send me any message, including replies and notifications
6. The chat with this service account {TBD: what happens to the chat and history after unfollowing, recommended: keep the chat and history, deletable manually}; the chat's bottom input area is replaced by a "Follow" button
7. The operator receives an unfollow event, and the user information in the event {TBD: which level of user identity the operator can recognize, recommended: only the anonymous identifier isolated per service account, with no nickname, avatar or phone number}
8. All of my signed-in devices sync to the not-followed state; where the chat goes after re-following follows item 6, and the welcome message is sent again
Note: item 6 (what happens to the chat and history) and item 7 (the user identity the operator can recognize) are placeholders, to be finalized before writing
