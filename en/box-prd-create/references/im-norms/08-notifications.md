# Notifications (Push, Mute Penetration, Badge)

> Applies to: PRD requirements for push previews, notification settings pages, mute and @mention/reply penetration, badge counts, multi-device push, and incoming-call and missed-call notifications. For mute markers and unread presentation on the chat list see 03-chat-list.md. Evidence in evidence/08-notifications.md.

## Baseline (follow by default, high confidence)
- **[NOTI-01] Layered notification settings**: a global master switch and alert sound switch + per-chat exceptions (which can override the global). Must define: whether sub-items are grayed out when the master switch is off; the per-chat exception entry; whether a one-tap restore to defaults is offered, and its confirmation copy and scope (whether it clears each chat's customizations). | Magnitude: — | Confidence: High
- **[NOTI-03] Preview control**: provides a control for "whether to show message content in notifications", and a tier of "do not show content" exists; when content is not shown the notification shows only the chat name or generic copy. Must define: the number of tiers and their copy (see NOTI-23); scope of effect (global, by chat type, single chat); whether lock screen and unlocked states are treated differently. | Magnitude: two to three tiers | Confidence: High
- **[NOTI-04] Silent by default during mute**: no notification pops up, no sound, no vibration; messages are stored as usual and unread keeps accumulating. Must define: whether notifications generated during the silenced period are re-sent after expiry. | Magnitude: — | Confidence: High
- **[NOTI-07] Badge is controllable and its basis explicit**: the badge count is an unread summary with an explicitly stated basis; the user can turn off the badge. Must define: counting unit (see NOTI-25); whether muted chats are counted, see NOTI-26; the chat types counted (whether chat-list ad items are counted, see ADS-07); truncation beyond a threshold. | Magnitude: — | Confidence: High

## Conventions (default-OK, mark as suggested)

- **[NOTI-05] @mention penetration is configurable**: whether a message that @me still notifies under mute is decided by a user setting and is not hardcoded; for the switch default see NOTI-20. Must define: whether an @ notification uses copy independent of ordinary messages and what that copy says; whether @all uses the same switch (see NOTI-21); whether replies use the same switch (see NOTI-22). | Magnitude: — | Confidence: Medium (two products have direct evidence of configurable; one product has mentions penetrate group mute fixedly and cannot be turned off separately, a counterexample)
- **[NOTI-02] Set separately by chat type**: at least distinguish notification preferences for one-on-one and group chats (whether to remind, preview, pop up). Must define: the dimensions set separately; whether group settings cover all groups; the initial inheritance of a newly created chat. | Magnitude: — | Confidence: Medium (two products have direct evidence, another is weaker)
- **[NOTI-08] Call alerts are independent of message alerts**: incoming calls have an alert sound setting independent of messages; a missed call leaves a call-record system message in the chat that can be traced at any time and is not lost because of mute or a focus period. Must define: the call alert sound entry; the missed-call record copy (see MISC-04); for incoming calls to muted chats and muting calls for a single group see NOTI-30. | Magnitude: — | Confidence: Medium (each of the two clauses has direct evidence from two products)
- **[NOTI-06] Duration-based mute automatically restores on expiry**: mute set by duration automatically restores notifications at the due time, with no user action. Must define: whether there is a prompt before expiry; how notifications for unread already present at the moment of expiry are handled. | Magnitude: — | Confidence: Medium (two products have direct evidence, another is inferred from tier semantics)

## Divergences (ask Box on must-ask; write default-OK per recommendation and list it)
- **[NOTI-20] Default for @me penetration**: Option A: not penetrating by default, the user must turn on "still notify when @me" / Option B: penetrating by default, the user can turn it off. Recommended: A. Rationale: user comprehension, since the literal meaning of "mute" is not being disturbed, and penetration is the user's active choice. Background: defaults differ across products (one penetrates by default, two do not). | Level: Default-OK
- **[NOTI-21] Whether @all penetrates**: only one product has direct evidence (the recipient can mute @all separately while keeping @me penetration), and other products show only an independent marker and copy. Option A: does not penetrate, only an independent @ marker in the list / Option B: penetrates / Option C: a separate switch independent of @me, off by default. Recommended: C. Rationale: user comprehension, since @all is easily abused and users should be able to decide separately, and an existing product provides this separate switch. | Level: Default-OK
- **[NOTI-22] Whether replies penetrate**: when replied to (a message that quoted mine). Option A: same switch as @mention ("mentions and replies only") / Option B: does not penetrate, @ only. Recommended: A. Rationale: user comprehension, since both are "messages directed at me" and a merged switch is easier to understand; the two existing products with direct evidence both let replies penetrate the same as mentions. | Level: Default-OK
- **[NOTI-23] Number of preview tiers**: Option A: two tiers (show content / do not show content, chat name still shown) / Option B: three tiers (show name and content / name only / neither name nor content shown) / Option C: two tiers plus a separate "show notification details" switch. Recommended: B. Rationale: privacy and data integrity, since it must cover the scenario of "not wanting even the chat name on the lock screen". | Level: Default-OK
- **[NOTI-24] Notifications for stranger requests and one-time content**: Option A: stranger messages uniformly show "message request" without body text; one-time content uses a type placeholder / Option B: same as ordinary messages. Recommended: A. Rationale: privacy, since a sender the user has not yet accepted should not have body text previewed through notifications. | Level: Must-ask
- **[NOTI-25] Badge counting unit**: Option A: number of unread messages / Option B: number of unread chats / Option C: user-switchable. Recommended: C. Rationale: user comprehension, since both bases have users, and there is direct evidence supporting switchability. | Level: Default-OK
- **[NOTI-26] Muted chats and the badge**: Option A: not counted by default, with "include muted chats" available in settings / Option B: counted, but distinguished from ordinary chats by a different state / Option C: always counted. Recommended: A. Rationale: user comprehension, since muted chats should not push up the badge and create anxiety. | Level: Default-OK
- **[NOTI-27] Multi-device push suppression**: this round obtained only the config field names for its semantics (low confidence). Option A: when any device is using the account, delay or do not push to other devices / Option B: each device pushes independently / Option C: on top of A, add a switch for "still pop up notifications when the app is in the foreground". Recommended: A. Rationale: user comprehension, avoiding repeated reminders from other devices beyond the one already being looked at. When A is adopted, "in use" must be written as a measurable basis: the window is in the foreground and there was an action within the last few minutes; looking only at whether the window is minimized makes a user who walked away from the computer miss messages on the phone. | Level: Default-OK
- **[NOTI-28] Notification merging**: this round did not obtain each product's merging rules (not evidenced). Option A: multiple notifications from the same chat merge into one and accumulate "{n} new messages" / Option B: shown one by one. Recommended: A. Rationale: user comprehension, avoiding the lock screen being flooded by the same chat. | Level: Default-OK
- **[NOTI-29] Notification profiles (focus mode)**: Option A: not offered / Option B: nameable notification profiles that set the chats allowed during the period and whether @mentions are allowed (name length magnitude a few dozen characters). Recommended: A. Rationale: user comprehension, since only one product has direct evidence and it overlaps in responsibility with the mute tiers. | Level: Default-OK
- **[NOTI-30] Incoming calls to muted chats**: Option A: calls are unaffected by chat mute and still ring (still subject to the system's do-not-disturb) / Option B: affected, leaving only a missed-call record / Option C: message mute and call mute are two separate switches (a group can mute calls separately), and calls still ring by default. Recommended: A. Rationale: accessibility and recoverability, since calls are time-sensitive and cannot be remedied after being silenced; option C has direct evidence from only one product and is an extension of A. | Level: Default-OK
- **[NOTI-31] Penetration for specially followed members**: Option A: not offered / Option B: in a group a given member can be set as "specially followed", whose posts penetrate mute, restored after canceling. Recommended: A. Rationale: user comprehension, since only one product has direct evidence and it overlaps with the @mention penetration feature. | Level: Default-OK
- **[NOTI-32] Notifications for reactions (emoji reactions)**: Option A: no notification / Option B: notify, can be turned off separately, and the preview can be controlled separately. Recommended: B. Rationale: user comprehension, since reactions to one's own messages are meaningful feedback, but it must be possible to turn off. | Level: Default-OK
- **[NOTI-33] Notification placeholder for protected chats** (applies only when "locked chats" are built, see LIST-31 in 03-chat-list.md): Option A: notifications of locked chats show only generic copy ({app name}, or "{app name}: 1 new message") and not the sender or content / Option B: follow the global preview tier. Recommended: A. Rationale: privacy, since the purpose of locking is not to expose the chat's existence and content, and a notification preview would defeat the lock; only one product has direct evidence. | Level: Default-OK

## Must-ask states (module-specific; supplements the general state matrix)
- Other party has blocked/deleted account: whether content they send after being blocked still produces notifications; whether notifications already shown are kept after deletion.
- Left or removed from a group: whether queued notifications for the group are cleared; whether @me notifications are kept.
- An archived or muted chat receives @me or a reply: whether it still notifies, whether it returns to the main list, whether the list shows @.
- Multi-device: after another device has read, whether notifications already shown on this device are cleared automatically; when a mute change on one device takes effect on others (one product is known not to sync mute settings to linked devices, and the desktop still pops notifications).
- Offline recipient: for notifications accumulated while offline, whether they are shown merged or re-sent one by one after coming online; how long a push delay counts as expired.
- Message unsent or edited: after the notification is shown, whether its content updates or is removed accordingly.
- Notification permission turned off by the system or revoked during use: presentation and guidance on the settings page; whether the app still has unread prompts.
- Lock screen and unlocked: whether preview tiers distinguish lock screen from unlocked; whether notifications state the account when there are multiple accounts.
- Group versus one-on-one differences: the same person messaging separately in a one-on-one chat and in a group, with mute taking effect independently for each; being @ed at the moment just before mute expires.
- Weak network: copy and destination on tap when the push arrives but fetching the message fails.
- Receiving a new message during a call: whether message notifications are downgraded to silent.
- Locked chats (if NOTI-33 is chosen): what notifications show on the lock screen and after unlock; whether incoming-call notifications for locked chats are likewise hidden.

## Anti-patterns
| Vague/wrong | Correct | Reason |
|---|---|---|
| "No notifications after mute" | State the silenced items during mute (pop-up, sound, vibration, badge) and the penetrating items (@me, reply, call) | Penetration or not is the point users complain about most |
| "Badge shows the unread count" | State the counting unit, whether muted chats are counted, the chat-type scope and the truncation threshold | The basis is unclear, and badge and list do not match |
| "Notifications show message content" | State the preview tiers, scope of effect, lock-screen versus unlocked difference, and placeholders for strangers and one-time content | The privacy leak surface is unclear |
| "Notify when @ed" | State the switch default, whether @all and replies share the switch, and the independent copy | Conflicts with mute priority |
| "Multi-device notification sync" | State clearing notifications after read, the suppression rules, and the boundary of per-device independent settings | Repeated reminders across devices |
| "Ring on incoming call" | State the relation to message mute, the missed-call record, and the fallback when permission is revoked | A missed call cannot be remedied |
| "Tap the notification to enter the chat" | State where it goes when the chat is deleted, left, archived, or the account is logged out | The landing point after tapping is undefined |

## Calibration sample
The feature most easily written vaguely: the "Still notify when @me" switch in a muted group chat. The following is the body of a qualified annotation card (there is no condition to check before tapping the switch, so no decision chain). This example has no must-ask item: the switch default, whether @all and replies share the switch, and multi-device sync are all written as body text per recommendation and listed one by one under "Defaulted to recommendation" in the delivery draft.

Description:
1. Display condition: after a group chat is muted, the switch "Still notify when @me" is shown in the group chat settings; group chats not muted and one-on-one chats do not show this switch
2. Default state: off
3. Tapping the switch toggles between on and off, takes effect immediately on this device, and syncs to all devices this account is logged in on
4. When on: during mute, messages that @me or reply to me (quoting my message) still push a notification, with copy "{sender} mentioned you in a group chat" or "{sender} replied to you"; other messages stay silent
5. When off: messages that @me and replies are silent like other messages; the chat list still shows the @ marker, and unread keeps accumulating
6. Messages that @all are not controlled by this switch, but by the separate "Still notify when @all members" switch on the same page, which is off by default
7. After mute is turned off this switch is hidden; when mute is turned on again, the previous switch state is restored
