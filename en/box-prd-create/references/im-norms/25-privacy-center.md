# Privacy compliance center (re-consent, consent management, data export and deletion, collection and sharing lists)

> Applies: read this file when the PRD involves notice and re-consent after terms and privacy policy updates, withdrawable consent items, download my data, delete my data and its relation to account deletion, personal information lookup and correction, channels for exercising data rights, system permission presentation on the privacy page, the personal information collection list and third-party sharing list, or the overall structure of the privacy settings page. For privacy visibility settings see REL-14, REL-24, REL-25; for permission requests and guidance after denial see DISC-01, DISC-02; for the account deletion method see ACC-21; for the balance at account deletion see WAL-18; for the data export cooldown see MISC-30; for AI data processing see AI-12, AI-13; for personalization consent see ADS-14, ADS-15; for age judging and confirmation data see AGE-07, AGE-10; for whether export is allowed during a penalty see ENF-14. Legal provisions live only in evidence; modules and cards always write "per launch-region compliance requirements" and write concrete values as {TBC}. Evidence is in evidence/25-privacy-center.md.

## Baseline (follow by default, high confidence)
- **[PRIV-01] Consent-based processing can be withdrawn**: Every data processing that depends on user consent (such as contacts upload, AI memory and improvement, personalized recommendation, saving payment information) can be withdrawn by the user. Must define: this product's list of consent-based processing items (contacts upload method see DISC-18); withdrawal completed item by item in the app (see PRIV-28); the feature state after withdrawal; handling of already collected data after withdrawal (treat as must-ask, see PRIV-13; contacts see DISC-21); whether the withdrawal result syncs across devices. | Magnitude: N/A | Confidence: High
- **[PRIV-02] Provide a channel for exercising data rights and state it in the privacy policy**: Requests to access a copy, correct, delete, object to or restrict processing have a clear intake channel (in-app form or a privacy mailbox), and the privacy policy states the channel. Must define: where the in-app entry is; which request types can be submitted; how the user's identity is verified before submitting; response time limit and conditions for extension (per launch-region compliance requirements, {TBC}); whether reasons are given and remedies pointed out when a request is not handled (per launch-region compliance requirements); how the user is notified during handling and of the result. | Magnitude: N/A | Confidence: High
- **[PRIV-03] Own profile data can be viewed and corrected by the user**: Own profile fields such as nickname, avatar, bio and birthday can be viewed and changed directly in the app without an application. Must define: the list of fields that cannot be self-corrected, or need verification or an application (changing the phone number goes through the verification flow; for birthday change count and threshold crossing see AGE-12); when changes sync across devices; whether viewing "other data the platform holds" goes through export (see PRIV-07) or a separate browsing page. | Magnitude: N/A | Confidence: High
- **[PRIV-04] Disclose sharing recipients and purposes by category**: The privacy policy states by category which third parties personal data is shared with (service providers, payment institutions, authorities as required by law, bots the user actively interacts with, etc.) and each purpose. Must define: the list of recipient categories; whether it states that user data is not sold; whether specific service providers are named; whether cross-border transfer and the regions are involved (per launch-region compliance requirements, {TBC}); whether the app also provides a structured list (see PRIV-20); who is responsible for checking consistency with the app marketplace privacy labels. | Magnitude: N/A | Confidence: High
- **[PRIV-05] Account deletion can be initiated in the app**: The deletion entry is in the app and cannot be only a support or email channel. Must define: the entry path (per the ZYMIX production path); the web deletion request entry outside the app (one app marketplace's developer policy requires that an app allowing account creation must, besides the in-app entry, provide a web page for submitting account and data deletion requests without reinstalling the app, checked against the policy text online on 2026-10-31; per the launch marketplace's requirements); the deletion method (see ACC-21); the deletion scope and retention exceptions stated on the deletion confirmation page (see PRIV-08); whether a prompt to export first is shown before deletion (see PRIV-07); which devices can initiate it (primary device only or any signed-in device). | Magnitude: N/A | Confidence: High

## Conventions (default-OK, mark as suggested)
- **[PRIV-28] Withdrawal is completed item by item in the app**: Every consent-based processing item (see PRIV-01) can be turned off or withdrawn individually in the app without contacting support. Must define: where each item's withdrawal entry is (centralized or scattered, see PRIV-12); entry depth does not exceed the path used when the consent was given (see PRIV-09). | Magnitude: N/A | Confidence: Medium (direct evidence from two products; another product has only a policy sentence "can withdraw anytime" with no in-app per-item display, not counted)
- **[PRIV-06] Major updates to terms or privacy policy are announced in the app**: A major update is announced with an in-app dialog or system notification stating the effective date and a summary of changes, with the full text openable. Must define: the criteria for a "major update" (new collection categories, new purposes or sharing recipients, changes to how rights are exercised, etc.); the notice vehicle and when it is shown (at sign-in, after a version update, some days before taking effect); whether old versions can be viewed; whether explicit consent is needed, see PRIV-10; what the consent record retains (version number, time, device); the advance notice in days (for reference: about 30 days, reference only). | Magnitude: N/A | Confidence: Medium (direct evidence from two products; another product only writes "notify when appropriate", and one product only updates the date)
- **[PRIV-07] "Download My Data" is self-service export, generated asynchronously with a notification**: An export entry is provided in settings; after submission it is generated in the background, the user is notified on completion, then it can be downloaded within a time limit. Must define: export scope (treat as must-ask, see PRIV-14); identity verification before requesting and downloading; security cooldown and all-device reminder see MISC-30; generation time and download validity (see PRIV-15); file format (for reference: a human-readable web version plus a machine-readable JSON version); a "contains personal private information" prompt in the file or on the download page (reference only, direct evidence from one product); whether the request is voided when the number is changed or the account deleted during the request (reference only, direct evidence from one product); which devices can initiate it; wallet transaction details are not in this export, see WAL-30. | Magnitude: generation takes hours to days | Confidence: Medium (direct evidence from three products, one product that does not provide export is a counterexample)
- **[PRIV-08] The deletion notice states retention exceptions and the effect on others**: The confirmation page for account deletion or data deletion states: which data is retained for legal or security needs and for how long, how long thorough clearing takes, and that message copies in the other party's hands and in-group content are unaffected. Must define: retention categories and periods (per the current ZYMIX privacy policy; anything it does not state is {TBC}); thorough clearing time limit (for reference: up to about 90 days, backup copies counted separately); how the account appears to others during clearing; handling of the user's own sent content on others' side (see PRIV-17). | Magnitude: thorough clearing takes tens of days up to 90 days | Confidence: Medium (retention exceptions have direct evidence from two products, not affecting others' copies has direct evidence from two products; the clearing time limit is reference only)
- **[PRIV-09] Withdrawing is as easy as giving, and refusal does not block unrelated features**: The path to withdraw a consent is no deeper than the path used to give it; refusing or withdrawing a consent disables only the features that depend on it, the rest work as usual; paid benefits are not conditioned on consenting to data processing. Must define: a comparison of the giving entry and withdrawal entry for each consent; the features unavailable after refusal, listed one by one; whether the explanation is shown again when re-enabled. | Magnitude: N/A | Confidence: Medium (direct evidence from one product plus platform spec)

## Divergences (ask Box on must-ask; write default-OK per recommendation and list it)
- **[PRIV-10] Consent form after terms and privacy policy updates**: Option A: explicit consent, a blocking dialog "Agree and continue" / "Do not agree", cannot continue using the app before consenting / Option B: notify only, continued use counts as acceptance, not blocking / Option C: split by the nature of the change: when a new consent-based purpose, collection category or sharing recipient is added, consent is requested separately, other changes are notified only. Recommended: C. Rationale: privacy: new purposes require consent, pure wording adjustments do not interrupt use; one product blocks explicitly, two accept by continued use, one asks per feature, and C matches the per-feature consent practice. Which changes must be re-consented per launch-region compliance requirements, {TBC}. | Level: Must-ask
- **[PRIV-11] Handling after re-consent is refused**: Option A: without consent the app cannot be used further, guide to account deletion, with a prompt to export data before deletion / Option B: the account enters a restricted state: can only view history, export data and delete the account, and can return to the consent page at any time to recover / Option C: disable only the features affected by this change, the rest work as usual. Recommended: C when the change only involves consent-based features, B when it involves the terms of service itself. Rationale: recoverable and data intact, no data lost from one refusal; opposite to the only product that offers a refusal path (refuse = delete account), a recoverability trade-off. How long the restricted state may last and how it is handled on expiry per launch-region compliance requirements, {TBC}. | Level: Must-ask
- **[PRIV-12] Entry form for consent management**: Option A: a centralized "Consent Management" page listing all withdrawable items, each stating its purpose, current state and consequence of withdrawal, and linking to the matching feature setting / Option B: scattered across each feature's settings / Option C: mostly left to system settings. Recommended: A. Rationale: users can understand the current state and withdrawal is easy to reach; one product is centralized, one is scattered, one relies on system settings. | Level: Default-OK
- **[PRIV-13] Handling of already collected data after consent is withdrawn**: Option A: stop only later processing, already collected data is handled by the retention period / Option B: withdrawal deletes the data collected solely on that consent (such as AI memory, personalization profile) / Option C: the withdrawal confirmation dialog states the consequence and offers a "Also delete collected data" option, checked by default. Recommended: C. Rationale: strictest on privacy while keeping the choice; one known product splits "stop syncing" and "delete synced data" into two steps, and C merges the two steps into one confirmation. Data already uploaded after contacts sync is turned off: see DISC-21, not in this entry. | Level: Must-ask
- **[PRIV-14] Export scope of "Download My Data"**: Option A: account information only (profile, settings, contact list, signed-in devices, the user's own feed posts, etc.), no chat history / Option B: account information plus chat history, the user checks by category / Option C: account information goes through "Download My Data", chat history goes through a separate chat export entry / Option D: account information plus messages the user sent (excluding others' messages and others' profiles; end-to-end encrypted chats are handled by the boundaries of AI-14/SAFE-22). Recommended: C. Rationale: two products export chat content and account information separately, one merges them into one export with checkboxes; chat history contains content sent by the other party, and a separate entry makes it easy to confirm chat by chat; when chat export is not built in this release use A, and the export page states that chat history is not in it. | Level: Must-ask
- **[PRIV-15] Delivery method and validity of the export**: Option A: in-app download, notification after generation, identity verified again before download, download link valid for a number of days, a new request needed after expiry / Option B: sent to a verified email / Option C: pull the generated file directly on the device, without server-side aggregation. Recommended: A. Rationale: the file contains the complete personal data, and the time limit plus second verification reduce the leak surface; the email may no longer be under the user's control. Wallet detail export is sent to a verified email (see WAL-30), and the objects differ: details are often submitted externally as proof, while the personal data package contains all categories and is only for the user's own keeping. The legal time limit for completing generation per launch-region compliance requirements, {TBC}. | Level: Default-OK
- **[PRIV-16] Whether to offer category deletion without deleting the account**: Option A: apart from each feature's own deletion, no centralized deletion is added, deleting all data equals deleting the account / Option B: the privacy center additionally offers category deletion (cloud drafts, call history, feed posts, etc.) and the account is kept. Recommended: B. Rationale: data minimization without forcing users to delete their account; two products offer single-item deletion, one treats deletion as equal to account deletion. Deleting uploaded contacts: see DISC-21, deleting AI conversations and memory: see AI-10, and the privacy center only holds the entry. The category list and whether each category can be recovered after deletion are treated as must-ask. | Level: Must-ask
- **[PRIV-17] Handling of the user's own sent content on others' side after account deletion**: Option A: kept in the other party's chats and in groups, with the sender shown as a deleted account / Option B: delete from the server the messages the user sent in one-on-one and group chats, copies already on the other party's device are unaffected / Option C: the user chooses at deletion. Recommended: A. Rationale: data stays complete and the other party's chat context is not broken; two products state that deletion does not affect copies in others' hands or groups and channels. | Level: Must-ask
- **[PRIV-18] System permissions on the privacy page**: Option A: list each system permission's current state and purpose, tapping jumps to system settings / Option B: do not list, handle only through permission guidance when a feature is triggered. Recommended: A. Rationale: users can understand the current state; one product lists them centrally, two rely only on system settings. | Level: Default-OK
- **[PRIV-19] In-app permission usage log**: Option A: not built, rely on the system-level privacy report / Option B: the app records when and for which feature each permission was read. Recommended: A. Rationale: none of the five products show an in-app log, the system layer already provides one, and duplicating it yields little. | Level: Default-OK
- **[PRIV-20] Personal information collection list and third-party sharing list**: Option A: two in-app list pages, listing by category the information collected, purposes, usage scenarios and the third parties shared with / Option B: disclose only in the privacy policy text / Option C: lists detailed down to the mapping between specific third parties and data items. Recommended: A, with third parties written to category level plus the service providers the current privacy policy already names. Rationale: users can look it up in the app without maintaining an item-by-item mapping; one product provides in-app lists, the rest rely on policy text. Whether launch regions mandate lists and their format per launch-region compliance requirements, {TBC}. | Level: Default-OK
- **[PRIV-21] Overall form of the privacy center**: Option A: a dedicated "Privacy & Data" page under "Settings", aggregating entries for visibility settings, consent management, system permissions, download my data, delete data and account deletion, the two lists, the full policy text and the rights request channel / Option B: items scattered across account settings and privacy settings. Recommended: A. Rationale: understandable and reachable for users; one product already aggregates, the rest are scattered. The "Privacy & Data" page is the original "Privacy" settings page expanded and renamed, with no second privacy page created; the whole library and cards use this name ("Settings" - "Privacy & Data"). | Level: Default-OK
- **[PRIV-22] Privacy visibility settings**: See REL-14; tiers and exceptions see REL-24, the scope of the first-release settings items see REL-25. The privacy center holds only the entry and does not set up a separate set of visibility toggles.
- **[PRIV-23] When system permissions are requested**: See DISC-01; the prompt after denial and the go-to-settings entry see DISC-02. The privacy center's permission list only jumps and does not redefine prompt copy.
- **[PRIV-24] Account deletion method and cooling-off period**: See ACC-21; automatic deletion for long-term inactivity see ACC-22, asset handling at deletion (wallet balance, unfinished payments, points, remaining membership period) see WAL-18. This module only defines the deletion scope and notice (PRIV-08, PRIV-16, PRIV-17).
- **[PRIV-25] AI-related consent items**: See AI-12 (who the content is handed to); whether it is used for training see AI-13, the first-use notice see AI-04. The consent management page only lists the state and the withdrawal entry.
- **[PRIV-26] Consent for personalized ads and recommendations**: See ADS-14; the usable data scope see ADS-15, the toggle form see ADS-16. The consent management page only lists the state and the entry.
- **[PRIV-27] Age and age confirmation data**: See AGE-07; retention of age confirmation data see AGE-10. The collection list and export scope list age-related data per their conclusions.

## Must-ask states (module-specific, supplementing the general state matrix)
- Re-consent: whether other devices still pop up after one device consents when there are several devices; going offline or a request failing while the dialog is up; multiple updates stacking without consent; accounts in the account-deletion cooling-off period, penalized or restricted that meet an update; where the version number and time of the consent record are retained.
- Withdrawing consent: whether a failed withdrawal request rolls the toggle back; multi-device sync of the withdrawal result; a related task in progress at withdrawal (such as a contacts upload); whether the explanation is shown again when re-enabled after withdrawal; whether the feature entry after withdrawal is hidden, grayed out, or prompts on tap.
- Export: applying again while a request is processing or awaiting download; canceling during the cooldown; generation failure; download link expired; resuming after an interrupted download; splitting a large file into parts; changing number, deleting the account or being penalized during the request (whether export is allowed during a penalty see ENF-14).
- Deletion and account deletion: starting account deletion while category deletion is in progress; starting account deletion while an export is in progress; whether export is possible during the cooling-off period; how local caches on other devices are cleaned after deletion; the notification when deletion completes.
- Rights requests: identity verification fails; the response time limit passes without handling; reason and remedies when a request is refused; repeated submission of the same request type.
- Lists and policy: lists staying in sync with the app marketplace privacy labels after a policy update; which version prevails when multilingual versions differ.

## Anti-patterns
| Vague/wrong | Correct | Reason |
|---|---|---|
| "Users can manage privacy in Settings" | List each withdrawable consent, its entry, the consequence of withdrawal and the handling of already collected data | "Manage" cannot be implemented, and engineering would only build an empty page |
| The deletion page says "All data will be permanently deleted" | State retention categories and periods, the thorough clearing time limit, and that others' copies are unaffected, consistent with the privacy policy | Conflicts with the policy's retention clauses and is a false notice |
| "Supports exporting personal data" | Write scope, identity verification, cooldown and all-device reminder, generation notification, validity, failure and voiding | Export is a high-risk exit for data leaving |
| A policy update only changes the date on the page | Announce major updates in the app, request consent separately for new purposes, and retain the consent record | Users cannot learn of the change, and new purposes lack a consent basis |
| Refusing consent deletes the account directly with no export prompt | The refusal path states the consequence and offers a restricted state or export-first exit | One accidental tap causes irreversible data loss |
| The withdrawal entry is buried in multi-level menus, or requires contacting support | Withdrawing is as easy to reach as giving, one step in the app | Launch regions commonly require withdrawal to be as easy as giving |
| The in-app list, privacy policy and app marketplace privacy label each say something different | Maintain all three from one source, and check them together when the policy updates | Inconsistent disclosure gets called out by marketplaces and regulators |
| Cards cite legal provision numbers | Write "per launch-region compliance requirements", write values as {TBC} and put them in Open items | Laws change, and cards write only product rules |

## Calibration sample
The feature most easily written too vaguely: download my data. Writing only "personal data can be exported" misses scope, identity verification, security cooldown, generation notification, validity and the voiding branches. After the tap there are three precondition checks, "network", "whether a request is already in progress" and "identity verification", so a decision chain is started; request status needs the server's return and goes after the network check. Export categories, cooldown and all-device reminder, delivery method, validity and file format are written as body text per recommendation, with card values illustrative; whether the export includes chat history is data scope, must-ask, so the card leaves a placeholder; the legal generation time limit is written {TBC}.

Description:
1. Entry: "Settings" - "Privacy & Data" - "Download My Data"; the "Request export" button lights up after at least 1 export category is checked
2. On tap, check in order:
   a. 1-Network check: whether the device currently has a network
      i. No network: toast: "Network unavailable. Check your connection and try again"
      i. Network available: proceed to the next check
   a. 2-Request status check: returned by server, whether this account already has an export request in progress or awaiting download
      i. Yes: toast: "You already have an export in progress. We'll notify you when it's done", stay on this page
      i. No: proceed to the next check
   a. 3-Identity verification: send a verification code to the phone number bound to this account; after it is entered the server validates it
      i. Fails: inline error "Incorrect verification code. Please try again", stay on the verification page
      i. Passes: submit the request, toast: "Request submitted", the page shows "Pending" and the estimated time it will be available to download
3. Export categories: "Account profile" / "Contact list" / "Logged-in devices" / "My feed posts" / "Privacy settings", all checked by default; chat history {TBD: whether the export includes chat history, recommended: not included, chat history goes through chat export, and the export page states chat history is not in this export}
4. Waiting period: after a successful request, generation starts only after a 12-hour wait; during it a push "Someone requested an export of your data. If this wasn't you, cancel it now" goes to all signed-in devices of this account, and tapping "Cancel request" on any device voids it
5. Generation complete: push and a platform system chat message "Your data is ready to download"; maximum time from request to availability {TBC: legal response time limit for the launch regions}
6. Download: complete identity verification again before tapping "Download"; the file is a compressed archive containing a human-readable web version and a machine-readable JSON version; the download link is valid for 7 days, the page shows the expiry time, and after expiry a new request is needed
7. Changing phone number or starting account deletion during the waiting period or generation: this request is voided automatically and the page returns to the requestable state
8. Generation failure: push "Data export failed. Please request again", the page returns to the requestable state
Note: whether the export includes chat history must be confirmed before finalizing; the legal response time limit is to be replaced after compliance answers
