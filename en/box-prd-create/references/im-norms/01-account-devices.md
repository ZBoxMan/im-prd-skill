# Account and Multi-Device

> Applies to: PRDs for sign-up and login, verification codes, two-step verification, multi-device login and device management, number change, account deletion and self-destruct features. Evidence in evidence/01-account-devices.md.

## Baseline (follow by default, high confidence)
- **[ACC-03] Two-step verification is an optional extra factor**: adds a password or PIN on top of the verification code. Must define: factor form and minimum length, whether a hint is offered, the recovery channel form and its state when not activated, how changes and turning off are confirmed, remaining-attempts copy after a wrong entry, and the migration prompt when an old PIN is upgraded to a password. | Magnitude: PIN or password minimum 4 to 6 characters, maximum a few dozen | Confidence: High
- **[ACC-04] A forgotten two-step factor must have a way out**: with no recovery channel, go through "reset after a waiting period" or "abandon history and register again"; exactly one of the two must exist. Must define: the reset method when a recovery channel exists (e.g. sending a code to the recovery channel), waiting period length and start point, whether it can be canceled during the waiting period, what the login entry shows during the waiting period, and the way out when the number is a recycled number carrying the previous owner's two-step factor. | Magnitude: waiting period counted in days, about a week | Confidence: High
- **[ACC-05] A new device must be confirmed by an existing device**: when a new device logs in or links, an existing device scans a code, taps confirm, or unlocks to verify. Must define: the confirmation method, confirmation timeout, fallback when no other device is online, whether the existing device receives an "is this you" prompt and the handling after choosing "not me", the risk prompt for unofficial entry points when linking, the confirmation duration after scanning (recommended: counted anew from the scan, not inheriting the QR code's remaining validity), the new-device info shown on the confirmation page (name, type, whether it includes city-level login region), and whether the device limit is checked on entering the confirmation page (recommended, so users do not remove a device and then have to scan again) or after tapping confirm. | Confidence: High
- **[ACC-06] Multi-device online at once must declare combinations and limit**: desktop, tablet, web and other devices besides the phone may be online at the same time as the phone. Must define: the device combinations that can coexist and the maximum count, whether primary device and linked devices are distinguished and the coexistence policy for the same device type (see ACC-23), and the prompt or replacement rule and copy when the limit is exceeded. | Magnitude: linked devices in single digits (4 to 5) | Confidence: High

## Conventions (default-OK, mark as suggested)

- **[ACC-01] Verification code resend cooldown**: resend has a cooldown, no new request is allowed during it, and resend is allowed once it ends. Must define: counting and cooldown follow whether the server actually sent (on request timeout the SMS may already have gone out, so a timeout must not release the count); counting dimensions include number, device and IP, and abnormally high frequency goes to a human-verification branch (after passing, sending continues; if dismissed, stay on this page); cooldown length, whether remaining time is shown during the cooldown, daily request cap per number, whether the old code is invalidated immediately after resend, and the channel order when the channel can be switched. | Magnitude: cooldown in seconds to minutes; daily request cap in single digits | Confidence: Medium (cooldown has direct evidence from only two products; showing remaining time during cooldown has evidence from only one product and has been moved to must-define)
- **[ACC-02] Verification code error prompts**: too many requests or attempts has its own prompt and tells the user to try later. Must define: whether "code wrong", "code expired", "too many wrong entries" and "too many requests" each have independent copy and retry timing, the wrong-entry limit, lockout duration, and the state of the input box and resend button during lockout. | Magnitude: evidence did not obtain wrong-entry limits or validity values, so no range is given; set by the PRD | Confidence: Medium ("too many attempts, try later" has only two products; separating the four prompts has evidence from only one product and has been moved to must-define)
- **[ACC-07] Device list and remote logout**: settings contain a list of logged-in devices showing device names, with removal one by one. Must define: whether this device is distinguished from other devices, whether last-active time is shown (basis is foreground use or time of an action, excluding background keep-alive, otherwise automatic expiry does not work for always-on devices), whether one-tap logout of all other devices is offered and its scope description, the next online behavior of a removed device, whether identity verification is required before removal, and whether login region is shown. | Confidence: Medium (direct evidence from only two products; distinguishing this device and one-tap logout of other devices has evidence from only one product and has been moved to must-define)
- **[ACC-08] Logout needs a second confirmation and states consequences**: a confirmation appears before logout, and its copy states the consequences. Must define: which consequences the confirmation copy states (e.g. no more new messages after logout, encrypted chats stored only on this device will be lost), and what happens to each kind of local data. | Confidence: Medium (only two products; each of the two states one kind of consequence, and the specific consequences have been moved to must-define)
- **[ACC-09] Multiple accounts on one device have a limit**: multiple accounts can be added and switched, and beyond the limit a prompt appears and no more can be added. Must define: the limit, how messages of the original account are received after switching, whether notifications of all accounts are aggregated, and the over-limit copy. | Magnitude: single digits | Confidence: Medium (only two products; the notification aggregation switch has evidence from only one product and has been moved to must-define)
- **[ACC-10] Number change keeps account and data**: changing number is a migration, not a new account; contacts, chats and settings are kept; the new number must first pass the verification code and (if any) the two-step factor. Must define: handling when the new number is already registered, when the old number is released, and whether the other party receives a change notice. | Confidence: Medium (only two products, one of which is Medium confidence; the other's body text was not read)
- **[ACC-11] A restricted account must state its scope and appeal entry**: See ENF-01. Scope: for the penalty gradient and restricted scope see ENF-01; for the appeal entry see ENF-02, for appeal eligibility, form, count and in-period data see ENF-09 to ENF-15; for restriction prompts and lift time see ENF-06, ENF-07; for disclosure of the reason see ENF-08.
- **[ACC-12] A pending item handled on one device syncs to the others**: (applies only to items requiring user action, not to pure notice notifications) after a notification, invitation or call is accepted/declined/handled on one device, other devices show "handled on another device" and are no longer actionable. Must define: the result of repeated operations during the sync delay. | Confidence: Medium (only two products, both domestic)
- **[ACC-13] A lapsed login state has a re-login entry**: when logged out by another device, the session expires, or the device is judged invalid, the current device prompts clearly and offers a "log in again" entry, does not fail silently, and does not make the user hunt for the cause on a screen where nothing can be sent; after registering on a new phone, the old device follows the same rule. | Confidence: Medium (only two products)

## Divergences (ask Box on must-ask; write default-OK per recommendation and list it)
- **[ACC-21] Account deletion method**: Option A: delete immediately after identity verification / Option B: always a cooling-off period during which logging in again cancels it / Option C: tiered by risk, users who can verify the two-step factor are deleted immediately, those who cannot take effect after a delay with a confirmation notice. Recommended: C. Rationale: balances recoverability and protection against mistaken deletion, and users who can verify identity are not delayed (accessibility and recoverability). Asset handling at deletion (wallet balance, unfinished payments, points, remaining membership period) see WAL-18, merged into one question. | Level: Must-ask
- **[ACC-22] Automatic deletion for long inactivity**: Option A: not offered / Option B: a long default period (year-level), user-adjustable, with multi-channel reminders before expiry. Recommended: A. Rationale: automatic data deletion conflicts with "data integrity", and in the existing evidence only one product adopts it; that product's approach is B, so recommending A is the opposite of existing product practice and is a data-integrity trade-off. | Level: Must-ask
- **[ACC-23] Coexistence policy for the same device type**: Option A: same-type devices coexist as equals, no primary device / Option B: one primary device plus a limited number of linked devices / Option C: same-type devices are mutually exclusive, the later login replaces the earlier. Three products adopt B (one of them by secondhand evidence, and with same-type linked devices kicking each other out), one adopts A. Recommended: B. Rationale: clear confirmation chain and good recoverability. | Level: Must-ask
- **[ACC-24] Data after resetting the two-step factor when the waiting period ends**: Option A: keep all cloud data, reset only the factor / Option B: clear account data and register again. Recommended: A. Rationale: data integrity first; if B is adopted, a dialog before the reset must state the data that will be lost. | Level: Must-ask
- **[ACC-25] Two-step verification strength**: Option A: purely optional / Option B: guided to enable after sign-up, skippable / Option C: required to be enabled before high-risk operations (number change, transferring group owner, account deletion). Recommended: B plus C. Rationale: no mandatory sign-up barrier, while protecting high-risk operations. | Level: Default-OK
- **[ACC-26] Verification code delivery channels**: Option A: SMS only / Option B: SMS plus voice call or in-app delivery / Option C: plus email. Recommended: B. Rationale: a fallback path when SMS is unreachable, for accessibility and recoverability. Background: two products offer email beyond B (that is C), and one was evidenced only for SMS; recommending B without email is a trade-off to control first-release scope. | Level: Default-OK
- **[ACC-27] Automatic expiry of inactive devices**: Option A: not offered, manual removal only / Option B: linked devices are disconnected automatically after the system's fixed idle duration (magnitude about one month) / Option C: old device sessions are terminated automatically after an inactivity duration set by the user. Recommended: C. Rationale: forgotten devices are a privacy risk, and a user-adjustable value fits different usage habits; the fixed duration or set value and the default are decided by business and listed under "Defaulted to recommendation"; when C is adopted the tiers do not include "never", only the primary device can change it, and when shortening the duration would invalidate devices immediately, a confirmation stating the number of devices is shown first. | Level: Default-OK
- **[ACC-28] Minor protection mode and age determination**: See AGE-07. Scope: for the age determination basis and defaults of accounts without completed age confirmation see AGE-07; for minimum age and whether minors are served (including minor mode) see AGE-06, for guardian capabilities see AGE-08.
- **[ACC-29] Login credentials without a verification code**: Option A: not in the first release / Option B: after two-step verification is enabled, a common device can be marked "trusted device" to reduce repeated verification / Option C: support passkeys. Recommended: A. Rationale: it would lower new-device confirmation strength (privacy and data integrity). Background: B is adopted by only one product; C by two products (one with Medium-confidence evidence); recommending A is the opposite of these two products' practice and is a trade-off that prioritizes new-device confirmation strength. | Level: Default-OK
- **[ACC-30] Encrypted chats on linked devices**: applies only when the product has end-to-end encrypted chats. Option A: linked devices can send and receive encrypted chats (each device has its own key, the sender encrypts separately) / Option B: encrypted chats are available only on the primary device, and the linked device's chat list shows a placeholder "Encrypted chats are only available on the phone" / Option C: linked devices show no encrypted chats at all. Recommended: B. Rationale: no cross-device key scheme in the first release, yet users on a linked device do not mistake the chat for lost. Background: one product's secret chats exist only on the originating device (logging out cancels all secret chats) and other devices do not show them; two other products' linked devices can send and receive encrypted messages, per public statements, not evidenced in this library. This is a scope and privacy trade-off and must not be written under "Defaulted to recommendation". | Level: Must-ask

## Must-ask states (module-specific; supplements the general state matrix)
- Verification code: whether the countdown continues after switching to the background and back; whether the old code still works after resend; how the button and countdown behave after a request timeout on a weak network.
- Verification code: which branch each of these takes: number already registered (go to login), number already deleted, number within the account-deletion cooling-off period; and when the number is recycled and the previous owner set a two-step factor.
- Two-step verification: forgetting the factor while the recovery email is "pending confirmation"; another device just changed the factor, and whether the logged-in session on this device expires.
- Multi-device: adding another when the device count has hit the limit; how a new device is confirmed when no other device is online; where an in-flight message goes when the current device is removed by another device.
- Multi-device: when a removed device is offline, when it actually becomes invalid; another device already handled the same login confirmation or notification; the prompt and re-link entry after a linked device is automatically disconnected for being idle; the prompt on the old device after a successful re-registration on a new phone; whether all linked devices go offline when the primary device re-registers on a new phone (recommended: all go offline), and this knock-on rule must appear in a ruling question or "Defaulted to recommendation", not buried only in the card.
- Multi-device: whether notifications are deduplicated between linked devices and whether @me is an exception (see NOTI-27); whether the confirmation copy for irreversible operations synced to all devices (clearing chat history, deleting a chat) states that all devices are affected; whether the permission and time limit for unsending one's own message on a linked device match the primary device; the prompt copy on linked devices when the account is banned or deleted (write out the copy, not "per existing rules", unless the source of truth already has it and the source is cited). The must-asks of a multi-device requirement are usually three: coexistence policy and limit (ACC-23), encrypted chats on linked devices (ACC-30, when encrypted chats exist), and history storage and the history scope for a new device (MISC-20, with MISC-21 attached depending on its value, merged into one question); draft sync across devices (MISC-32) is default-OK and listed under "Defaulted to recommendation".
- Account deletion: what happens on login during the cooling-off period; what the other party's chat and group member list show after deletion, and for the handling of the person's own sent content on others' side see PRIV-17; handling when the deleting user is a group owner or has unfinished items; wallet balance, unfinished payments, points and remaining membership period are merged into one question, see WAL-18; invitation rewards within the lock period are decided together with INV-18, not a separate question. The must-asks of an account-deletion requirement are usually four: deletion method (ACC-21), the person's own sent content on others' side (PRIV-17), asset handling (WAL-18), deleting user is a group owner (GRP-28).
- Number change: new number already registered; old number receiving a verification code again; whether contacts are notified.
- Restricted account: graying out and tap prompts at each entry during the restriction (see ENF-03); status while an appeal is in progress (see ENF-11).

## Anti-patterns
| Vague/wrong | Correct | Reason |
|---|---|---|
| "Show an error when the verification code is wrong" | State whether wrong, expired, too many wrong entries and too many requests are prompted separately and the copy for each, with retry timing for the count-based ones | The four exceptions call for different user actions; if unwritten they get merged into one |
| "Support multi-device login" | State the device type combinations, count limit, over-limit prompt and replacement rule | An unwritten limit leaves engineering to decide |
| "Forgot password can be reset" | Split into with and without a recovery channel, and state the waiting period length and whether it can be canceled | The no-recovery-channel path is the branch most often missed |
| "Data is deleted after account deletion" | State the cooling-off period, login behavior during it, what the other party sees, and handling of group-owner status | Irreversible operations must state an undo window |
| "Redirect to the login page when logged out" | State the reason prompt for being logged out and where unsent messages go | Users need to know they were removed by another device |
| "The account stays the same after a number change" | State new-number verification, when the old number is released, and whether contacts are notified | A number change involves the state of two numbers |

## Calibration sample
The feature most easily written vaguely: the "Resend" button on the verification code page. After a tap there are only two pre-checks, "has the request count reached the cap" and "is there a network", so no decision chain. This page has no must-ask item: cooldown length, daily cap, old-code invalidation and the like are all written as body text per recommendation; the numbers on the card are illustrative, actual values are set by business, and each is listed one by one under "Defaulted to recommendation" in the delivery draft.

Description:
1. During the cooldown the "Resend" button is grayed out and not tappable, with copy "Resend in {seconds}s"; when the cooldown ends the copy returns to "Resend" and the button lights up
2. On tapping "Resend", when the current number has reached 5 requests today: dialog: "You have reached today's limit for verification codes. Please try again tomorrow", the button is grayed out until 00:00 the next day, and the input box stays usable
3. Under the cap but offline: toast: "Network unavailable. Check your connection and try again", the button stays lit, and this attempt is not counted toward the request count
4. Under the cap and online: the button shows a loading state and cannot be tapped again; after a successful send, toast: "Verification code sent", the previously issued code is invalidated immediately, and the button is grayed out and enters a new 60-second cooldown
5. On request timeout: toast: "Failed to send. Please try again", the button lights up again, no cooldown starts, and this attempt is not counted toward the request count
6. Switching to the background during the cooldown and returning to this page: the countdown continues by actual elapsed time; if the full cooldown has passed, the button lights up directly
