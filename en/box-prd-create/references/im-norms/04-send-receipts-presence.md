# Message Sending, Receipts and Presence

> Applies to: PRDs involving sending messages, send states, failure retry, offline sending, send results after being blocked or removed, scheduled/silent sending, read receipts, typing indicators, online status. Evidence: see evidence/04-send-receipts-presence.md.

## Baseline (follow by default, high confidence)
- **[SEND-01] Minimum set of core message types**: Text, image, video, file and voice are the five required types; location, contact card, sticker, poll, short video, etc. are added as needed. Must define: size/duration/length limit per type, whether each is controlled by its own group permission switch, placeholder copy when the peer's version does not support the type. | Magnitude: N/A | Confidence: High
- **[SEND-03] Failed messages are kept and marked**: A message that fails to send stays in place in the chat with a failure indicator and does not silently disappear. Must define: failure reason categories (no network, recipient rejected, no permission, rate limit, content too large, server error) and the copy for each; server-side rejections (banned, resource limit exceeded, terms must be accepted first) are presented separately from network problems (see UX-16); whether failure is a terminal state. | Magnitude: N/A | Confidence: High
- **[SEND-04] Resend and delete for failed messages**: The failed message itself offers a resend entry; tapping it either asks for confirmation or resends directly. Must define: whether a failed message can be deleted (local only) and whether deletion needs a second confirmation, whether multiple failed messages can be resent all at once or deleted all at once, how a single failure and multiple failures are resent, where the message sits after resending, the prompt when resending fails again. | Magnitude: N/A | Confidence: High
- **[SEND-06] Block sending without permission and state the reason**: When the user has left the group, been removed, banned or muted, sending is blocked (input bar unavailable or send rejected) and reason copy is shown; history stays readable. Must define: copy for each reason, the form of the restricted input bar (see UI-D7), where an existing draft goes. | Magnitude: N/A | Confidence: High
- **[SEND-07] Typing indicator in one-on-one chat**: In one-on-one chat, "typing" is shown while the other party is typing. Must define: refresh and expiry mechanism (whether the sender refreshes on a timer and the receiver expires it automatically on timeout, without relying on a "stop" signal), trigger condition (input changes), sender refresh interval, receiver expiry duration, stop conditions (sent/cleared/focus lost/timeout), restart condition, whether it still shows when the receiver is not in that chat or not online, whether it is constrained by the online-status visibility setting (one product is not constrained). | Magnitude: refresh interval several seconds to ten-plus seconds, receiver expiry several seconds to thirty seconds | Confidence: High

## Conventions (default-OK, mark as suggested)

- **[SEND-02] Text length limit and over-limit result**: A single text message has a limit; when exceeded, the user gets a clear result and is not misled into thinking it was sent in full. Must define: how the limit is measured (characters or bytes), whether the caption limit for media with a caption is smaller than the body limit (magnitude: about a thousand characters), the hint in the input box when over the limit and the number of characters that must be removed, whether over-limit content is saved as a draft. | Magnitude: several thousand to tens of thousands of characters | Confidence: Medium (two products block sending with direct evidence, one product truncates directly when the total limit is exceeded)
- **[SEND-05] No silent loss when offline**: When sending without network, the message either queues in a "sending/paused" state, or is explicitly turned into failed or cancelled and the user is told; it must not be neither sent nor reported. Must define: the time limit or condition for moving from queued to failed and the behavior after the network recovers (see SEND-10), the copy for the number of cancelled messages. | Magnitude: N/A | Confidence: Medium (three products with direct evidence, but queueing and cancelling coexist)
- **[SEND-16] Read receipt switch is reciprocal**: (The reciprocity rule is privacy-related, treat as must-ask: list it under "Decisions for Box" in the delivery draft, recommend reciprocal) When a read receipt switch is offered, design it as two-way reciprocal: once off, you neither send nor see others'. Must define: whether the switch defaults to on or off (privacy default, treat as must-ask); whether one-way visibility is offered (some products let users pay to see others' receipts without exposing their own, and the protocol layer also has private receipts visible only to oneself) — this is a ZYMIX trade-off; before Box rules, write the card as reciprocal and mark it `Suggested`; the highest state visible to the user once off; whether the delivered state is turned off with the switch; whether group receipts and voice "played" receipts are controlled by the switch; whether the switch syncs across devices; switch location and explanatory copy. For the switch form (how many switches, whether per-chat override is allowed) see SEND-22. | Magnitude: N/A | Confidence: Medium (two products with direct reciprocal evidence, one product's paid tier is a counterexample)
- **[SEND-21] Separate receive states for voice and one-time media**: The receive state of voice and view-once media is expressed separately from "read": seen but not played, and played (or viewed), are different states, and the sender can tell them apart. Must define: state names, whether they are controlled by the read receipt switch, whether group chats aggregate by count or show per person, whether playing on one device syncs to the others in multi-device. | Magnitude: N/A | Confidence: Medium (three products with direct evidence, one of which only yielded group statistics)

## Divergences (ask Box on must-ask; write default-OK per recommendation and list it)
- **[SEND-08] Handling of over-long text**: Option A: block sending and prompt that the length is exceeded (two products) / Option B: automatically convert to a long-text attachment, with only the first short segment in the body (one product) / Option C: truncate directly at the total limit (not recommended, users do not notice lost text; the same product as B behaves this way at the total limit). Recommended: A. Rationale: user understanding (what you send is what you get) and no attachment parsing cost. | Level: Default-OK
- **[SEND-09] Receipt levels and semantics**: Option A: two-level terminal states, sending/sent/read, no "delivered" (one product; the specification layer also only defines read receipts) / Option B: four levels, sending/sent/delivered/read, with delivered defined as reaching any one device of the recipient, and voice additionally has played (two mainstream products; verified to be uniquely definable under multi-device accounts) / Option C: one-on-one chat offers no read state, only send success and failure (one product, inference only, medium confidence). Recommended: B. Rationale: user understanding (can tell "the other party has not received" from "the other party has not read"), and the "any device" definition has precedent; privacy is covered by SEND-16. Must define: states only move forward and never back, delivered can be skipped to go straight to read, "delivered" does not appear when the recipient's device is off and nothing has reached any device, the other party may not send a read receipt on first receipt. | Level: Must-ask
- **[SEND-10] Offline send lifetime and automatic retry**: Option A: queue in local storage, resend automatically when online, turn into failed after the lifetime is exceeded (about one day), showing "sending paused" in the meantime (privacy-first products) / Option B: cancel if it still cannot be sent after the network returns and prompt the number of unsent messages (mainstream domestic products) / Option C: keep showing a pending indicator (clock type), resend after the network returns, no explicit lifetime (two products, expiry policy not evidenced). Recommended: A. Rationale: recoverable, users do not lose messages, and the lifetime cap avoids staying "sending" forever. Whichever is chosen, order within the same chat must stay first-sent-first-delivered. | Level: Default-OK
- **[SEND-11] Message ordering basis**: Option A: server confirmation time is authoritative, pending messages are temporarily placed at the end by local send time / Option B: local send time throughout / Option C: by the chat sequence number assigned by the server, timestamps for display only. Recommended: A. Rationale: consistent across devices and pending messages do not get out of order (insufficient evidence: only "pending messages are sent in ascending local number order" was obtained; the ordering basis was not directly evidenced this round). | Level: Default-OK
- **[SEND-12] Send result for the blocked party**: See REL-22 (what the sender sees is defined only there).
- **[SEND-13] Sending by non-friends/strangers**: See REL-21 (whether strangers can send directly and whether they go to message requests first is defined only there); for the reason prompt the sender sees when intercepted see REL-12, for sending restrictions before a reply is received see REL-05.
- **[SEND-14] Scheduled sending**: Option A: not offered / Option B: offer single-shot scheduling with a date and time, a cap on the number of messages (magnitude: tens to a hundred), send immediately if too close to the current time, with reschedule and cancel-all / Option C: B plus "send when the other party comes online" and repeat cycles. Recommended: B. Rationale: recoverable and bounded scope (only one source was fully evidenced). Must define: the result when permission has been revoked at trigger time. | Level: Default-OK
- **[SEND-15] Silent sending**: Option A: not offered / Option B: "no sound" can be selected when sending, and the receiver only gets a silent notification. Recommended: A. Rationale: single source only, and it easily conflicts with the mute rules in module 08; add it when there is demand. | Level: Default-OK
- **[SEND-17] Group read details**: Option A: not offered / Option B: aggregate counts only (read count, voice listened count, video watched count) / Option C: per-member list grouped by sent/delivered/read/not sent with times, with the overall state aggregated over "everyone" (delivered is shown only when all have received, read only when all have read, or an extra "partially sent" overall state) (two products). Recommended: B. Rationale: low privacy cost; the member-count threshold is ruled by ZYMIX group size (aggregate only for large groups, lists only for small groups, threshold not evidenced). Must define: whether a member's receipt is still kept in the details after they leave the group, whether group receipts are controlled by the SEND-16 switch. | Level: Must-ask
- **[SEND-18] Typing activity types and display in groups**: Option A: only "typing" (three products) / Option B: add activity types such as recording, uploading, choosing a sticker (two products, one of which only has a speaking state). Display in groups: Option a: not shown / Option b: show one person's name, aggregating multiple people as "{name} and {n} others are typing". Recommended: A + b. Rationale: user understanding and the smallest scope (the "one/two/several people" group copy has corroboration from protocol clients, but on the product side only one product was evidenced). | Level: Default-OK
- **[SEND-19] Online/last seen**: Option A: not offered (one product, reverse inference; another not evidenced) / Option B: offered, showing the exact time when the other party allows it and only a fuzzy tier (recently, within a week, within a month, long ago) when not, with reciprocal sharing: if you do not share, you cannot see the other party's exact value (two mainstream products offer online/last seen constrained by privacy settings, and for one of them "online" only means the app is open and connected, not that a message has been read) / Option C: offered with exact online status and a user-set status (another mainstream domestic product, precision not evidenced). Recommended: B. Rationale: privacy reciprocity while keeping the activity signal. Must define: the semantics of "online" (app open and connected, not equal to read), the day boundaries of the fuzzy tiers (magnitude: several days, one week, one month), for the last seen shown to a blocked user see REL-08, temporary online exposure when sending/reading/typing to the other party (magnitude: tens of seconds). | Level: Must-ask
- **[SEND-20] Other party has deleted their account**: Option A: handle the same as blocked (blocked-party behavior see REL-22) / Option B: explicitly prompt "this account has been deleted", with the chat kept read-only / Option C: messages show as sent but are never delivered. Recommended: B. Rationale: user understanding (no evidence, hint only; none of the five sources this round yielded send behavior for this state). | Level: Default-OK
- **[SEND-22] Switch form for read receipts and typing status**: Option A: only a read receipt switch, typing status has no switch and is always sent (two products) / Option B: separate switches for read receipts and typing status, once off you neither send nor see others', switches sync across devices (one product) / Option C: one global switch controlling both read receipts and typing status (no product observed). Another option: on the chosen form, allow per-chat override of the global switch (no product observed). Recommended: B. Rationale: privacy-controllable and consistent with the SEND-16 reciprocity principle; for the smallest scope in the first release A is acceptable. Must define: switch location and explanatory copy, whether turning off affects aggregated display in groups, whether group chats and voice play receipts are exceptions. | Level: Must-ask

## Must-ask states (module-specific, supplements the general state matrix)
- The other party has blocked me/removed me: blocked mid-send, the result of in-flight messages and whether receipts of existing "sent" messages are kept
- The other party has deleted their account: send result, receipts of sent messages, chat header display
- I have left the group/been removed/been muted: input bar state, draft retention, result of in-flight messages, result when a scheduled message triggers
- Non-friend, message request not accepted: whether receipts are sent, whether typing is sent
- Multi-device: how the local state syncs when another device has read/sent/unsent; whether receipt and typing switches sync across devices; display when typing on multiple devices at once
- Offline recipient: distinguishing sent from delivered; whether the sender is notified after the server retention period (magnitude: tens of days) expires
- Weak network: timeout from sending to failed; recovery after switching to background or the app being killed by the system during upload
- A message fails or is unsent after it has already been forwarded, quoted or reacted to: how quoted/forwarded content is displayed
- Group vs one-on-one differences: overall state when sending fails for some group members; group receipt aggregation basis; aggregation of typing in groups
- Peer version does not support the type: placeholder copy and upgrade guidance
- The other party restricts receiving certain message types (voice, non-contact messages): copy when sending is rejected and whether it can be resent
- Rate limit/throttling triggered: prompt copy, cooldown duration, whether it counts as failure
- Empty and whitespace-only messages: send button state and prompt
- After the other party turns receipts off: the highest state visible to me
- Reasons other than the switch for not seeing a read mark (other party has not opened the chat, blocked, connection problem, first receipt): whether to explain to the user, or only show the highest state reached
- Voice: distinguishing seen-but-not-played from played, multi-device play sync, whether the "played" receipt is still sent after the receipt switch is turned off

## Anti-patterns
| Vague/incorrect | Correct | Reason |
|---|---|---|
| "Failed sends can be retried" | State the resend entry location, message position after resend, prompt on repeated failure, whether it can be deleted | Developers cannot implement it uniquely |
| "Read/unread" two states | State each state's semantics, whether levels can be skipped, terminal states and whether they change with the switch | Receipts are a state machine, not two labels |
| "Turn off read receipts" written for only the user's own side | State two-way reciprocity, and whether group chats, voice playback and delivered state change with the switch | One-way turn-off or unclear exceptions create a gap in privacy expectations |
| "Retry automatically on a poor network" | State queue lifetime, paused-state copy, the condition for timing out into failed, ordering guarantee | Without a lifetime it stays sending forever |
| "Sending fails when blocked" | Settle the REL-22 ruling first, then state what the sender sees and whether it reveals the block | Directly affects privacy |
| "The other party is typing" without stop conditions | Write it in four parts: trigger/refresh/stop/restart, with stop including sent, cleared, focus lost, timeout | Otherwise the indicator may show forever |
| "Show last seen time" | State the fuzzy tiers when the other party does not share, the fixed tier for blocked users, temporary exposure after sending a message | Precision and reciprocity are the core of privacy |
| "Show read in groups" | State aggregate count or list, member-count threshold, whether members who left are counted | The group receipt basis is not unique |
| When there is no permission, only "cannot send" | Give copy per reason, and state whether the input bar is greyed out or reports an error on tap | Users do not know why |

## Calibration sample
Easiest to write vaguely: tapping a failed message in a group chat to resend. This sample has no must-ask items: offline queue lifetime, position after resend, and deleting failed messages are all written as body text per recommendation; the values in the card are illustrative, actual values are set by the business and listed one by one under "Defaulted to recommendation" in the delivery draft.

Description:
1. After a message fails to send, it stays in place in the chat, with a failure indicator next to it
2. On tapping the failure indicator, check in order:
   a. 1-Membership check: is the current account still in this group chat
      i. Left or removed: Dialog: "You are no longer a member of this group and cannot send messages", the message stays failed
      i. Still in the group chat: go to the next check
   a. 2-Mute check: is the current account muted in this group
      i. Muted: Toast: "You have been muted and cannot send", the message stays failed
      i. Not muted: go to the next check
   a. 3-Network check: is there network now
      i. No network: the message state changes to "Sending paused" and is queued, and is resent automatically when the network recovers; if still unsent after 24 hours in the queue it returns to the failed state
      i. Network available: go to the next step
3. After passing all checks, the message moves to the end of the chat and its state changes to "Sending" and it is resent; after a successful send the state becomes "Sent", and on another failure it returns to the failed state, Toast: "Failed to send. Please try again later"
4. Long-press a failed message to choose "Delete", Dialog: "This cannot be undone, and the other party will not receive this message", buttons "Cancel" and "Delete"; deletion affects only this device
5. When there are multiple failed messages in the chat they are resent one by one, and "resend all" is not offered
