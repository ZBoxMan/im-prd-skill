# Support and tickets: generic feedback and appeal state machine (entry, states, supplementary materials, time limits, results and satisfaction, human and bot support)

> Applies: read this file when the PRD involves the help and contact support entry, submitting feedback, the "My Feedback" list and ticket detail, ticket states and transitions, requests for supplementary materials, confirmation and reopening after resolved, processing-time commitments, result notification, satisfaction rating, bot support handoff to a human, or handler identity display. This module defines one generic ticket state machine, reused by reports (SAFE-12), penalty appeals (ENF-10 to ENF-13) and wallet transaction disputes (WAL-07); each type's entry, eligibility, count and result disclosure still belong to the original module. For the report form see SAFE-09; for penalties and appeals see module 22; for the wallet dispute entry see WAL-07; for the platform system chat see BOT-09; for bot and AI identity labeling see BOT-03, AI-03; for rate limit prompts see SAFE-13. Legal response periods for privacy requests and penalty reviews are always written "per launch-region compliance requirements", and this file gives no values. Evidence is in evidence/26-support-tickets.md.

## Baseline (follow by default, high confidence)
- **[SUP-01] Help and contact support entry in the app**: The app has a fixed help and contact support (feedback) entry. Must define: entry location and copy (for reference: placed in settings, direct evidence from two products); whether FAQs are shown before the contact entry (for reference: direct evidence from one product prompts viewing FAQs before contacting); the list of issue types and routing by type (whether privacy requests, accessibility, wallet and account security go through separate entries); where to start when unable to sign in (for reference: a web form, direct evidence from two products) and how the ticket is seen inside the account after signing in; for the scope of the ticket system see SUP-09. | Magnitude: N/A | Confidence: High
- **[SUP-02] Diagnostic logs and technical information are attached only after user confirmation**: When submitting feedback or on an error, attaching diagnostic logs and device and technical information requires first informing the user and getting confirmation (a dialog prompt, a checkbox or a statement before submitting), with no silent upload. Must define: the list of attached content and a statement of whether chat content is included (for reference: direct evidence from one product states conversation content is not leaked); whether attaching is checked by default (a privacy default, treat as must-ask); the log retention period; whether encrypted chat content could enter the logs and how it is excluded. | Magnitude: N/A | Confidence: High

## Conventions (default-OK, mark as suggested)
- **[SUP-04] State changes and results are actively notified**: When a ticket enters needs more info, resolved or closed, the user is notified proactively, tapping goes to the ticket detail, and the detail state updates in sync. Must define: the notification vehicle (for reference: send a reviewable notification in the platform system chat and push it; the vehicle has direct evidence from only one product and another product uses push, so it is moved into must define); which state changes send a notification (whether acceptance also notifies); notification copy; compensation after push is turned off or the system chat is deleted (the next time "My Feedback" is opened it shows an unread mark); for the system chat form see BOT-09; for the notification vehicle of penalty appeals see ENF-13; for report feedback copy see SAFE-12. | Magnitude: N/A | Confidence: Medium (proactive notification of state changes has direct evidence from two products)
- **[SUP-05] Tickets are started from the disputed object and carry the object automatically**: When there is a question about a specific object, the ticket is started from where the object is (transaction detail, penalty notice, message or profile page, call-ended page), automatically carrying the object identifier, so the user does not have to type a number by hand. Must define: the start entry for each object type; the fields carried and whether they are visible to the user; whether a ticket can be started when the object is deleted, unsent or expired. For wallet transactions see WAL-07, for penalty appeals see ENF-02, for report objects see SAFE-11. | Magnitude: N/A | Confidence: Medium (direct evidence from two products)
- **[SUP-06] Prompt that support never asks for verification codes or passwords**: See SAFE-15 (anti-impersonation prompts at the support entry, at the top of the support chat and on the submit page follow this entry too).
- **[SUP-07] Identity label of bot support**: See BOT-03 (a type label distinguishable from human accounts; for the label of AI-generated replies see AI-03, for the auto-reply label and the "transfer to human" entry itself see BOT-29). This module only governs the trigger and continuation of handoff to a human (SUP-15) and handler identity display (SUP-16).
- **[SUP-08] Type rules for reports and penalty appeals**: See SAFE-09 (report form; for feedback copy see SAFE-12); for the appealable scope, form, count, time commitment and notification vehicle of penalty appeals see ENF-09 to ENF-13. Both reuse the SUP-10 state machine.

## Divergences (ask Box on must-ask; write default-OK per recommendation and list it)
- **[SUP-03] Whether a new ticket can be submitted when the same object already has an open ticket**: Option A: when the same object (same transaction, same penalty, same reported object) already has an open ticket, do not create a new one, prompt and guide to the original ticket to add to it or view progress, and later additions count toward the original ticket / Option B: allow submitting again, merged on the handler's side. Recommended: A. Rationale: avoids duplicate tickets and duplicate handling, and the user sees progress in one place; one known product has direct evidence (the same transaction is not accepted twice), and another only says bypassing the process will not speed up handling, which is not the same thing. Must define: the basis for identifying the object (transaction number, penalty record, reported account or message); whether general feedback not bound to an object is also limited in repeat submission, and its rate limit prompt (wording see SAFE-13); with multi-device simultaneous submission, the one the server accepts first prevails. | Level: Default-OK
- **[SUP-09] Scope of the ticket system**: Option A: a unified ticket system: general feedback, reports, penalty appeals and wallet transaction disputes share the SUP-10 state machine and the same "My Feedback" list, entries stay at each object, and time limits, notifications and counts are configured per type / Option B: only general feedback and wallet disputes use tickets, reports and penalty appeals stay independent and are not in the list / Option C: no tickets, general feedback is answered in a support chat, and reports, appeals and disputes stay independent. Recommended: A. Rationale: users see the state of everything pending in one place, and the rules for supplementing and reopening are defined once; opposite to what existing products do (known products route by disputed object, and each flow's states, time limits and notifications are independent with no unified list), a user-comprehension-first trade-off. | Level: Must-ask | Framing: yes
- **[SUP-10] Generic ticket state machine**: Option A: five states plus reopen: Submitted (accepted by the server, not yet being handled), In progress (a handler is assigned or it has entered review), Needs more info (waiting for the user to supply materials, see SUP-11), Resolved (the handler has given a result, awaiting user confirmation or expiry, see SUP-12), Closed (end state, no longer accepts additions); Resolved can be reopened within the period back to In progress / Option B: three states, Submitted, In progress, Answered; answering ends it, and a new problem is submitted separately / Option C: show no state, only notify when the result is out. Recommended: A. Rationale: users understand who the ticket is waiting on, and supplementing and reopening have clear destinations; the only complete end-user sample known has three states plus "continue complaint" returning to the start, and A splits out Needs more info and the end state on top of it. Each type may keep its own naming but must map to these five states: for penalty appeals, Under review is In progress, Approved and Rejected are the two results of Resolved, and Expired is Closed; for wallet disputes, Answered is Resolved; reports use only the three states Submitted, In progress and Closed, and whether the result is told to the reporter follows SAFE-12. User withdrawal: Submitted and In progress can be withdrawn, and withdrawal means Closed. For the time limit basis see SUP-13, for notification see SUP-04. | Level: Default-OK
- **[SUP-11] Needs more info**: Option A: the handler starts Needs more info and states what to add, notified via the platform system chat; the user adds text and images in the ticket detail and after submitting returns to In progress; a waiting period is set, and on expiry it turns Closed automatically with a notice that it can be resubmitted; the processing time clock pauses during Needs more info / Option B: no such state, the user can add messages at any time, the handler replies at any time, and the state does not change / Option C: no supplementing is supported, insufficient materials get a result and a request to resubmit. Recommended: A. Rationale: users know the process is waiting on them and what to add; one known product uses a "user message awaiting reply" mark, close to B. Types and count caps of supplementary materials (screenshots, files; logs per SUP-02) and the waiting period are set by the business. | Level: Default-OK
- **[SUP-12] Closure and reopening after resolved**: Option A: on Resolved the user can tap "Resolved" to close directly, or within the period tap "Not resolved yet" and fill in a reason to reopen once, returning to In progress; with no action on expiry it turns Closed automatically; once the reopen count is used up or after Closed only a new ticket can be created, and the new ticket automatically links to the original / Option B: closed once a result is given, no reopening, objections require a new ticket / Option C: unlimited reopens, with the reopen count recorded for the handler's reference. Recommended: A. Rationale: a misjudgment or an off-topic answer still gets one remedy without being hammered repeatedly; the only complete known sample has unlimited "continue complaint" returning to pending and defaults to resolved with no feedback, close to C plus automatic closure. For the re-appeal count of penalty appeals see ENF-11. | Level: Default-OK
- **[SUP-13] Basis for writing processing-time commitments into a card**: Option A: commit per ticket type, written "usually answered within {N} working days", stating the start point (server acceptance time), working days by the account's time zone (see UX-36) and which calendar, and pausing the clock during Needs more info; when a commitment is exceeded without an answer the state shows still processing, and the ticket does not close automatically / Option B: no duration commitment, only "we will notify you after handling" / Option C: commit to a fixed duration, with automatic escalation or compensation on timeout. Recommended: A, with reports not committing per SAFE-12 and whether penalty appeals commit per ENF-12. Rationale: users understand the current state, with fewer duplicate submissions and chasers; known commitments are concentrated in disputes with a clear object, penalty reviews and privacy requests, while general inquiries mostly commit nothing or give only a range (magnitude: one to several working days, from one day to half a month for disputes and reviews). Duration values depend on support and review operations capability and are a source-of-truth gap, write {TBC} into Open items; the legal response period for privacy requests is per launch-region compliance requirements. | Level: Default-OK
- **[SUP-14] Satisfaction rating**: Option A: invite one rating when a ticket turns Resolved, merged into one step with SUP-12's "Resolved" / "Not resolved yet", with optional stars and a note, skippable, not affecting state transitions; reports and penalty appeals do not invite a rating / Option B: only ask at the bottom of help articles whether the problem was solved, tickets are not rated / Option C: no rating. Recommended: A. Rationale: merging rating with confirmation adds no extra interruption, and service quality becomes measurable; opposite to what existing products do (known products only ask whether the problem was solved at the help article level, and there is no sample of ticket-level rating), a measurable-service-quality trade-off; the results of reports and appeals are not decided by satisfaction, and inviting a rating is easily understood as able to influence the result. | Level: Default-OK
- **[SUP-15] Trigger and continuation of bot support handoff to a human**: Option A: for the form of the handoff entry see BOT-29; after two consecutive unrecognized turns, or when the issue is account theft, funds or penalties, a handoff to a human is offered proactively; on handoff the existing conversation and issue type are carried over so the user need not repeat themselves; when no human is in service hours or the queue times out it converts to a message ticket, enters the SUP-10 state machine, and the reply is notified via the platform system chat / Option B: the handoff only appears after a multi-turn conversation with the bot / Option C: no live human, tickets can only be submitted. Recommended: A. Rationale: users can always reach a person, and sensitive issues are not blocked by the bot; one platform policy requires automated replies to provide a direct path to a human. Whether queue position and estimated wait are shown, and human service hours, are set by operations. | Level: Default-OK
- **[SUP-16] Whether to disclose the handler's identity to users**: Option A: show only the category "Human support" / "Smart support", with no personal information / Option B: category plus agent ID or alias, with no real name or photo / Option C: category plus real name. Recommended: B. Rationale: users can name the specific handler in ratings, reopening and complaints without exposing employee personal information; all three options distinguish human from machine (see AI-03); no product has direct evidence, so this is inference. Level rationale: the handler is an employee, the agent ID or alias is employee information rather than the user's privacy default, does not change the main flow, and involves neither funds nor irreversible handling, so it is Default-OK. Also: whether a ticket result is produced automatically by the system and whether the user is told: for penalty appeals see ENF-08; other tickets follow the basis of ENF-08's recommendation B, with the result notification stating whether the system judged it automatically. | Level: Default-OK

## Must-ask states (module-specific, supplementing the general state matrix)
- Multi-device: when one device submits or supplements, when the other devices' lists and details refresh; which one prevails when two devices supplement materials or tap "Not resolved yet" at the same time.
- Offline and weak network: network lost while submitting or supplementing, whether entered content and selected images are kept; attachment upload failure, partial success, exceeding the count or size cap; offline at a state change, what is seen first after coming online.
- Object changes: the object is deleted, unsent, the transaction refunded, the penalty expired and lifted automatically, or the reported account deleted while a ticket is in progress; the object no longer exists when the handler gives the result.
- Account changes: account deleted while a ticket is in progress (unsettled wallet disputes blocking account deletion see WAL-18); whether a banned account can view and supplement existing tickets (appeal entry during a ban see ENF-02); how a ticket submitted on the web while unable to sign in is attached to the account after sign-in; historical tickets after changing the bound phone number.
- Period boundaries: the cutoff moments for the Needs more info waiting period, reopen period and automatic closing follow server time; the user is submitting a supplement at the cutoff instant; holidays within a committed duration.
- Handoff to a human: leaving the chat or going to the background while queueing; network lost during the handoff; the user keeps messaging after the human ends the chat; the user follows up in the bot chat after converting to a message outside service hours.
- Ticket records: how long closed tickets stay in the list; whether users can delete ticket records and whether the handler side keeps them after deletion (treat as must-ask); retention period of IDs and screenshots in tickets.
- Regional differences: legal response periods for privacy requests and penalty reviews and whether a human must be involved, per launch-region compliance requirements.

## Anti-patterns
| Vague/wrong | Correct | Reason |
|---|---|---|
| Draw only a "Submit feedback" button with nothing after submitting | Write the state after acceptance, where to check progress, how the result is notified, and the destinations for Needs more info and reopening | A ticket is a stateful flow, and missing branches make it impossible to implement |
| List states by name only | First describe each state's meaning in one line each, then write the conditions for entering and leaving | Resolved vs Closed and In progress vs Needs more info are most easily mixed up |
| Commit to "handled within 24 hours" without a start point or timeout behavior | Write the start point, working day basis, whether the clock pauses during Needs more info, and the state display after timeout | The commitment cannot be accepted, and after timeout users only see a broken promise |
| On Needs more info, send just one message and leave the ticket state unchanged | The state turns Needs more info, stating what to add, how long the period is, and where it goes on expiry | Users do not know the process is waiting on them, and tickets hang for a long time |
| Cannot express disagreement after resolved | Provide "Not resolved yet" and a reopen count, and after it is used up provide a new-ticket entry linked to the original | Users can only create new tickets repeatedly, and the handler cannot see the history |
| No human can be found in the bot chat | Provide the handoff entry per BOT-29, hand off proactively for sensitive types, and carry the existing conversation on handoff | The bot blocks urgent matters such as account theft and funds |
| Bot replies look the same as human replies | Label per BOT-03 and AI-03, and decide handler identity display per SUP-16 | Users cannot tell whether an answer was confirmed by a human |
| Logs are uploaded silently by default | Have the user confirm before attaching, stating the content list and whether chat content is included | Logs may contain personal information, and silent upload violates informed notice |
| Invite a rating after a report or appeal ends | Reports and appeals do not invite a satisfaction rating | Users will think a score can change the handling result |

## Calibration sample
The feature most easily written too vaguely: the "My Feedback" ticket detail page and state transitions. All user actions on the detail page depend only on "whether there is a network" and the current state returned by the server, so no decision chain is started. The ticket system scope was determined as the unified ticket system at framing; the state set, needs more info, closure and reopening after resolved, satisfaction, withdrawal, time limit basis and handler display are written as body text per recommendation, with card values illustrative and actual values set by the business; this example has no must-ask items; processing durations for each issue type depend on support operations capability and are written {TBC}.

Description:
1. Entry: in "Help & Feedback" on the "Settings" page tap "My Feedback"; the list is sorted by most recent update descending, each row shows issue type, submission time and current state; reports, penalty appeals and wallet disputes are also in this list, each started from its original object
2. States:
   Submitted: accepted by the server, not yet being handled
   In progress: support or review staff are handling it
   Needs more info: the handler has asked for supplementary materials and is waiting for your reply
   Resolved: the handler has given a result and is waiting for your confirmation
   Closed: the ticket has ended and can no longer be supplemented or reopened
3. Submission succeeds: enter the ticket detail with the state "Submitted", toast: "Feedback submitted. We usually reply within {TBC: committed response time per issue type}"
4. Time limit basis: the processing time counts from the server acceptance time, in working days, and the clock pauses during "Needs more info"; when the committed duration is exceeded without an answer, the state shows "This is taking longer than usual. We're still working on it" and the ticket does not close automatically
5. Needs more info: the platform system chat sends "Your feedback needs more information" and a push, tapping enters the ticket detail; the top of the detail shows what the handler needs added, and "Add materials" at the bottom accepts a note (up to 500 characters) and screenshots (up to 3); after submitting the state returns to "In progress"; if nothing is added within 7 days it turns "Closed" automatically, and the system chat sends "Your feedback was closed because no materials were added. You can submit it again"
6. Resolved: the platform system chat sends the handling result and a push; for general feedback and wallet disputes the detail page shows the result and two buttons "Resolved" / "Not resolved yet", with an optional 1 to 5 star rating and note below, and not rating does not affect the state; reports do not go through "Resolved" and turn "Closed" directly when handling ends; the result and re-appeal of penalty appeals are handled on the appeal detail page; neither reports nor penalty appeals show these two buttons or the rating
7. Tap "Resolved", or no action within 7 days: the state turns "Closed"
8. Tap "Not resolved yet": after filling in a reason (required, up to 500 characters) and submitting, the state returns to "In progress"; each ticket can be reopened 1 time, and after a reopened ticket is resolved again only "Resolved" is shown, with "Submit new feedback" at the bottom, and the new feedback automatically links to this ticket
9. Withdraw: in the "Submitted" and "In progress" states the detail page shows "Withdraw feedback" at the bottom, tapping it opens a dialog: "Handling will stop after withdrawing. Withdraw?", buttons "Withdraw" / "Cancel"; after withdrawing the state is "Closed"
10. Handler display: human-handled tickets show "Human support" and the agent ID, bot-handled ones show "Smart support", and no real name or photo is shown
11. No network when submitting supplementary materials, a reopen reason or a withdrawal: toast: "Network unavailable. Check your connection and try again", and the entered content is kept
12. Server returns that the state has changed (such as another device already supplemented or closed it): toast: "Feedback status updated", and the detail page refreshes
Note: processing time in item 3 awaits an answer from support operations
