# Media and Files

> Applies to: PRDs involving sending images/videos/files/voice, size and count limits, compression and original quality, metadata such as where an image was taken, auto-download, media expiry and cache cleanup, send progress and failed re-upload, file risk warnings. Evidence: see evidence/06-media-files.md.

## Baseline (follow by default, high confidence)
- **[MEDIA-01] Single-file size limit and over-limit prompt**: A single file has a size limit; when exceeded, it is intercepted with a prompt. Must define: the limit value and unit, whether images/videos/ordinary files have separate limits, whether over-limit is intercepted at selection or at sending, whether the prompt states the limit value, the copy. | Magnitude: ordinary files 100 MB to several GB, video sending target tens to a hundred MB | Confidence: High
- **[MEDIA-02] Compression by default, original/HD optional**: Images and videos are compressed by default before sending to save data, and the sender may choose original/HD. Must define: the default tier, the switch entry, whether the receiver can view or download the original and whether the entry shows the file size, whether the original expires over time, the data-usage prompt after choosing original, whether already-sent media can be upgraded afterwards (one product cannot). | Magnitude: N/A | Confidence: High
- **[MEDIA-03] Limit on how many can be selected at once**: A single send of images/attachments has a count limit. Must define: the limit value, handling and prompt when exceeded (block further adding at selection, keep the first N, or reject entirely), whether images and videos can be mixed, whether they are merged into an album or sent one by one. | Magnitude: about 10 to 100 items | Confidence: High
- **[MEDIA-04] Placeholder when media is unavailable**: When media is unavailable (the local cache was cleared or the server content has expired), tapping or opening gives a reason prompt, leaving no blank and no silent failure. Must define: whether the two reasons are prompted separately (cache cleared can be re-downloaded, server expiry cannot be recovered), the placeholder copy for each, the actions available on the placeholder (re-download, favorite, forward), whether thumbnail information is kept in the chat history after expiry, the placeholder for one-time content that expired unopened. | Magnitude: N/A | Confidence: High
- **[MEDIA-08] Voice recording gesture**: Hold to record, release to send; there must be a way to cancel during recording. Must define: whether desktop and web start and end by holding or by clicking, the cancel gesture direction and trigger distance (a keyboard key on desktop), the prompt after cancelling, the result when recording is interrupted by an incoming call, whether the recording draft is kept, whether lock-to-hands-free is supported (see MEDIA-18). | Magnitude: N/A | Confidence: High

## Conventions (default-OK, mark as suggested)

- **[MEDIA-06] Risk prompt for dangerous files**: For high-risk types such as executables, a risk prompt is shown before opening or saving. Must define: the list of risk types, the prompt timing (open, preview, save), whether it continues after confirmation, whether sending or opening is forbidden outright for some types, whether a separate prompt is shown when the preview may expose a network address. | Magnitude: N/A | Confidence: Medium (direct evidence from two products: one shows a risk prompt for executables, one marks dangerous or suspicious files; the latter also has a prohibited-file mark that may forbid outright, so "rather than a blanket ban" does not hold and has been moved into must define; a preview exposing a network address is another kind of risk with evidence from only one product, and is only in must define)
- **[MEDIA-05] Failed media/file sends can be resent**: After an upload is interrupted or fails, the failed message offers a resend entry and states whether the file must be selected again (it cannot be resent if the source file has been deleted). Must define: whether an interrupted upload resumes, the prompt when the source file does not exist, progress reset after resending. | Magnitude: N/A | Confidence: Medium (media-specific direct evidence from only two products, the rest is general failed-send resend)
- **[MEDIA-20] Compressed images sent by default carry no capture location or other metadata**: When an image is sent in the default (compressed) way, the sender re-encodes it and does not carry the original's capture location, capture device or other metadata. Must define: whether video is handled the same way when compressed by default; for handling when sending the original or sending as a file see MEDIA-19. | Magnitude: N/A | Confidence: Medium (direct evidence from the source code of two open-source clients)

## Divergences (ask Box on must-ask; write default-OK per recommendation and list it)
- **[MEDIA-07] Voice duration limit and behavior at the limit**: Option A: send automatically at the limit and prompt that recording can continue (one product, magnitude: about one minute) / Option B: stop automatically at the limit and enter pending-send or draft (one product, desktop magnitude: about one hour) / Option C: stop automatically at the limit and discard (not recommended). Recommended: A. Rationale: user understanding and no content lost (voice is a high-frequency IM entry, a limit on the order of one minute is controllable). Must define: when the remaining-time countdown prompt appears. | Level: Default-OK
- **[MEDIA-09] Voice to text**: Option A: not offered / Option B: long-press or swipe triggers transcription, a "no speech detected" prompt when there is no speech, higher quota for paying users (two products, one of which only yielded the settings page title, medium confidence). Recommended: A. Rationale: privacy (voice is uploaded for recognition) and the smallest scope; add it when there is demand. | Level: Default-OK
- **[MEDIA-10] Video messages (short video shot and sent on the spot)**: Option A: not offered / Option B: offer round/square short videos, with limited size and bitrate (magnitude: a dozen or so MB), can be set by the other party to not receive, can be disabled by group admins. Recommended: A. Rationale: single source, overlaps with image/video/voice, evaluate again later. | Level: Default-OK
- **[MEDIA-11] Auto-download policy**: Option A: users set size thresholds separately by media category (image/video/voice/file/animation) and chat type (one-on-one/group/channel) (one product) / Option B: fixed thresholds, small files are always downloaded, large files never, with values in between set by the user (one product, magnitude: below a hundred KB always downloaded, above several hundred MB not downloaded) / Option C: only one item supported, "auto-download content already viewed on other devices" (one mainstream domestic product) / Option D: tick images, voice, video and documents separately by network type (mobile data, Wi-Fi, roaming), no size thresholds, roaming warns of possibly high data charges, voice auto-downloads by default (one product). Recommended: D. Rationale: user understanding (what you tick is what you get) and covers the data-sensitive cellular scenario; the default ticked set under each network type needs a separate ruling from Box. | Level: Default-OK
- **[MEDIA-12] Server-side media retention period**: Option A: stored long-term in the cloud, can be re-downloaded after the local cache is cleared (one product) / Option B: limited retention period, expires when due (mainstream domestic products, retention period not officially published, third-party accounts say several days to tens of days) / Option C: the server only temporarily holds undelivered content and discards it after several weeks to tens of days, delivered content is no longer stored (privacy-first products; another product keeps encrypted media on the server for several weeks, evidenced only for the one-time content scenario). Recommended: B. Rationale: storage cost is controllable and fits the MEDIA-04 placeholder; if A is chosen, storage cost and cleanup after account deletion must be defined. Must define: whether the retention period is tiered by type (image, video, voice, file), whether a reminder is given before expiry. | Level: Must-ask
- **[MEDIA-13] Local cache cleanup policy**: Option A: manual cleanup only, showing usage by category and chat, with a prompt after cleanup that media can be re-downloaded / Option B: A + automatic cleanup: retention duration set by chat type, plus a maximum cache size, clearing the least recently used when exceeded / Option C: trim chat history by message count or duration, clearing media at the same time (privacy-first products, with confirmation). Recommended: B. Rationale: recoverable (media can be re-downloaded from the cloud); if C is chosen it must state that it is unrecoverable. Must define: low-disk-space warning tiers (magnitude: one to three tiers, three tiers in only one product). | Level: Default-OK
- **[MEDIA-14] Handling of oversized files**: Option A: reject outright above the limit and prompt the limit (three products) / Option B: automatically convert to a cloud share link above the limit, and the other party downloads through the link (one mainstream domestic product). Recommended: A. Rationale: user understanding and does not introduce link expiry or a second download flow. Must define: whether a daily sending quota exists, the prompt when the quota is used up. | Level: Default-OK
- **[MEDIA-15] Whether to tier by payment**: Option A: no tiers (privacy-first products, one mainstream domestic product, and another global mainstream product, the latter at medium confidence) / Option B: payment raises the single-file limit and transfer speed, the free tier is throttled with a prompt (one product, limit about double in magnitude) / Option C: payment raises the daily quota (another mainstream domestic product). Recommended: A. Rationale: ZYMIX's existing rules do not register tiers, so no new user stratification is added. When B or C is chosen, for existing content that exceeds the free limit after membership expires see PTS-25. | Level: Default-OK
- **[MEDIA-16] Handling of large videos**: Option A: the client compresses to a target size before sending, and a source video beyond the extreme limit is not transcoded and is prompted as unsupported (two products, magnitude: target tens to a hundred MB, smaller target and lower resolution when the network is slower, source extreme about 1 GB) / Option B: upload as is, with the server transcoding asynchronously, a placeholder "Video is being processed, this may take a few minutes" while transcoding, and forwarding is published after transcoding completes (one product). Recommended: A. Rationale: failures on a weak network are found early; B must state the result of transcoding failure. | Level: Default-OK
- **[MEDIA-17] Quality tiers and data-usage prompt**: Option A: choose whether to send original on each send (two products) / Option B: global setting "Standard/HD", with a prompt that HD uses more data (two products) / Option C: global default plus a one-time override at send time, a confirmation dialog when sending HD on cellular, already-sent items cannot be upgraded, HD does not apply to feed posts and avatars (one product, the union of A and B) / Option D: automatic selection by network type (not evidenced this round). Recommended: C. Rationale: user understanding (convenient by default, changeable per send), and covers both A and B approaches at once. | Level: Default-OK
- **[MEDIA-18] Recording lock for hands-free and pause-and-preview**: Option A: not offered, the user must keep holding during recording, and releasing sends or cancels / Option B: swipe up to lock for hands-free, can pause and preview, send when satisfied, or turn into a draft (two products). Recommended: B. Rationale: privacy and data integrity first, reducing accidental sends and loss of long recordings. Must define: lock entry and cancel method, where and how long the draft is kept after pausing, the result when a call interrupts during preview. | Level: Default-OK
- **[MEDIA-19] Capture location and other metadata when sending the original or sending an image as a file**: For default (compressed) sending see MEDIA-20; this entry covers only the original and file form. Option A: strip capture location and other metadata by default as well / Option B: prompt "includes capture location" before sending, and the sender chooses whether to strip / Option C: no handling, send as is. For the original switch see MEDIA-02, for sending a location message see RICH-01. Recommended: A. Rationale: privacy — capture location exposes home address and whereabouts, and the receiver does not need such information to view an image; background: only one product has direct evidence (an "includes capture location" prompt and a "strip capture location" entry when sending an image, default not evidenced); the other four products' handling of original and file form was not evidenced, which is not the same as counterexamples. | Level: Must-ask

## Must-ask states (module-specific, supplements the general state matrix)
- The other party has blocked/removed me: media blocked partway through upload, the send result and cleanup of the already uploaded file
- The other party has left the group/deleted their account: the state the sender sees when the other side can no longer download
- Cancelled while sending: location of the cancel entry, whether the already uploaded part is discarded, whether a failed bubble is left
- Multi-device: whether media already downloaded or viewed on another device is marked in sync locally; whether old media never downloaded on this device can be pulled from the cloud or other devices; failure prompt when other devices do not have the attachment
- Offline recipient: media retention period while the other party is offline; whether auto-download triggers after they come online
- Weak network: presentation and timeout of upload progress, whether resumable upload is supported, continued upload after switching to background
- Permission revoked midway: a group admin turns off the "send images/files/voice" permission during upload, the result of the in-flight message
- The other party restricts receiving certain message types (voice, video messages): rejection copy and whether another type can be used instead
- Message already forwarded/quoted: how forward and quote cards display after the original media expires
- Media expired or cleared: whether tapping the placeholder re-downloads or prompts expiry
- Voice: whether continuous playback (auto-play the next unheard voice after one finishes) is offered, whether the heard mark syncs across devices, earpiece/speaker switching, an incoming call or backgrounding during recording
- Album: one image in a multi-image set fails, whether the whole set is resent
- Size basis: display unit (MB/GB) and rounding rules
- One-time content: placeholder for expired-unopened, backups keep only unopened ones, already opened on another device
- Cellular and roaming: data-usage confirmation before sending HD or auto-downloading
- Sending an image or video as a file: whether capture location and other metadata are handled the same way (follows MEDIA-19)

## Anti-patterns
| Vague/incorrect | Correct | Reason |
|---|---|---|
| "File size is limited" | State the limit value, whether it is set separately by type, the intercept timing, over-limit copy | Without a number developers cannot implement it |
| "Supports sending originals" | State the default tier, switch entry, size display, whether the original expires | The original is separate state and storage |
| "Expired files cannot be downloaded" | Distinguish local cache cleared from server expiry, and write the placeholder and actions for each | The former is recoverable, the latter is not |
| "Select at most N images at once" | State whether over-limit truncates or rejects, whether mixing is allowed, whether merged into an album or sent one by one | The over-limit branch is not unique |
| "Voice is at most 60 seconds" | State whether it auto-sends or stops at the limit, the countdown prompt, the result of interruption, the cancel gesture | The behavior at the limit is a core branch |
| "Failed uploads can be retried" | State whether it resumes, what to do if the source file was deleted, progress reset on resend | Media resend has extra failure states |
| Auto-download written only as "download by network" | State the three dimensions category, chat type, size threshold, and the defaults | Missing one dimension means it cannot be implemented |
| "Hold to record and send" | State the cancel gesture and feedback, whether it can be locked for hands-free, the result of interruption, draft retention | Cancel and lock are core branches |
| File types written only as "forbid dangerous files" | State the risk type list and prompt timing, and distinguish prompting from forbidding | A blanket ban hurts normal files |

## Calibration sample
Easiest to write vaguely: selecting multiple images or videos in a chat to send. This sample has no must-ask items: count and size limits, mixed selection, over-limit intercept timing, album form, original entry and failed resend are all written as body text per recommendation; the values in the card are illustrative, actual values are set by the business and listed one by one under "Defaulted to recommendation" in the delivery draft.

Description:
1. In the album, images and videos can be selected together; once the selected count reaches 20, the remaining items cannot be selected, Toast: "You can select at most 20 at a time"
2. When a selected single file exceeds 1 GB, that item cannot be selected, Toast: "{filename} exceeds 1 GB and cannot be sent", and the other already selected items are unaffected
3. By default the bottom sends compressed images and videos, and after ticking "Original" the original files are sent; once at least one item is selected the "Send" button lights up
4. Tap "Send": multiple items are merged into one album message and sent, with upload progress shown for each item; with no network the whole message shows "Sending paused", and uploading continues automatically after the network recovers
5. When a single item fails to upload, that item shows a failure indicator, and tapping resends only that item; when the source file has been deleted, Toast: "File does not exist. Please select again"
