# User acquisition and invitations, external sharing

> Applies: read this file when a PRD involves inviting friends to register (invite links, invite codes, entering a code on the registration page), the conditions, anti-abuse, failure and revocation of invitation rewards (points, etc.), invitation records, inviting unregistered contacts (by SMS or sharing), and sharing invitations or content to external apps and web landing pages. Inviting into a group is in GRP-07, GRP-18; the personal QR code is in DISC-14; contacts upload and matching are in DISC-18, DISC-19, DISC-21; the wording of rate-limit prompts is in SAFE-13; the registration flow itself and verification codes are in module 01 (ACC-). Evidence is in evidence/20-invite-growth.md.

## Baseline (follow by default, high confidence)
- **[INV-01] State the reason when an invitation credential cannot be used**: when an invite link or invite code cannot be used, give a clear prompt matching the cause (e.g. expired, invalid, use limit reached), without failing silently and without covering everything with one "Operation failed". Must define: which causes are distinguished and the copy for each (registration invite codes consider at least: wrong format, does not exist, invalid (inviter deleted or disabled, code reset), use limit reached, belongs to oneself); whether "does not exist" and "invalid" are merged into one message (merging reduces enumeration probing of valid codes); the way out after the prompt (edit, clear and continue, ask the inviter for a new code); the expiry copy for group invite links: see GRP-07. | Magnitude: N/A | Confidence: High

## Conventions (default-OK, mark as suggested)
- **[INV-02] A shareable link is the main carrier of invitations**: the "Invite friends" entry generates invitation copy containing the download address, sent through the system share sheet or by copying, with the user choosing the channel and recipients. Must define: the invitation copy (including link and invite code); the copy-success prompt; the information carried by the link (see INV-12); the landing when not installed (see INV-04); whether desktop provides this entry. | Magnitude: N/A | Confidence: Medium (direct evidence from two products)
- **[INV-03] Give an invite entry for unregistered contacts**: when contacts or lookup by number finds an unregistered contact, state that the other party does not use this product yet and provide an "Invite" entry; once the other party registers, they can be added and messaged normally. Must define: where the entry appears (contacts friends page, number search with no result, contact details); the sending method after tapping (see INV-22); a registered user who has set themselves as not findable is likewise shown as unregistered with "Invite" (see DISC-07); the alternative when contacts permission is denied (for reference: use the system contact picker to pick a single contact). | Magnitude: N/A | Confidence: Medium (direct evidence from two products)
- **[INV-04] Invite links distinguish installed from not installed**: when installed, the link opens the corresponding object directly in the app; when not installed, it goes to a web landing page with a download entry. Must define: what the landing page shows (see INV-26); the download destination for each platform; the prompt when opened in an in-app browser that does not support redirects; how the invitation relationship is carried over after installation (see INV-24); the landing page copy when the link has expired (consistent with INV-01). | Magnitude: N/A | Confidence: Medium (direct evidence from two products)
- **[INV-05] Prompt when a contact joins**: See REL-04 (the prompt and switch after a contact registers); the notification to the inviter after registering via an invite code or invite link is in INV-21.
- **[INV-06] Inviting others into a group**: See GRP-07 (expiry mechanism and copy for group invite links and group QR codes); validity period and use count: see GRP-18, join approval is in GRP-08, and an invitee restricting direct adds through privacy settings is in REL-11. This module covers only inviting others to join this product.
- **[INV-07] Personal QR code**: See DISC-14 (validity period and reset of the personal QR code); scan failure causes are in DISC-06; when the personal QR code doubles as a registration invite, the landing for someone who has not installed follows INV-04 after scanning.
- **[INV-08] Contacts upload, matching and permissions**: See DISC-18 (contacts upload method); the default tier of "Find me by phone number" is in DISC-19, already-uploaded data after sync is turned off is in DISC-21, the hidden party being indistinguishable is in DISC-07, the relationship after matching is in DISC-20, and the prompt when permission is denied: see DISC-02.
- **[INV-09] Rate-limit prompts for invitations and code entry**: See SAFE-13 (rate-limit prompts state the limit and when to retry); this module defines only the restricted actions and the limit basis (INV-14, INV-23).

## Divergences (ask Box on must-ask; write default-OK per recommendation and list it)
- **[INV-10] Whether to offer an invitation reward and who receives it**: Option A: no reward, invitation is only a sharing entry / Option B: reward the inviter only / Option C: the inviter and the invitee each get a reward. Recommended: per existing ZYMIX rules; when undecided, recommend C. Rationale: the invitee has a motive to enter the code, and the invitation relationship is more complete; it is the opposite of mainstream instant-messaging practice (none shows a registration reward for ordinary users, and only one product has a promotion commission that goes to the inviter only) and is a growth trade-off. If the reward is cash, wallet balance or points pegged to cash, see PTS-13. | Level: Must-ask | Framing: yes
- **[INV-11] Reward issuing condition and timing**: Option A: issued as soon as the invitee registers successfully / Option B: issued after the invitee completes a specified real action within a period (days) (e.g. completing the profile, sending a first message) / Option C: part issued on registration, the rest after the real action is completed. Recommended: B. Rationale: anti-abuse, since accounts that only register and never use the product get no reward; one product counts commission only when the promoted person pays, and financial analogues all require a real action. If the specified action is wallet account opening or top-up (a fund action in exchange for a reward), see PTS-13. Must define: the completion period and its start point (based on registration success time), the state of the invitation record when it is overdue and not completed, and whether both parties are credited at the same time. | Level: Default-OK
- **[INV-12] Invite code form and information carried by the link**: Option A: one fixed invite code per person (letters and digits, case-insensitive), valid long-term, invalid when the account is deleted or disabled; the invite link carries only that invite code / Option B: the user can reset the invite code, and after reset the old code and old links are invalid immediately / Option C: a one-time code generated for each share. Recommended: A. Rationale: user understanding, easy to pass on verbally; the link carries no identifiable information such as phone number, account ID or nickname. Background: one product's referral link carries the referrer identifier in a short parameter (within a few dozen characters), and the rest are not evidenced. Must define: code length and character set, and whether easily confused characters are excluded (0 vs O, 1 vs I). | Level: Default-OK
- **[INV-13] When an invite code can be entered, and where a failed check leads**: Option A: can be entered only at registration (auto-filled when registering via an invite link), cannot be added or changed after registration / Option B: within a period after registration (days) it can be added once in settings, and cannot be changed after it is entered / Option C: can be entered and changed at any time. Recommended: A. Rationale: the invitation relationship is unique and the basis is simple, avoiding searching for codes after registration to farm rewards. When the check fails, stay on the registration page and state the reason; the user can edit or clear and continue registering; registration is not blocked by the invite code, and an entered code is not silently ignored (rationale: the user can understand the current state and does not mistakenly think it is bound). Background: no product evidence in this library; recommended per the conflict-ruling ladder. | Level: Default-OK
- **[INV-14] Anti-abuse: use limit and new-user determination**: Option A: the invite code has a cumulative use limit and cannot be entered after it is used up; the same phone number and the same device count as a new user only once, and a phone number that has ever registered (including deleted accounts) does not count as a new user / Option B: the invite code has no use limit, only the inviter has a reward cap, and beyond it the binding still happens as usual but the inviter no longer gets rewards / Option C: no cap, relying only on after-the-fact risk control. Recommended: A. Rationale: the invitee knows the result on the spot and the reward basis is unique; financial analogues all limit the number of invitees and exclude existing users by "has ever opened an account". Must define: the use limit and counting basis (cumulative per invite code, not reset over time); how phone numbers of deleted accounts are retained to determine new users (for reference: store only an irreversible digest, not the plaintext number, retention period {TBC}, disclosed in the privacy policy; the relationship with delete-on-deletion: see ACC-21); the rate limit for failed code-entry checks (time window, count, cooldown; prompt wording: see SAFE-13); the basis for same-device determination. | Level: Default-OK
- **[INV-15] Self-invite determination and feedback**: Option A: when the invite code belongs to another account signed in on this device, block immediately on the registration page with a prompt; associations such as same-device history, same real name or same payment identity are determined when the reward is issued, and on a hit no reward is issued and the associated basis is not disclosed / Option B: the registration page never blocks, and everything is determined at issue time / Option C: the registration page blocks all associations immediately and states the reason. Recommended: A. Rationale: relationships the user can see themselves are told on the spot, and risk-control grounds are not exposed. Background: one product does not allow sending a gift to oneself (marked "This is you" when oneself is selected); financial analogues exclude by "has ever opened an account"; one product's promotion terms do not mention self-invite. Must define: the immediate-block copy; the state shown on the invitation record after a hit at issue time (consistent with INV-19). | Level: Default-OK
- **[INV-16] Reward lock period**: Option A: usable as soon as credited / Option B: locked for a period after crediting (days to several weeks), showing "Pending unlock" and the unlock date during the lock period, and automatically usable when it expires. Recommended: B. Rationale: leaves a revocation window for after-the-fact risk control, working together with INV-18. Background: one product's promotion commission is locked for several weeks after crediting and valid for several years, and the rest are not evidenced. Must define: the lock duration and its start point (based on the crediting time), and whether the reward expires and is voided. | Level: Default-OK
- **[INV-17] Points reward issuing failure (invitation, tasks, check-in, etc.)**: Option A: the main action takes effect as usual (registration and invitation relationship, task completion and check-in records are not rolled back), the reward is retried automatically in the background, the invitation record or points details show "Issuing", with a notification once credited; if retries still fail, it goes to manual reissue / Option B: silent retry, not shown to the user. Recommended: A. Rationale: the user can understand the current state, and the main action is not rolled back by a failure in a follow-up reward. Background: no product evidence in this library; recommended per the conflict-ruling ladder. Must define: the number of automatic retries, when it goes to manual handling, whether the status seen by both sides of an invitation reward is consistent, and whether to notify after reissue. Task and check-in rewards follow the same basis. | Level: Default-OK
- **[INV-18] Scope of points reward revocation (invitation, tasks, check-in, etc.)**: Option A: for rewards with a lock period (e.g. invitation), cheating found during the lock period revokes all of it; for rewards after the lock period and rewards with no lock period (e.g. tasks, check-in), only the unspent part is revoked, and the spent part is not clawed back / Option B: revoke all at any time, with the balance recorded as negative if insufficient, and points cannot be used until it is made up / Option C: already issued rewards are not revoked, only subsequent invitation eligibility is canceled. Recommended: A. Rationale: the lock period already covers most cheating, and clawing back to a negative balance after the lock period would hurt users who were misjudged. An invitee deleting their account during the lock period: treated as not completed, and handled by this entry's revocation scope during the lock period, decided together with this entry, without opening another question in the account-deletion requirement. Background: one product's terms reserve the right to revoke, withhold and claw back promotion commission, deducting from the balance when the promoted person gets a refund; financial analogues all reserve clawback rights. It concerns the scope of disposal. Must define: whether and how to notify the revoked party (copy), and the appeal entry. | Level: Must-ask
- **[INV-19] What the inviter can see about invitees**: Option A: the invitation record shows each invitee's avatar, nickname and status (registered, completed, reward credited, not counted) / Option B: show only the number of invitees and the reward total, without listing specific people / Option C: show each entry with a masked phone number. Recommended: A. Rationale: the invitee actively entered the invite code, so showing the nickname is within their expectation; do not show phone numbers; "Not counted" does not state a specific reason, so as not to expose that the other party was risk-controlled or disabled. After an invitee deletes their account, the row shows "Deleted user", which belongs to the same decision. Background: one product's promotion statistics give only the number of people who opened it and do not list specific users, and the rest are not evidenced. It concerns what the other party can perceive. | Level: Must-ask
- **[INV-20] Relationship between both parties after registration**: Option A: both automatically become friends after registration / Option B: no relationship is established automatically; the registration success page shows the inviter and provides "Add as friend", with contact rules see REL-21 / Option C: automatically send the invitee a friend request from the inviter. Recommended: B. Rationale: privacy: entering a code only signals acceptance of the invitation and does not equal agreeing to become friends; consistent with not automatically becoming contacts after contacts matching (DISC-20). Background: no product evidence in this library; recommended per the conflict-ruling ladder. | Level: Must-ask
- **[INV-21] Notification on invitation success and reward crediting**: Option A: send the inviter a system notification when the invitee registers successfully and when the reward is credited, which can be turned off in notification settings / Option B: only update the status in the invitation record, no notification. Recommended: A. Rationale: the user can understand the current state; the switch form is consistent with the contact-joined prompt (REL-04). Must define: the notification copy, whether the invitee side also receives a crediting notification, and whether multiple notifications in the same period are merged. | Level: Default-OK
- **[INV-22] Sending an SMS invitation to an unregistered contact**: Option A: open the device's SMS composer with the invitation copy and link prefilled, and the user confirms sending personally; charges follow the user's carrier standard rates, the invite action does not go through the ZYMIX server, and the other party's number is neither uploaded nor stored / Option B: the platform sends the SMS on the user's behalf, the server obtains the other party's number and bears the cost, requiring a per-person daily cap, a cooldown for the same number, and the other party's opt-out / Option C: no SMS, only the system share sheet (INV-02). Recommended: A. Rationale: privacy: an unregistered person has not consented to handing their number to the platform; one product goes through system SMS and states it is charged at standard rates, one has removed SMS and only shares links, and no platform-sent SMS has been seen. When B is chosen, the SMS delivery regions and compliance requirements are a source-of-truth gap, write {TBC}. It concerns the other party's privacy and what the other party can perceive. | Level: Must-ask
- **[INV-23] Charge prompt and repeat invitations for SMS invitations**: Option A: before the first SMS invitation, prompt that carrier standard rates apply; after a contact is invited, show "Invited"; tapping again within a time window (days) prompts that they were already invited, and sending again is still allowed; the invitation status is stored only on the device / Option B: no charge prompt and no invitation status recorded. Recommended: A. Rationale: costs are borne by the user and must be known beforehand, and repeat reminders reduce disturbance to unregistered people. Background: one product states it is charged at standard rates, and the rest are not evidenced; rate limits when the platform sends on the user's behalf (INV-22 Option B) are set separately. Must define: the length of the time window; devices without SMS capability (tablet, desktop) use the system share sheet instead. | Level: Default-OK
- **[INV-24] How the invitation relationship is carried over after installation**: Option A: when installed, opening the link prefills the invite code; when not installed, the landing page shows the invite code and provides "Copy invite code", and after installation it is entered or pasted manually on the registration page / Option B: tapping download on the landing page writes the invite code to the clipboard, and the first launch reads the clipboard and fills it in automatically / Option C: the server automatically matches the device that tapped the link by device and network characteristics. Recommended: A. Rationale: privacy: C collects device characteristics of unregistered people, and B reading the clipboard on first launch triggers the system paste prompt and causes unease; with A the user sees everything throughout. Background: no product evidence in this library; recommended per the conflict-ruling ladder. It is a privacy default. | Level: Must-ask
- **[INV-25] Content of external share cards**: Option A: the card contains the product name, the sharer's nickname and avatar, one invitation line and the link, with a preview before sharing / Option B: only generic product copy and the link, without sharer information. Recommended: A. Rationale: the recipient can tell who invited them; no phone number or account ID; the sharer sees a preview before sending, and it is the user's own choice. Background: the fields of external share cards are not evidenced in mainstream products. Must define: the card title and description copy; degrade to plain text plus link when the target app does not support cards. | Level: Default-OK
- **[INV-26] What the external-link landing page shows to someone who has not installed**: Option A: show only the object type and "Open in ZYMIX" and "Download", without specific information / Option B: show the name and avatar (personal invite: the inviter's nickname and avatar; group: group name, avatar, member count), without message and feed content / Option C: show full content (including feed post text and images). Recommended: B. Rationale: the recipient can judge whether to join, and messages and feed posts are not exposed to signed-out people; what a group shows on the landing page does not exceed the group profile's visibility to non-members. Background: one product's invite link shows the group name, description, avatar, member count and some members before joining, and the rest are not evidenced. It concerns external visibility scope. | Level: Must-ask

## Must-ask states (module-specific, supplementing the general state matrix)
- Entering a code at registration: wrong format; code does not exist; code invalid (inviter deleted or disabled, code reset); use limit reached; belongs to oneself or to an associated account of the same person; phone number already registered (switch to login, the invite code takes no effect); registering again with a phone number that previously registered and was deleted; the user edits or clears after prefill from opening the link; no network or timeout during the check; failed code-check count triggering the rate limit.
- Rewards: registration succeeds but reward issuing fails or is in progress; invitee does not complete the specified action by the deadline; judged as cheating during the lock period; revoked after being spent; inviter or invitee deletes the account or is disabled; which rule version applies to invitations created before a reward rule change; new invitations after the inviter reaches the cap.
- Contacts invitations: permission denied or only some contacts authorized; the other party is actually registered but set as not findable (same as unregistered); repeat invitation to the same contact; invalid number or unable to receive SMS; this device has no SMS capability; the user cancels sending in the SMS composer; the prompt after the other party registers (see REL-04).
- External sharing: installed vs not installed; opened in an in-app browser that does not support redirects; link expired; sharer deleted the account; opened on desktop; what the landing page language follows.
- Multi-device: when the other device updates after one device resets the invite code; how reward crediting and revocation sync across devices.

## Anti-patterns
| Vague / wrong | Correct | Reason |
|---|---|---|
| "Enter an invite code and both get points" | State the issuing condition and timing, lock period, cap, self-invite determination, issuing failure and revocation | If reward rules are not fully written, they get farmed as soon as they go live |
| "Invalid invite code" as one message for all failures | Distinguish wrong format, does not exist or invalid, use limit reached, belongs to oneself, and state the way out (edit or clear and continue) | The user cannot tell whether they mistyped or should switch codes |
| Blocking registration or silently ignoring when the invite code is wrong | Stay on the registration page and state the reason, and the user can edit or clear and continue registering | Blocking loses new users, and silent ignoring makes users think it is already bound |
| Rolling back the whole registration or showing no prompt when reward issuing fails | Registration still succeeds, the reward is retried automatically, and the invitation record shows "Issuing" | A failure in a follow-up action should not drag down the main action |
| "Can invite contacts" without saying how to send | State the sending method (device SMS or share sheet), who bears the charges, whether the other party's number is uploaded, and the handling of repeat invitations | An unregistered person's number is third-party privacy |
| The invitation record shows the invitee's phone number directly, or "Banned" | Show only avatar, nickname and status, and "Not counted" states no reason | Exposes the other party's number and the risk-control result |
| Phone number or plaintext account ID in the invite link | The link carries only the invite code | Links get forwarded, screenshotted and logged externally |
| Automatically attributing by device characteristics when an uninstalled user taps the link, without telling them | The landing page shows the invite code, to be entered or pasted manually after installation | Collecting device characteristics of unregistered people has no basis of consent |

## Calibration sample
The feature most likely to be written vaguely: the optional invite code on the registration page. The reward form was already fixed at framing as the inviter and invitee each getting points. Five preconditions, rate limit, network, format, validity and self-invite, form a decision chain; the entry timing, where a failed check leads, use limit, scope of self-invite blocking, issuing condition, lock period and handling of issuing failure are written as body text per the recommendation, and values in the card are illustrative; the scope of reward revocation concerns the scope of disposal, is must-ask, and is left as a placeholder in the card.

Description:
1. Entry: the "Invite code (optional)" input box on the registration profile page; when opened via an invite link, the invite code from the link is filled in automatically and can be edited or cleared; after entering a nickname, the "Complete registration" button lights up
2. On tap, check in order:
   a. 1-Rate limit check: when an invite code has been entered, whether invite code checks on this device have failed ≥ 5 times within 24 hours
      i. ≥ 5 times: prompt below the input box "Too many invite code attempts. Try again in 24 hours, or clear the invite code and continue registering", stay on the registration profile page
      i. < 5 times or no invite code entered: go to the next check
   a. 2-Network check: whether there is a network now
      i. No network: toast prompt: "Network unavailable. Check your network and try again", stay on the registration profile page, keep the entered content
      i. Network available: go to the next check
   a. 3-Format check: whether the invite code is empty, or is 8 letters and digits
      i. Empty: complete registration, no invitation relationship established
      i. Wrong format: prompt below the input box "Invite code format is incorrect. Check it and enter again", stay on the registration profile page
      i. Correct format: go to the next check
   a. 4-Validity check: the server checks the invite code status
      i. Check times out: prompt below the input box "Network error. Try again, or clear the invite code and continue registering", stay on the registration profile page
      i. Does not exist or invalid: prompt below the input box "Invalid invite code. Check with the inviter, or clear it and continue registering", stay on the registration profile page
      i. Use limit reached: prompt below the input box "This invite code has reached its use limit. You can clear it and continue registering", stay on the registration profile page
      i. Valid: go to the next check
   a. 5-Self-invite check: whether the invite code belongs to another account signed in on this device
      i. Yes: prompt below the input box "You can't enter your own invite code", stay on the registration profile page
      i. No: complete registration and establish the invitation relationship, which cannot be changed after registration
3. Issuing condition: the invitee sends a first message within 7 days after registering, and the inviter and invitee each get 100 points; if not completed by the deadline, the invitation record shows "Not completed"
4. After the reward is credited it is locked for 14 days; during the lock period the points details show "Pending unlock" and the unlock date, and it becomes usable automatically when the period ends
5. Reward issuing fails: registration and the invitation relationship are unaffected, the reward is retried automatically in the background, the invitation record shows "Issuing", and a notification follows once credited: "Invitation reward of 100 points has been credited"
6. Handling after cheating is determined: {TBD: scope of reward revocation, recommended: revoke all during the lock period, revoke only the unspent part after the lock period}
Note: the reward revocation scope in item 6 is a placeholder and must be finalized before writing
