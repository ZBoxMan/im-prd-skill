# Chat List (Functional Rules)

> Applies to: PRD requirements for chat ordering, pinning, mute, archive/collapse, mark as unread, drafts and summary prefixes, delete/clear chat, chat grouping, and unread counts. For the visual hierarchy and element layout of list rows see 11-ui-structure.md; this file covers functional rules only. Evidence in evidence/03-chat-list.md.

## Baseline (follow by default, high confidence)
- **[LIST-01] Pin**: a chat can be pinned and unpinned; pinned chats are fixed at the top area of the list; the number of pins is capped. Must define: the cap {N}; handling when exceeded (reject with a prompt, or another approach) and the prompt copy and carrier; order within the pinned area (by pin time or manually adjustable); whether one-on-one and group chats share the cap; whether pinning syncs across devices; whether pinning has an expiry (see LIST-30); for pins beyond the free cap after a paid tier lapses see PTS-25. | Magnitude: free tier 3 to 5, paid tier 10 to 20 | Confidence: High
- **[LIST-02] Mute**: a single chat can be muted; for reminder and unread rules during mute see NOTI-04. Must define: entry location; how the list row shows mute state; for mute penetration by @me see NOTI-20, for the effect on incoming calls see NOTI-30; whether unread in muted chats counts toward the total badge, see NOTI-26; whether mute state is visible to the other party in the chat. | Magnitude: — | Confidence: High
- **[LIST-03] Archive/collapse does not delete data**: moving a chat into the archive or collapsed area does not delete chat history; the main list keeps an independent entry for that area, and archived chats can be found through the entry. Must define: entry location; whether the entry shows a count and its basis (number of chats or number of chats with unread); whether they can be found through search; whether they can be moved out manually; whether pinning still works inside the archive area; feedback copy for batch archiving. | Magnitude: — | Confidence: High
- **[LIST-04] Mark as unread and read**: the chat menu offers "Mark as unread" and "Mark as read". Must define: how the list presents a chat with no new messages that is marked unread (with or without a number); the basis on which the mark counts toward total unread and badge; the condition that clears the mark; whether it syncs across devices. | Magnitude: — | Confidence: High
- **[LIST-06] Summary type placeholders**: non-text messages (including one-time media) use a type placeholder copy in the summary and do not show the original content. Must define: the placeholder copy for each message type; whether one-time or self-destructing content uses a dedicated placeholder; summary copy for call records and messages unsupported by the version; the source-label copy for service/official chats. | Magnitude: — | Confidence: High
- **[LIST-07] Unread @me marker**: when a group chat has an unread @me message, the list row has an @ marker independent of the unread number. Must define: whether @all uses the same marker (see NOTI-21); whether being replied to uses the same marker (see NOTI-22); jumping to each of multiple @ one by one; the condition that clears the marker. | Magnitude: — | Confidence: High
- **[LIST-08] Deleting a chat and clearing records are two different things**: "Delete chat" makes the chat disappear from the list and clears this device's records with it; "Clear chat history" keeps the chat entry and clears only the records; by default both act only on this account, and the other party's records are unaffected (for whether two-sided clearing is offered see LIST-25). Must define: location and confirmation copy of the two entries; confirmation dialog or timed undo (see LIST-26); for interception when the chat has unhandled payments see PAY-26; whether deletion syncs across this account's devices. | Magnitude: — | Confidence: High

## Conventions (default-OK, mark as suggested)

- **[LIST-05] Draft display**: for a chat with unsent content, the list summary replaces the last message summary with a "Draft" marker plus the draft content; for when drafts are saved, restored and cleared see UI-31. Must define: the marker copy; placeholder copy in the summary for non-text drafts (image, voice, quote, location, etc.); whether a draft affects ordering (see LIST-20); draft sync across devices (see MISC-32). | Magnitude: — | Confidence: Medium (the draft marker has direct evidence from three products; non-text draft placeholders have evidence from only one product and have been moved to must-define)
- **[LIST-10] Unread count display**: the chat row shows the unread count; for the truncation cap see UX-D5, for how unread appears in muted chats see UX-23. Must define: whether @ unread and ordinary unread are counted separately; when the unread count clears (on entering the chat, or after scrolling to the bottom). | Magnitude: — | Confidence: Medium (showing the unread count on the chat row has direct evidence from four products; truncation and the distinct presentation for muted chats are now defined by the entries that own them)
- **[LIST-28] Group chat summary carries the sender name**: the last-message summary of a group chat is prefixed with "{sender name}: ". Must define: whether the last message sent by oneself gets a "You: " prefix; whether the sender name is the group nickname or the account nickname; whether type placeholders also carry the prefix (e.g. "{sender name}: [Image]"); whether system messages carry a prefix. | Magnitude: — | Confidence: Medium (client string direct evidence from two products, both Medium confidence: in one, the list row's accessibility readout contains "from: sender", in the other the summary format is sender prefix plus type placeholder; the own-side "You" prefix and prefixed type placeholders each have evidence from only one product and have been moved to must-define)

## Divergences (ask Box on must-ask; write default-OK per recommendation and list it)
- **[LIST-20] Ordering and drafts**: this round obtained no direct evidence on the ordering algorithm or the effect of drafts (low confidence). Option A: pinned first, the rest by last-message time descending, drafts do not affect ordering / Option B: same as A, but chats with drafts take part in ordering by draft save time / Option C: same as A, and chats with unread @me are also lifted to just below the pinned area. Recommended: A. Rationale: user comprehension, since ordering affected only by message time is the most predictable, and if drafts took part in ordering, order would differ across devices. Ad items in the chat list do not take part in chat ordering, see ADS-07. | Level: Default-OK
- **[LIST-21] Mute duration**: Option A: on/off only, lasting until manually turned off / Option B: fixed tiers (hours, days, forever), automatically restored on expiry, the list shows the end time / Option C: B plus a custom end time. Recommended: B. Rationale: accessibility and recoverability, since automatic restoration on expiry avoids missing things through permanent muting. Magnitude: shortest one hour, longest about a week, plus "forever", 3 to 7 tiers. Background: tiers appear in three products, while two others are on/off only, so it does not enter the baseline. | Level: Default-OK
- **[LIST-22] Group message reminder tiers**: Option A: groups and one-on-one chats share the same mute switch / Option B: groups have their own four tiers (receive and remind, receive without reminding, move into the archive area without reminding, block). Recommended: A. Rationale: privacy and data integrity, since the "block" tier means messages are not received, which conflicts with history integrity, and the other tiers can be achieved by combining mute with archive. Muting calls for a single group is not in this entry, see NOTI-30. | Level: Default-OK
- **[LIST-23] New message in an archived chat**: Option A: always move back to the main list / Option B: only non-muted chats move back, muted ones stay in the archive / Option C: stay in the archive by default, and a user setting decides whether to move back. Recommended: B. Rationale: accessibility and recoverability, since messages in non-muted chats are not missed and muted ones do not disturb the user. Background: four products' practices fall into A, B and C with no consistent practice. | Level: Default-OK
- **[LIST-24] Where a new stranger chat lands**: for the contact model (whether one can message directly, whether it goes to message requests first) see REL-21; this entry only covers the position of message-request chats in the list. Option A: enter the main list with a "message request" state, with limited capabilities before acceptance / Option B: automatically move into the archive and mute, which can be turned off in settings / Option C: enter the main list on equal footing with ordinary chats. Recommended: A. Rationale: user comprehension, since stranger messages are not hidden, and it is consistent with the REL-21 contact model. | Level: Default-OK
- **[LIST-25] Clearing or deleting on both sides**: Option A: this side only, the other party's records are unaffected / Option B: in private chats, optionally "also clear for the other party", and the group creator can "delete for all members". Recommended: A. Rationale: privacy and data integrity, since unilateral erasure of records held by the other party is not allowed. | Level: Must-ask
- **[LIST-26] Guarding against accidental deletion**: Option A: second-confirmation dialog, no undo / Option B: no confirmation, a timed "Undo" prompt after deletion / Option C: confirmation dialog plus timed undo. Recommended: A. Rationale: user comprehension, since a confirmation dialog is the most predictable when clearing records cannot be restored; confirmation before deletion has direct evidence from two products, timed undo from only one product. | Level: Default-OK
- **[LIST-27] Chat grouping**: Option A: no custom grouping, only the main list and the archive / Option B: built-in filters (e.g. unread only) / Option C: custom folders or lists (with include/exclude rules, a count cap, deleting a group does not delete chats, can be muted as a whole). Recommended: A. Rationale: user comprehension, since mainstream domestic products replace grouping with collapse or archive; custom grouping needs its own count cap and multi-device sync rules, and three products have it (two with Medium-confidence evidence) while two do not, so it does not enter the baseline. Magnitude: folders within a few dozen, each folder's hand-picked chat cap about a hundred to a few hundred. | Level: Default-OK
- **[LIST-29] Mark all as read**: Option A: offered, with a second confirmation / Option B: not offered. Recommended: B. Rationale: privacy and data integrity; only one product has direct evidence and that product offers it, so recommending B is the opposite of existing product practice and is a trade-off against accidental taps: clearing unread in bulk is easy to tap by mistake and loses important unread prompts. | Level: Default-OK
- **[LIST-30] Pin expiry**: Option A: pins have no expiry, canceled manually / Option B: choose a duration when pinning, and the pin is canceled automatically on expiry (tiers set separately). Recommended: A. Rationale: user comprehension; only one product has direct evidence, and automatic cancellation on expiry would make the pin state deviate from user expectation and multi-device display, requiring separate expiry-prompt and sync rules; for the duration of pinned messages see also 05-message-actions.md. | Level: Default-OK
- **[LIST-31] Locked chats**: Option A: not offered / Option B: a chat can be locked, entering requires extra verification (device verification or a self-set code) and the chat is moved into a hidden entry; notifications of locked chats do not show sender or content (see NOTI-33); automatically re-locks after the device locks; "unlock and clear" when the code is forgotten also clears the messages in locked chats. Recommended: A. Rationale: privacy and data integrity; only one product has direct evidence and that product offers it, so recommending A is the opposite of existing product practice and is a data-integrity trade-off: "clear messages if the code is forgotten" conflicts with data integrity and needs a separately designed recovery path. | Level: Default-OK
- **[LIST-09] Deleting a group chat while still in the group**: Option A: only "delete and leave" or leave first and then delete; the state "chat deleted but still a member" does not exist / Option B: allow only deleting or hiding the group chat from the list while keeping membership, and the chat reappears on new messages. Recommended: A. Rationale: user comprehension, since there are the fewest states and no invisible-member state of "not in the list yet still receiving group messages". Background: A has direct evidence from three products; one mainstream domestic product uses B (a hidden chat reappears on new messages), and for domestic users B is closer to habit. If B is chosen, also define: whether this device's records are cleared on deletion, whether history is visible after reappearing, whether @me makes the chat reappear, and extra options for the group owner/creator (see 07-groups-channels.md). | Level: Must-ask

## Must-ask states (module-specific; supplements the general state matrix)
- The other party has blocked/deleted account/left the group: whether the chat stays in the list; what the summary shows; whether it can be pinned, muted, deleted.
- Group dissolved or the person removed from the group: whether the chat stays read-only or disappears automatically; whether pin and mute states are kept; how to clear when unread @ remains.
- Multi-device: when and how this device's list updates after another device has pinned, archived, deleted or marked as unread; which device prevails when two devices pin at the same time and exceed the cap.
- Offline recipient: for messages received while offline, whether ordering after coming back online uses server time or local receive time; whether the unread count is filled in at once.
- The last message is unsent, deleted, or edited by the other party: what the summary shows; whether ordering changes; whether the unread count rolls back.
- Pin cap reached: the prompt and destination of pinning again; multi-device concurrent overrun.
- Mute expires: how unread already present at the moment of expiry is presented; whether there is a prompt on expiry.
- An archived chat receives @me, a reply or a call: whether it still reminds, whether it returns to the main list.
- Draft and failed-send message coexist: which the summary shows first.
- The chat holding a draft is deleted or cleared: whether the draft is cleared with it.
- Weak network or first load: list loading state; whether pins and unread being synced show the local cache first.
- If there are topics or reply threads: for in-thread unread, @me and mute basis see FEED-39 (for whether message-level reply threads are offered see FEED-40).
- After backup restore: whether chats deleted earlier or records cleared earlier reappear; only backups older than the deletion moment can bring them back.
- When pins have an expiry (if B of LIST-30 is chosen): how the list presents it at the moment of expiry, whether it syncs across devices, whether there is a prompt.
- Locked chats (if B of LIST-31 is chosen): visibility of the locked chat in the list and in search, what the summary and notification show, whether it is still locked after switching to a new device, whether calls to a locked chat ring as usual.
- The original chat is deleted after a message was forwarded or quoted: what the quote card shows.

## Anti-patterns
| Vague/wrong | Correct | Reason |
|---|---|---|
| "Chats are sorted by time" | State the primary key (pinned first, then last-message time descending), whether drafts/unsend affect ordering, and whether time is server or local | Order differs across devices, and ordering after unsend is undefined |
| "Pin a chat" with no cap | State the cap {N}, the over-limit prompt, and handling of multi-device concurrent overrun | Without a cap the pinned area loses meaning, and devices conflict under concurrency |
| "No messages are received after mute" | Mute only silences reminders; messages and unread keep accumulating | Confused with archive and block, creating an expectation of data loss |
| "Delete chat" without distinguishing clear records | Define delete chat, clear records and delete-and-leave separately, with their own confirmation copy and whether each can be restored | Users cannot predict whether records are kept |
| "An archived chat returns to the main list on a new message" | Split muted and non-muted per the ruling on LIST-23 | Muted chats get disturbed, or important messages get missed |
| "Show the unread count" | State the truncation threshold, whether @ unread is separate, how unread appears in muted chats, and when it clears | The counting basis is unclear, and badge and list do not match |
| "Show drafts in the list" | State the marker copy, placeholders for non-text drafts, clearing after send, and whether it syncs across devices | Leftover or lost drafts are undefined |
| "When a chat is deleted, the other party's is also deleted" | Default is this side only; if two-sided clearing is offered, rule on it separately and state the prompt on the other side | Privacy conflicts with data integrity |

## Calibration sample
The feature most easily written vaguely: "pin". Before tapping there is only one pre-check, "has the cap been reached", so no decision chain. This example has no must-ask item: the pin cap, the position of a new pin and multi-device sync are all written as body text per recommendation; the numbers on the card are illustrative, actual values are set by business, and each is listed one by one under "Defaulted to recommendation" in the delivery draft.

Description:
1. When a chat is not pinned, the chat menu shows "Pin"; when pinned it shows "Unpin"
2. On tapping "Pin", when the current pin count has reached 5: toast: "You can pin up to 5 chats", the chat stays in place, and the pinned area is unchanged
3. When the current pin count is under the cap: the chat moves to the first position of the pinned area, the menu item becomes "Unpin", with no prompt
4. On tapping "Unpin": the chat leaves the pinned area, returns to the normal area and takes its place per the chat ordering rule, with no prompt
5. Pinning and unpinning sync to all devices this account is logged in on; when several devices pin at the same time and exceed the cap, the operation the server received first prevails, and the later device rolls back that pin with toast: "You can pin up to 5 chats"
