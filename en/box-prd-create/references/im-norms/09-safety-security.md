# Safety and Risk Control

> Applies to: PRDs on end-to-end encryption, safety codes, disappearing/auto-delete messages, view-once media, screenshots, reports, risk control and rate-limit prompts, suspicious link/scam warnings. Evidence: see evidence/09-safety-security.md.

## Baseline (follow by default, high confidence)
- **[SAFE-01] State the encryption scope explicitly**: State which chats or content are protected end to end, and do not write "secure" generically. Must define: the protection status of each chat type (one-on-one, group, call, channel); whether the unprotected parts (such as metadata and cloud backups) are stated as well; display location (chat info or another entry) and copy. | Confidence: High
- **[SAFE-02] Safety code can be viewed and compared**: The encrypted chat details provide a safety code (graphic or digit string); the same display on both devices proves there is no man in the middle. Must define: entry location, whether a "verified" mark is offered and whether a trace is left in the chat, sync of the verified mark across devices, how to copy and share. | Magnitude: digit-string form of about several tens of digits | Confidence: High
- **[SAFE-04] Disappearing timer applies only to new messages after it is set**: Existing messages are unaffected. Must define: when messages disappear on each participating device after expiry (timer start see SAFE-24), which side messages in flight at the moment of setting belong to, the chat list summary display after expiry, whether forwarded-out content is still bound by the timer. | Confidence: High
- **[SAFE-06] Timer tiers include off and fixed tiers**: Offer off plus fixed tiers. Must define: the list of fixed tiers, whether custom is supported and its unit and bounds. | Magnitude: lower bound several tens of seconds to one day, upper bound four weeks to about three months | Confidence: High
- **[SAFE-08] Screenshots can be blocked in protected scenarios**: Screenshots can be blocked within a specified scope. Must define: the protected scope (protected chats, one-time content or a global switch), whether screen recording is blocked too, whether an in-place prompt is shown when enabled, the promise boundary of the explanatory copy (whether it states that photographing with another device cannot be prevented), degraded copy when the system does not support it. | Confidence: High
- **[SAFE-10] Report and block can be done together**: Reporting and blocking can be completed together in one flow, or only one of them; the two are independent and not forcibly tied. Must define: the form of the combined entry (tick block when reporting / tick report when blocking), the default checked state, where the chat goes after blocking. | Confidence: High
- **[SAFE-13] Rate-limit prompts state the limit and the retry timing**: When a frequency limit is triggered, state "limit reached" explicitly and give "try again later", "try again tomorrow" or a countdown; do not fail silently and do not use a generic "Operation failed". Must define: the limit value for each restricted action, the prompt carrier, when buttons are greyed out and when they recover, how server rate-limit errors are mapped to prompts users can understand. | Confidence: High
- **[SAFE-14] In-place risk prompts**: Prompt the risk right next to high-risk content (such as a first message from a stranger, a suspicious file type, a risky external link). Must define: trigger condition, prompt copy, whether the user can choose to continue or cancel, whether the same content is no longer intercepted after continuing and the scope of that memory. | Confidence: High

## Conventions (default-OK, mark as suggested)

- **[SAFE-03] Disappearing-timer changes leave a system message**: Setting, changing or turning off the timer each generates a system message in the chat, stating the actor and the new tier. Must define: system message copy, whether consecutive changes within a short time are collapsed and the collapse threshold. | Confidence: Medium (only two products)
- **[SAFE-05] Global default timer applies only to newly opened chats**: The default value does not change existing chats. Must define: the auto-apply condition (such as one-on-one only, the other party registered, no timer yet), whether a system message is generated when it is applied. | Confidence: Medium (only two products state it applies only to new chats)
- **[SAFE-07] View-once media does not leak content**: The chat list, notifications and similar places show only a "one-time photo/video" placeholder and not the content; it disappears after the receiver opens it; it cannot be forwarded. Must define: display when quoted, whether it can be edited, whether the sender's device deletes in sync, prompt copy on repeated taps, whether the receiver's screenshots are blocked (see SAFE-08). | Confidence: Medium (placeholder and non-forwardable each have direct evidence from two products)
- **[SAFE-11] Report targets cover users and groups**: Both users and groups can be reported. Must define: whether reporting a single message is supported, the entry locations (profile page, group info page, message long-press menu), the report target for group-invite requests (the group or the inviter), whether the reason list is the same at every entry, handling when the target has deleted their account or left the group, whether the leave-group entry can report at the same time. | Confidence: Medium (group reporting for one product comes from a paraphrase of an official specification page)
- **[SAFE-12] Report feedback does not promise a result or a time limit**: After submission the copy says only "Submitted, will be reviewed by the team" or "Notified", and does not state a handling time or result. Must define: whether a report progress entry is offered, whether the reported party is notified. For the state machine see SUP-10. | Confidence: Medium (feedback copy evidenced from only two products)

## Divergences (ask Box on must-ask; write default-OK per recommendation and list it)
- **[SAFE-09] Report form**: Option A: one-tap report, no reason breakdown, with the system attaching the most recent several messages of the reported content / Option B: pick a reason category first, optional additional description, with confirmation feedback after submission (the number of reason categories is on the order of 7 to 10; the character limit of the additional description and the inline prompt for submission failure must be defined). Pick-reason-first two products, no-reason-breakdown one product, the reason items of another not evidenced. Recommended: B. Rationale: reason categories help reviewers triage and users can understand them; the disclosure scope follows SAFE-28. When B is adopted, the reason list is filtered by report target (one each for message, user, group) and must include high-risk categories (self-harm or suicidal tendencies, minor safety, personal threats): high-risk categories are flagged as priority by the server, after submission use a result page rather than a toast, showing help resources and "In an emergency, contact local police or emergency services immediately", with the resource content written as {TBC}. | Level: Default-OK
- **[SAFE-21] Default encryption scope**: Option A: all one-on-one chats are end-to-end by default / Option B: only "encrypted chats" the user actively turns on are end-to-end, the rest go through the cloud / Option C: transport encryption only. Recommended: A. Rationale: privacy first; if ZYMIX already has an end-to-end encryption page, the existing rules prevail. | Level: Must-ask | Framing: yes
- **[SAFE-22] Feature boundaries of encrypted chats**: Option A: same as ordinary chats / Option B: no forwarding, no editing, no cross-device sync. Whether link previews are generated by default see MISC-31, who fetches them see RICH-57; for translation and AI see AI-14. Recommended: A corresponds to default encryption, B corresponds to optional encryption, decided together with SAFE-21. | Level: Default-OK
- **[SAFE-23] Prompt strength for safety code changes**: Option A: a dialog before sending, send only after confirmation / Option B: a system message in the chat, on by default / Option C: a system message in the chat, off by default, and the user turns it on separately on each device / Option D: silent renegotiation. Recommended: B. Rationale: neither blocking nor silent; for high-risk needs, layer A on top as a user-selectable setting. This is the opposite of the evidenced products' practice (three known products are A, C and D respectively), a trade-off between security awareness and disturbance. | Level: Default-OK
- **[SAFE-24] Disappearing timer start point**: Option A: counts from sending / Option B: counts after the other party reads / Option C: by scenario, cloud chat counts from sending, one-time content counts after reading. Recommended: B. Rationale: avoids disappearing before the other party has read it, data integrity. | Level: Must-ask
- **[SAFE-25] Disappearing timer scope and who can set it in groups**: Option A: one-on-one only / Option B: one-on-one and groups, only admins can change it in groups / Option C: everyone in the group can change it. Recommended: B. Rationale: prevents it from being turned off by an individual member. | Level: Default-OK
- **[SAFE-26] Scope of view-once media**: Option A: images and videos only / Option B: plus voice and files. Recommended: A. Rationale: smallest scope for the first release. | Level: Default-OK
- **[SAFE-27] Screenshot detection and notification**: Three products show no detection or notification, only one product notifies on a best-effort basis in encrypted chats. Option A: no detection / Option B: detect only in encrypted or disappearing chats and notify the other party by system message, with copy noting best effort / Option C: block only, no notification. Recommended: C. Rationale: detection is unavailable on some systems and notification misleads users (user understanding). | Level: Must-ask
- **[SAFE-28] Whether a report attaches chat content**: Option A: do not attach, send only the account and metadata / Option B: attach the single reported message / Option C: attach several messages of context (a single-digit count, such as the most recent 5) / Option D: attach the single reported message by default, and the reporter can tick other messages in the same chat (limit about 10, in group chats only messages from the reported person and oneself can be chosen). Recommended: D. Rationale: harassment and scams often need context to judge, and letting the reporter choose balances minimal disclosure; in encrypted scenarios, before submission the user must be told the messages will be submitted to the platform in readable form (a persistent notice, with a second confirmation on the first report). When B or D is adopted, the upload content must be stated per message type (whether images, videos, voice and files upload the original file or a summary, and the size limit). | Level: Must-ask
- **[SAFE-29] Follow-up actions after a report**: Option A: report only / Option B: after reporting, prompt that the user can block / Option C: group reports linked with leaving the group (after reporting add "Leave group chat", or when leaving the group the user can tick "Report group"). Recommended: C. Rationale: after reporting a harassing group users usually need to get out. | Level: Default-OK
- **[SAFE-30] Cooldown threshold for high-risk operations**: Option A: none / Option B: only after two-step verification has been on for several days plus a new-device login of at least 1 day are group owner transfer and withdrawal-type operations allowed. Recommended: B. Rationale: prevents fast transfer after an account is stolen, the magnitude is set by the business. | Level: Default-OK
- **[SAFE-31] Chat-level "restrict content leaving" switch**: Option A: do not build / Option B: either party in a one-on-one chat or group admins can turn it on for the chat, restricting export, forwarding or saving / Option C: one-time media only. Recommended: A. Rationale: it cannot prevent screenshots and retelling, and easily gives users a false sense of security (user understanding); if adopted, the copy must follow the boundary of SAFE-08. | Level: Default-OK
- **[SAFE-32] "Keep" mechanism for disappearing messages**: Option A: do not build / Option B: group members can "keep" a disappearing message, the sender has final control and is notified, and can cancel the keep. Adopted by only one product. Recommended: A. Rationale: smallest scope for the first release; if B is adopted, the backup, forwarding and expiry rules of kept messages must be defined at the same time. | Level: Default-OK
- **[SAFE-15] Verification code and PIN anti-scam**: Option A: state "No one will ever ask for your verification code or PIN" on the verification code page, stranger requests or safety prompt pages / Option B: in addition to A, the server automatically invalidates a verification code that is forwarded or pasted into a chat / Option C: no dedicated prompt. Recommended: A. Rationale: low prompt cost and users understand it; auto-invalidation needs the server to recognize verification codes in chats and can be a later enhancement. Background: each of the two approaches has direct evidence from only one product. | Level: Default-OK

## Must-ask states (module-specific, supplements the general state matrix)
- Encryption: another device has not yet synced keys; the first message after the other party reinstalls or changes device; the other party's device does not support encryption; the safety code changes after the other party adds or removes a linked device.
- Safety code: the verified mark is cleared by another device midway; the safety code changes during verification; the other party is a deleted account; when change prompts are turned on per device, the display on another device that has not turned it on.
- Disappearing: the original message expires after it has been forwarded, quoted or favorited; a pinned message expires; an offline receiver comes online only after expiry; one device in multi-device has not read it.
- Disappearing: in-flight messages when an admin turns off the timer in a group; this device's timer conflicts with the other party's setting; handling of messages already expired when forwarded to a chat without a timer or when restoring from backup; notification previews still lingering after expiry.
- View-once media: one device in multi-device opens it first; opening is interrupted on a weak network; the sender unsends; the other party's device takes a screenshot.
- Screenshot: the system does not offer blocking; screen recording and screen casting; protected content being retold by others (cannot be prevented).
- Report: the target has been blocked, has deleted their account, has left the group; the reported message was unsent by the other party (recommended: accept as normal based on the message snapshot the client holds when entering the report page, and do not reject, otherwise send-then-unsend can destroy evidence; fall back to reporting the user only when there is no local content either); whether a reporter who is themselves banned or restricted can report and can see records; groups the user was removed from or has left can still be reported from the history chat; a report does not automatically trigger punishment and must go through review, the handling basis for malicious reports (how many malicious determinations restrict reporting and for how long, and the prompt copy); high-risk categories are not fully exempt from rate limits (a separate higher limit, or a risk-control mark once exceeded); the help entry for high-risk categories is shown as soon as that reason is selected, and is also kept on the repeat-report and submission-failure paths; when reporting a group, the messages that can be ticked are limited to those sent by the group owner, admins and oneself (third-party members' messages are not handed over with a group report); when the unsend happened before entering the report page, the unsend placeholder offers a "Report this user" entry; forwarded or quoted messages are reported against the current sender, not traced back to the original author; screenshots are uploaded one by one and a single failure can be retried; reporting the same target repeatedly; draft retention after submission fails on a weak network; the message scope attached to a report and the disclosure notice in encrypted chats.
- Risk control: multi-device operating at once during a restriction; switching to background during a countdown; the restriction expires while content is being edited.
- Scam prompts: a link in a stranger's message is long-pressed and copied by the user; a file comes from a blocked account.

## Anti-patterns
| Vague/incorrect | Correct | Reason |
|---|---|---|
| "Messages are end-to-end encrypted, safe and reliable" | State the encryption scope, boundaries, entry location and copy | A generic promise carries compliance risk |
| "Supports burn after reading" | State the tiers, start point, new messages only, change system messages, when messages disappear on each device | Missing any one leads to inconsistency across devices |
| "Notify the other party when a screenshot is detected" | State whether detection is reliable, the degradation when it cannot detect, notification copy noting best effort | Cannot be guaranteed under system limits |
| "Admins handle it after a report" | State the reason list, whether messages are attached, feedback copy and no promised time limit | A report is a privacy disclosure action and must be stated explicitly |
| "Too many operations, try again later" | State which action, the limit, the recovery timing and the scope of greyed-out controls | Cannot be accepted or verified |
| "Prompt when the safety code changes" | State the prompt strength, whether it blocks sending, whether the verified mark is invalidated | Prompt strength is a divergence |

## Calibration sample
Easiest to write vaguely: reporting a user. The report page form, the default checked state of also blocking, and handling of deleted accounts are written as body text per recommendation and listed under "Defaulted to recommendation" in the delivery draft; whether a report attaches chat content falls in the privacy disclosure scope, is must-ask, and is left as a placeholder in the card.

Description:
1. Tap "Report" on the other party's profile page to enter the report page: first single-select a report reason, with an optional additional description
2. "Also block this user" is a tick option, not ticked by default
3. After a reason is selected the "Submit" button lights up; it is greyed out when no reason is selected
4. Chat content attached to the report: {TBD: whether a report attaches chat content and its scope, recommended: attach the reported message by default, the reporter can tick other messages in the same chat, and is told before submission}
5. On tapping "Submit", check in order:
   a. 1-Network check: is there network now
      i. No network: Toast: "Network unavailable. Check your network and try again", keep the filled-in content
      i. Network available: go to the next check
   a. 2-Target status check: has the reported account deleted their account
      i. Deleted: submit the report, do not block, Toast: "Report submitted, will be reviewed by the team"
      i. Not deleted: go to the next check
   a. 3-Block tick check: is "Also block this user" ticked
      i. Ticked: submit the report, block after success, Toast: "Report submitted and user blocked"
      i. Not ticked: submit the report, Toast: "Report submitted, will be reviewed by the team"
6. Submission fails (service timeout): Toast: "Submission failed. Please try again", keep the filled-in content and tick state, do not block
7. Note: the report attaches {TBD: scope of chat content attached to the report, recommended: the reported message plus the same-chat messages the reporter ticks}; when the chat is end-to-end encrypted, a dialog before submission explains the message scope that will be submitted with the report
