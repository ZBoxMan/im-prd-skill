# Discovery and adding, third-party login, system permission prompts

> Applies: read this file when a PRD involves QR code cards and scanning, face-to-face group creation, people nearby, contacts matching and upload, Apple / Google login and account bind/unbind, or the timing of system permission requests (notifications, contacts, microphone, camera, location, screen recording) and guidance after denial. Verification codes, multi-device and account deletion are in module 01 (ACC-); stranger contact is REL-21; friend search and adding is REL-01; group join links are GRP-07, GRP-18; permissions and devices during calls are in module 10. Evidence is in evidence/18-discovery-login-permissions.md.

## Baseline (follow by default, high confidence)
- **[DISC-01] Device permissions are requested on demand**: device permissions such as microphone, camera and screen recording are requested only when the user first triggers a feature that needs them, not all at once at launch or registration. Must define: the list of triggering features per permission (e.g. microphone: voice messages, calls; camera: capture, QR scanning, video calls; screen recording: screen sharing); whether an own explanation is shown before the system dialog (see DISC-04); permission and device gaps in call scenarios are in MISC-10. | Magnitude: N/A | Confidence: High
- **[DISC-02] On re-trigger after denial, explain why and offer a path to Settings**: when the user uses a feature again after denying a permission, the prompt states "which feature needs which permission" and offers a "Go to Settings" entry that jumps to system settings. Must define: the denial prompt copy and carrier (dialog or inline prompt) for each permission; button copy (e.g. "Go to Settings", "Cancel"); whether desktop writes out the path inside system settings; whether the original action resumes automatically after returning from system settings. | Magnitude: N/A | Confidence: High

## Conventions (default-OK, mark as suggested)

- **[DISC-03] Denial does not block the rest**: permission explanation screens and prompts both provide a "Not now"-type exit; after denial only the features that depend on that permission are disabled, and everything else works as usual. Must define: the features unavailable after denial, listed one by one; whether the corresponding entry is grayed out or shows a prompt on tap (the empty state for a denied permission is in UX-18); when the same denied permission may be prompted again (for reference: platform guidelines require no full-screen blocking and no repeated dialogs urging the user). | Magnitude: N/A | Confidence: Medium (direct evidence from two products plus platform guidelines)
- **[DISC-04] Show an own explanation before the system dialog**: before requesting a permission that needs a stated purpose, such as contacts or notifications, first show one own explanation screen (one-sentence purpose, primary button, "Not now"); the system dialog is triggered only after the user taps the primary button; when the system will no longer show the dialog (already denied and the system does not ask again), the primary button changes to "Turn on in Settings". Must define: which permissions need an explanation screen (device permissions may trigger the system dialog directly); the title, purpose copy and button copy of each explanation screen; the prompt for partial grants (e.g. notifications partially turned off). | Magnitude: N/A; whether to show it once more at a valuable moment after "Not now" (recommended: show notifications once more when the first message is received, and stop showing if the user picks "Not now" again) | Confidence: Medium (direct evidence from two products plus platform guidelines)
- **[DISC-05] Location is requested on demand and is not a precondition**: location is requested, with its purpose stated, only when using location-related features (send location, nearby-type features), and location authorization is not a prerequisite for using other features. Must define: the authorization scope (while in use or always, precise or approximate location) is a privacy default and is treated as must-ask; the authorization scope for live location: see RICH-39 and is not asked again; the purpose copy; the alternative for location-related features after denial (e.g. manual place search). | Magnitude: N/A | Confidence: Medium (direct evidence from one product plus platform guidelines)
- **[DISC-06] QR scan failures distinguish causes**: scan results distinguish at least "code expired" from "unrecognized or not a code of this product", each with its own copy, rather than one blanket "Recognition failed". Must define: the copy and destination for each cause; the prompt when no QR code is detected in the frame; whether an expired code prompts the user to ask the sharer for a new one; whether an external URL is opened when scanned and whether a prompt precedes opening it; whether recognition from a photo-library image is supported; the camera permission for the scan entry follows DISC-01, DISC-02. | Magnitude: N/A | Confidence: Medium (direct evidence from two products)
- **[DISC-07] Contacts matching cannot distinguish a hidden party**: when the matched party is set to not be findable by phone number, contacts matching and lookup by number return the same result for them as "this number is not registered", and the searcher cannot tell the difference; the switch for being findable by number is in REL-01. Must define: whether they remain visible when a chat already exists or they are already mutual contacts; the matching and lookup rate limit per account (for reference: client-side throttling, the server may require retrying later); whether match results include people who blocked me or whom I blocked. | Magnitude: N/A | Confidence: Medium (direct evidence from two products)
- **[DISC-08] Third-party accounts can be unbound**: a bound Apple or Google account can be unbound in settings. Must define: the unbind entry and confirmation copy; whether unbinding is allowed, and the prompt copy, when the account has only one sign-in method left (for reference: one product disallows unbinding and requires binding or switching to another method first); whether one third-party account or phone number can be bound to multiple ZYMIX accounts (for reference: one-to-one); the prompt and way out when the third-party account is already bound to another ZYMIX account; after unbinding, whether signing in with that third-party account creates a new account or prompts that it is not bound; behavior after the user revokes authorization on the third-party side. | Magnitude: N/A | Confidence: Medium (direct evidence from one product plus platform guidelines)
- **[DISC-09] Validity period and expiry of group QR codes**: See GRP-07 (expiry mechanism and expiry copy); validity period and use count: see GRP-18, approval for joining via QR scan is in GRP-08, and re-entry by scan after being removed is in GRP-25. This module defines only the scan entry and failure causes (DISC-06).
- **[DISC-10] Contact rules after scan, contacts or nearby discovery**: See REL-21 (strangers obtained from scan, contacts matching or nearby discovery are all handled by the stranger contact model for whether they can be messaged directly); adding by searching an account identifier is in REL-01.
- **[DISC-11] QR login, passkey and account deletion**: See ACC-05 (a signed-in device scans to confirm a new device sign-in); passkeys are in ACC-29, account deletion: see ACC-21 (when listed on iOS, an in-app deletion entry is mandatory). This module defines only third-party login and binding.
- **[DISC-12] Prompt when a contact joins**: See REL-04.

## Divergences (ask Box on must-ask; write default-OK per recommendation and list it)
- **[DISC-13] Timing of notification and contacts permission requests**: Option A: request notifications and contacts together on the post-registration onboarding pages, each page skippable / Option B: both triggered by scenario (notifications after the first message sent or first entry to the chat list, contacts when the user taps "Add from contacts") / Option C: notifications via the post-registration onboarding page (skippable), contacts triggered by scenario. Recommended: C. Rationale: notifications are a prerequisite for receiving messages, and requesting early reduces missed messages; contacts are private data, and requesting by scenario matches platform guidelines. Background: one product uses a consolidated onboarding page, one requests per scenario. | Level: Default-OK
- **[DISC-14] Validity period and reset of the personal QR code**: Option A: valid long-term, the user can reset manually, the old code is invalidated immediately on reset, contacts are not notified / Option B: expires automatically on a schedule (days), with the expiry time shown under the code / Option C: the code is bound to the username and expires when the username changes. Recommended: A. Rationale: user understanding (the code can be printed on a business card long-term), and the user can reset it themselves if it leaks. Background: A has direct evidence from one product (the other is a search snippet), C from one product; B appears only for group QR codes. | Level: Default-OK
- **[DISC-15] Whether the source of adding is shown to the added party**: Option A: show the source category on the friend request or new contact (scan, group chat, contacts, search, shared card) / Option B: do not show the source. The scope of the shared person's information in a shared card and "Allow others to add me via card": see RICH-44. Recommended: A. Rationale: user understanding, and it helps the added party decide whether to accept; show only the category, not the specific group name. Background: evidence from only one product (shows the source category). Showing the specific group name or the search term falls under what the other party can perceive, so treat as must-ask. | Level: Default-OK
- **[DISC-16] Face-to-face group creation**: Option A: not provided / Option B: provided; nearby people enter the same numeric code to join the same group, the code is valid for a short time (minutes) and distance is limited by location / Option C: provided; code only, no location, the code is valid for a short time. Recommended: A. Rationale: privacy: B requires collecting location, and C without a distance limit lets strangers collide on the same code and join the group; only one product offers it, and its newer description no longer states distance or validity duration; the recommendation is already the most conservative option and falls under "whether to provide a secondary feature". | Level: Default-OK
- **[DISC-17] People nearby**: Option A: not provided / Option B: provided; invisible to others by default, the user appears in others' lists only after actively turning on "Let people nearby see me", can turn it off at any time, and turning it on requires location permission. Recommended: A. Rationale: privacy and harassment surface: nearby discovery exposes approximate location; one product still keeps it and the other has taken the feature offline (inferred); the recommendation is already the most conservative option and falls under "whether to provide a secondary feature", and when Box asks for it to be provided, its default visibility is treated as must-ask. | Level: Default-OK
- **[DISC-18] Contacts upload method**: Option A: raw numbers are continuously synced to the server for matching and friend recommendations / Option B: numbers are processed into salted digests before upload or matched in an encrypted environment (phone numbers can be enumerated, so the copy does not say "irreversible"), and the server does not keep a plaintext address book / Option C: contacts are not uploaded, only lookup by a single number is supported (see REL-01). Recommended: B. Rationale: privacy and data integrity: the server does not hold others' plaintext numbers, and the matching value is retained. Background: A and B are one product each. When B is adopted, the card must state: digests are salted and the matching API is rate-limited (the phone number space is small, so unsalted digests can be enumerated and reversed, and credential-stuffing-style probing can also reveal whether a number is registered); whether matched data is deleted immediately or the salted digest is kept, and for how long; the explanation screen copy is consistent with the chosen option and does not over-promise. | Level: Must-ask
- **[DISC-19] Default tier of "Find me by phone number"**: Option A: everyone (the number itself is still not shown to others) / Option B: only people in my contacts / Option C: nobody, can be added only by username or QR code. The switch itself and its copy are in REL-01; this entry defines only the default value, and it also constrains contacts matching (DISC-07). Recommended: A. Rationale: contacts matching requires the searcher to already hold the number, and A exposes only "this number is registered", while B and C make contacts matching largely ineffective; it is a privacy default and is for Box to decide. Background: both products provide this switch; the default value is not evidenced. | Level: Must-ask
- **[DISC-20] Relationship after contacts matching**: Option A: matched people automatically become contacts and can be messaged directly / Option B: matched people are only listed in the "Contacts friends" list and must be added actively, with contact rules per REL-21. Recommended: B. Rationale: the matched party has not consented, and becoming contacts automatically would bypass the stranger contact gate. Background: A and B are one product each. | Level: Default-OK
- **[DISC-21] Already-uploaded data after contacts sync is turned off**: Option A: turning it off deletes the uploaded address book from the server, and established contacts and chats are unaffected / Option B: stop further syncing, keep the uploaded data, and provide a separate "Delete synced contacts" entry. Recommended: A. Rationale: privacy and data integrity: a user who turns off sync expects the server to no longer hold their address book. Background: one product provides a separate delete entry (B), the rest are not evidenced. Handling of already-collected data after other consents are withdrawn: see PRIV-13. | Level: Must-ask
- **[DISC-22] Third-party login and phone number**: Option A: after signing in with Apple or Google, a phone number must be bound to complete registration / Option B: the phone number is optional; when unbound, the third-party account is the only credential, and the settings page prompts the user to bind one later / Option C: no third-party login. When listed on iOS with a third-party account as the primary sign-in method, review rules require offering another equivalent sign-in option that meets privacy conditions (the common practice is Apple sign-in); cases such as using only the company's own account system may be exempt (not rechecked online). Recommended: A, per existing ZYMIX rules. Rationale: recoverability: after the third-party account is disabled or authorization is revoked, the user can still sign in with a phone number; the only product with evidence has changed historical third-party registered users to mandatory phone binding. | Level: Must-ask
- **[DISC-23] Phone number already registered when binding it during third-party login**: Option A: prompt that the number already has an account and guide the user to sign in with the phone number instead; after signing in, the third-party account can be bound in settings; no new account is created this time / Option B: allow switching to another number to continue creating a new account. Recommended: A. Rationale: data integrity: avoids one person having two accounts with scattered history. Not evidenced in this library; recommended per the conflict-ruling ladder. | Level: Must-ask

## Must-ask states (module-specific, supplementing the general state matrix)
- System permissions: the app goes to background while the system dialog is showing; enabling in system settings after denial and returning; permission revoked by the system during use (while recording, in a call, while scanning); a one-time grant that has expired; partial grants (notifications partially turned off, only some photos or contacts authorized); settings path differences between desktop and mobile.
- QR codes: code reset or expired, group dissolved, sharer left the group (whether the code expires with it), group full, scanner already removed from the group, scanner blocked by the other party, scanning one's own code, scanning a code from another product, no network when scanning.
- Contacts matching: authorization denied or only some contacts authorized; upload progress, failure and retry for a large address book; the other party turns off being findable; sync after deleting a contact locally; the other party changes number or deletes the account; whether blocked and blocking people appear in the list.
- Third-party login: cancel, failure or network interruption on the third-party authorization page; that third-party account is already bound to another account; signing in again after the third-party side revokes authorization; Apple sign-in with the hidden email option; how to sign in after an account registered with Apple on iOS moves to Android.
- Face-to-face and nearby (if provided): location denied or inaccurate, code collision, code expired, group member count reaching the limit, when others' lists remove me after I turn visibility off.
- First-launch onboarding: whether the step order in the requirement source causes downstream problems (e.g. finding friends first and setting a profile later, so sent requests carry only the default nickname); if so, send it to a ruling (profile first or nickname required); the default nickname must not contain any part of the phone number; onboarding progress is stored on the server per account, and the two permission steps appear based on whether the local system status is "not determined", which equally applies to returning users on a new device or after reinstalling; the verification code page keeps entered input on network loss or timeout; validation order is local format, protocol, cooldown, network, then server rate limit; the minimum age goes to a ruling per AGE-06 and is not hardcoded.
- Multi-device: when the other device's sign-in state and lists update after one device unbinds a third-party account or turns off contacts sync.

## Anti-patterns
| Vague / wrong | Correct | Reason |
|---|---|---|
| Showing contacts, notifications, camera and microphone system dialogs back to back at launch | Device permissions are requested on first use of the feature; for contacts and notifications, show an own explanation screen first, then trigger the system dialog | System dialogs usually appear only once, and out-of-context requests have a high denial rate that is hard to recover from |
| "Prompt to enable the permission when denied" | State which feature needs which permission, the "Go to Settings" and "Cancel" buttons, and which features are unavailable after denial | The user does not know why to enable it or where |
| Blocking the whole page after a permission is denied, or showing a dialog on every entry | Disable only the features that depend on the permission, and prompt only on re-trigger | Violates platform guidelines and disturbs the user |
| "QR scan recognition failed" as a single blanket message | Distinguish expired code, unrecognized or not this product's code, and no QR code detected | The remedy available to the user differs |
| "Sync contacts to find friends" | State the upload method, the matched party's findability switch and its default, the relationship after matching, and what happens to the data after sync is turned off | Contacts are other people's data; privacy and revocability are both required |
| "Supports Apple / Google login" | State whether a phone number must be bound, the way out when the number is already registered, the unbind rules, and keeping at least one sign-in method | When the third-party account becomes invalid, the user is locked out of the account |
| "People nearby can see each other" | State invisible by default, how to turn it on, can be turned off at any time, and the location authorization scope | Location is highly sensitive data |
