# Page structure (main frame, chat list, chat page, input bar, profile and settings pages)

> Applies when: read when drawing IM prototype screens (top-level pages, chat list, chat page, input bar, profile page, settings page) and writing annotation cards for those pages. Annotation cards describe only behavior, structure and priority, never visual specs; the "magnitude" and "time window" values in this file serve only to judge whether a value is off the charts. Evidence is in evidence/11-ui-structure.md.
> Evidence boundary: the local client yielded only static strings, with no live UI; official help centers cover only feature rules and almost never describe UI layout. Layout conclusions rely on open-source client source code; platform design guidelines and open-source SDKs serve only as corroboration and are not counted toward the product count; three tiers apply: conclusions where three or more of five products have consistent direct evidence go into the baseline, those with only two products go into conventions (Medium confidence), and those with only one product are treated as divergences.

## Baseline (follow by default, high confidence)

### Main frame and search
- **[UI-02] Search entry and result sections**: The search entry sits at the top of the chat list; results are sectioned by type such as "Contacts and chats / Message history", each with a section title. Must define: the list of searchable objects, section order, placeholder copy (whether it states the search scope), no-results copy; retention and clearing of recent searches (see MISC-03); filter dimensions and in-chat jump-to-date (see MISC-24). | Confidence: High

### Chat list
- **[UI-06] Last message unsent**: The summary shows an unsend placeholder (distinguishing own from others'), never the original text. Must define: placeholder copy; whether the placeholder names the actor when an admin unsends someone else's message; if the product leaves no unsend trace, whether the list falls back to the previous message (see module 05). | Confidence: High
- **[UI-07] In-row send status**: Shown only for the last message the user sent; priority: failed > sending > read > delivered > sent; the last message from the other party shows no send status at all; the semantics of status icons inside the bubble are in UI-39. Must define: whether the read state is still shown when the counterpart is blocked or receipts are turned off (consistent with UI-39). | Confidence: High
- **[UI-09] Pin**: See LIST-01 (limit, over-limit prompt, paid tier and pinned-area order are defined only there); this module adds only that pinned chats are visibly distinguished from regular chats in the list. | Confidence: High (same as LIST-01)
- **[UI-12] Long-press menu and swipe action set**: The chat-level action set is highly consistent: mark as read/unread, pin/unpin, mute/unmute, archive or fold, delete. Must define: menu item order (whether delete-type items go last in a destructive style); the swipe action composition (see UI-D5) and whether each swipe action has an equivalent entry in the long-press menu; mute duration tiers; whether multi-select is offered, the multi-select action bar composition, and the confirmation copy before deleting. | Confidence: High
- **[UI-13] Archive and fold entry**: Archived or folded chats collapse into a single entry row in the chat list. Must define: entry position (top or bottom of the list) and whether it takes part in normal sorting; the basis of the count on the entry (total archived chats, or only archived chats with unread; whether it shows an @ marker instead when there is an unread @); the back-navigation copy after entering; whether a new message returns the chat to the main list: see LIST-23. | Confidence: High
- **[UI-14] Stranger chat entry**: An unaccepted stranger chat or message request carries a clear request state (a standalone entry, a chat label, or a banner at the top of the chat); whether that chat lands in the main list or a standalone entry is in the stranger-landing divergence in module 03. Must define: where the request state appears and its copy; the actions offered (accept, delete, block, report); abilities restricted before acceptance; whether the notification preview of a request-state chat shows body text: see NOTI-24 (must-ask). | Confidence: High

### Chat page
- **[UI-22] System messages**: Copy uses the third person, with a second-person variant for the user's own actions ("You unsent a message", "{nickname} unsent a message"). Must define: display form (centered or not, no bubble, no avatar, no read status, cannot be reacted to, cannot be @-ed, no long-press menu); the list of events that enter the timeline (whether low-level state events such as permission changes and join rules enter the timeline); which roles an event is visible to (for example a leave prompt visible only to admins); whether consecutive join and leave events and consecutive deleted messages are folded, and the fold threshold. | Confidence: High
- **[UI-23] Content-type templates**: Content types such as text, image or video thumbnail, voice, file, location, contact card, sticker, link preview, poll and call record each have their own display; types unsupported by the version show fallback copy. Must define: display elements per type (voice: duration and playing state; file: name, size, status; link preview: title, summary, thumbnail, whether the whole card is tappable, placeholder copy when fetching fails); whether a removable preview bar appears above the input bar before a link preview is sent; fallback copy and whether to guide an upgrade (see MISC-17). | Confidence: High
- **[UI-24] Quote block**: A reply carries a quote block with the quoted person and a content summary; tapping the quote block jumps to the original message. Must define: quote block position (above the body inside the bubble, or outside the bubble); the summary form per type (text truncated, image thumbnail, voice duration); whether the landing briefly highlights after the jump; how to jump when the original message is not in the loaded range; copy and tap behavior when the original message has been unsent or does not exist; whether the quoted original is still shown after a disappearing message expires. | Confidence: High
- **[UI-25] Positioning on entering a chat**: With unread messages, scroll to the first unread and show an unread divider above it; with none, stay at the latest message. Must define: divider copy (whether it includes a count) and when the divider disappears; whether messages are held back from being marked read until positioning completes. | Confidence: High
- **[UI-27] Jump to bottom and jump to @**: After scrolling up to browse history, a "Back to bottom" entry appears; when there are unread @s, a separate "Jump to @" entry appears. Must define: the scroll threshold at which "Back to bottom" appears and whether it shows a new-message count; the jump order with multiple unread @s, whether the landing is highlighted, and when the entry disappears. | Confidence: High
- **[UI-28] Failed-send retry entry**: A message that failed to send shows a failure indicator beside the bubble; the failed state is expressed with a status icon and does not recolor the whole bubble. Must define: what tapping the failure indicator does (resend directly, or pop up "Resend / Delete"); whether the long-press menu also offers "Resend" and where. | Confidence: High
- **[UI-39] Bubble receipt icons**: The user's own message bubbles use separate icons for sending, sent, delivered or read, and failed, one icon per state; the number of levels and whether "delivered" is included follow the receipt-level ruling (see SEND-09); the distinction between delivered and read follows UX-28. Must define: each state icon's semantics and screen-reader copy; whether voice has a "played" state; the group-chat read criterion (any one person or everyone) and whether details can be expanded; the display after receipts are turned off or the counterpart is blocked; whether the read state resets after the user's own message is edited. | Confidence: High

### Input bar
- **[UI-31] Draft**: Unsent text is saved when leaving a chat and restored when returning; draft save, restore, clear timing and overwrite confirmation are defined only in this entry, and the chat-list draft indicator: see LIST-05. Must define: whether it is kept after quitting the app; draft clear timing (such as after a successful send); whether to confirm discarding when edit mode is closed with non-empty content; whether to confirm before an existing draft is overwritten and the confirmation copy; the save scope for non-text drafts; cross-device sync: see MISC-32. | Confidence: High

## Conventions (default-OK, mark as suggested)

### Main frame and search

- **[UI-01] Top-level navigation**: 3 to 5 bottom top-level entries, each with both an icon and a single-word label; top-level pages have no back key, second-level pages have a back control in the top bar and support the system edge-swipe back; "More" is not used to hold high-frequency entries. Must define: the entry list and order, the default landing, which entries carry badge counts, and the behavior of tapping the current entry again. | Magnitude: 3–5 entries | Confidence: Medium (the entry count has direct evidence from only one product; icon plus label, the back rules and not using "More" rest on platform design guidelines as corroboration)

### Chat list

- **[UI-03] Row composition**: avatar → first line (chat name truncated to a single line + status icon + time) → second line (summary truncated + indicator area). Long text is always ellipsized and never wraps to grow the row. Must define: summary line count (1 or 2 lines); which indicators can sit side by side in the indicator area and their order (see UI-08). | Magnitude: summary 1–2 lines | Confidence: Medium (row composition has direct evidence from two products; summary line count has only one product's source code plus open-source client corroboration, and has been moved to must define)
- **[UI-04] Summary content priority**: When a local draft exists, the summary shows the draft, taking priority over the last message. Must define: the full priority among search-state matched snippet, other party typing, unsend placeholder, system message or call record, and regular message preview (for reference: matched snippet > typing > draft > unsend placeholder > system message or call record > regular message); which level it returns to after typing ends; the display copy for each level. | Confidence: Medium (draft taking priority over the last message has direct evidence from three products; typing overriding the summary and the full order have one product's evidence plus open-source SDK corroboration and involve inference, and have been moved to must define)
- **[UI-15] List empty states**: Filter-no-results and search-no-results each use their own copy and do not reuse the "no chats" empty state. Must define: the composition of the empty state when there are no chats at all (title, explanation, primary action such as "Start a chat"); whether the filter empty state carries an "Edit filter" entry. | Confidence: Medium (direct evidence from only two products; the no-chats empty-state composition has only open-source client corroboration)
- **[UI-08] Unread and @ indicators**: The unread count and the @ indicator can sit side by side; the presentation of unread in muted chats: see UX-23. Must define: the count cap (see UX-D5), whether copy distinguishes @ from "@all"; whether only the @ indicator is shown when the total unread is exactly 1 and that one is an @; the order and trade-offs when several indicators (in a call, muted, @, unread count, pin icon) coexist. | Confidence: Medium (@ and unread side by side has direct evidence from two products; indicator order has one product plus open-source client corroboration, and has been moved to must define)

### Chat page

- **[UI-16] Top bar**: The title shows the other party's name or the group name, and the subtitle shows live status (connecting, typing, online or last seen). Must define: the composition of the right-side entries (call, search, more); where tapping the title area goes; whether a group title includes the member count; the priority and copy of each subtitle state; what the subtitle shows after the privacy setting is turned off. | Confidence: Medium (subtitle live status has direct evidence from two products, and a third's placement is inferred; entry composition and state priority have evidence from only one product, so they appear only under must define)
- **[UI-18] Message grouping and breaks**: Consecutive messages from the same sender merge into one group; a new day, a change of sender, or exceeding the time window breaks the group. Must define: the time window (see UI-D2); other break conditions (a system message inserted between, a scheduled message, a message with reactions, whether forwarded messages are judged by original author or forwarder). | Magnitude: 3–10 minutes | Confidence: Medium (direct evidence from only two products)
- **[UI-17] Pinned message bar**: The pinned message is permanently shown below the top bar, and tapping it jumps to the original message; with several pins you can switch between them, with an index or count shown. Must define: whether the pinned bar can be hidden; the cap and full-capacity policy: see ACT-21; validity period: see ACT-23; who may pin and whether members are notified: see ACT-22; whether a message still sending can be pinned; whether a system message in the chat says who pinned it. | Confidence: Medium (a permanent bar below the top bar and switching between several pins have direct evidence from only two products, plus open-source client corroboration)

### Input bar

- **[UI-30] Input length and growth**: When the input exceeds the send length limit, give clear copy ("Text is too long to send"). Must define: the length limit; whether the input box grows with content, its growth cap, and whether it scrolls inside the box beyond that. | Magnitude: about 5 lines | Confidence: Medium (the over-length prompt has direct evidence from only two products; the growth rule has only open-source SDK corroboration)
- **[UI-32] Reply and edit bars**: Reply state: a quote bar appears above the input box (quoted person + summary + close), and tapping close cancels the reply; edit state: an "Edit message" bar appears with the original text prefilled. Must define: whether tapping the quote bar itself jumps to the original message; the send button copy in edit state; whether the pre-edit draft is restored after canceling an edit; whether canceling asks for confirmation when there are changes. | Confidence: Medium (reply and edit bars have direct evidence from two products, and a third has a quote panel as support; the details under must define each have evidence from only one product)
- **[UI-33] @ panel**: Typing @ in a group chat pops up a member picker, and selecting inserts @nickname. Must define: whether continued typing filters; whether the insertion acts as a single block and whether backspace deletes it as a block; whether it triggers in one-on-one chat; the permission for @all (can be limited to admins only by a member-count threshold) and the entry position. | Confidence: Medium (direct evidence from only two products; panel details have only open-source SDK corroboration)

### Profile and settings pages

- **[UI-34] Profile page groups**: The header has avatar, name and primary actions (message, call, etc.), followed by groups such as personal info fields, shared content (media, files, links), chat settings (notifications, pin, message retention), (group) members, and a danger zone. Must define: the group order; the conditions under which each group is shown. | Confidence: Medium (direct evidence from only two products; the order is inferred)
- **[UI-36] Permission entries on group profile**: Management groups (member management, permissions, invite links, join requests) appear only to those with permission; admins are marked with a label. Must define: whether an entry without permission is hidden or grayed out with an explanation; whether "Remove" appears in the member actions for roles that cannot be removed. | Confidence: Medium (management groups appearing by permission have direct evidence from four products, the admin label from two; hidden versus grayed out has evidence from only one product, so it appears only under must define)
- **[UI-37] Settings top-level groups**: Account and profile, notifications, privacy and security, data and storage (auto-download, storage usage, clear cache), general (appearance, language), about and help; danger items such as "Log out" and "Clear all chat history" go at the bottom with confirmation. Must define: group order and the list of second-level pages. | Confidence: Medium (three products' groupings overlap; the order is unconfirmed)
- **[UI-38] Settings item interaction**: Toggles take effect immediately with no "Save" button; settings that need a choice go to a second-level page and show the current value on the right. Must define: which settings need a one-line consequence note under the item (those that change what the other party sees or device behavior once on). | Confidence: Medium (toggles taking effect immediately and second-level-page choices have direct evidence from two products each plus platform-guideline corroboration; the consequence note has only one product)
- **[UI-35] Danger actions at the bottom**: Block, report, leave group chat, delete chat and remove contact are gathered in a standalone group at the very bottom of the page, with verb-object phrase copy, and each is confirmed after tapping (confirmation rules: see UX-11, UX-12). | Confidence: Medium (bottom placement has direct evidence from only one product plus platform design guideline corroboration; verb-object copy and confirm-after-tap have three)

## Divergences (ask Box on must-ask; write default-OK per recommendation and list it)
- **[UI-D1] Top-level navigation composition**: A Chats / Contacts / Me (3 entries); B Chats / Contacts / Discover or Feed / Me (4 entries, mainstream in China); C Chats / Calls / Settings (minimal, privacy-first types). Recommended: A. Rationale: user understanding (no empty entries when there is no content-feed feature); top-level entries hold only high-frequency items; the three-entry structure differs from the entry composition of every evidenced product, so this is a user-understanding trade-off. | Level: Default-OK
- **[UI-D2] Grouping time window**: A about 3 minutes; B about 10 minutes; C about 1 minute; D no time window, grouped only by consecutive sender. Recommended: A. Rationale: user understanding (timestamps neither too dense nor too sparse). | Level: Default-OK
- **[UI-D3] Avatar and nickname display rhythm**: A avatar at the end of the group, nickname at the start of the group; B avatar and nickname on every message (some products in China); C avatar at the start of the group. Recommended: A. Rationale: user understanding, consistent with the grouping rule; avatar at the end of the group has source-code evidence from two products. | Level: Default-OK
- **[UI-D4] Chat-list time style**: A relative time ("3 minutes ago"); B absolute time (time of day for today / yesterday / weekday / date). Recommended: B. Rationale: user understanding (matches habits of users in China, and screen readers can still read the full time); it is the opposite of the only product with source-code evidence (A), so this is a user-understanding trade-off. | Level: Default-OK
- **[UI-D5] Chat row swipe action composition**: A a single "Archive" action, executed on full swipe; B 2–3 items exposed on each side (swipe right: read + pin; swipe left: mute + delete + archive); C swipe left only, exposing "Pin / Mark unread / Delete". Recommended: B. Rationale: recoverable (delete always carries a confirmation or undo) and the action set matches the long-press menu. | Level: Default-OK
- **[UI-D6] Archived chat receives a new message**: See LIST-23 (defined only there).
- **[UI-D7] Input bar form when restricted (muted, left the group, blocked)**: A replace the whole input bar with explanatory text or a single action button (unblock, rejoin); B keep the input bar and prompt with a dialog or system message after tapping send. Recommended: A. Rationale: accessibility and recoverability (users see the cause and what they can do at a glance). | Level: Default-OK
- **[UI-D8] Display of very long messages**: A fold beyond the display limit and show "Read more", tapping goes to a full-text page; B no folding, show the full text; C fold, then expand in place. Recommended: A. Rationale: user understanding (long text does not fill the screen); this item has evidence from a single source only. | Level: Default-OK
- **[UI-05] Summary prefix and type placeholders**: See LIST-28 (group-chat sender-name prefix and the user's own "You:" prefix), LIST-05 (draft indicator), LIST-06 (type placeholders and the fallback placeholder for unsupported messages).
- **[UI-10] Sorting**: See LIST-20 (sort key and the effect of drafts are defined only there).
- **[UI-19] Bubble timestamp and nickname display conditions**: Only one product has direct source-code evidence this round (low confidence). Option A: the in-bubble time is shown only at the end of a group, and messages that are sending, failed to send, or carry an expiry countdown always show it; the sender nickname is shown only in multi-person chats / Option B: every message shows its time, and the sender nickname is shown only in multi-person chats. Recommended: A. Rationale: user understanding: no repeated timestamps within a group, while abnormal states stay visible. Background: not showing nicknames in one-on-one chat is common practice but not evidenced product by product; avatar and nickname position: see UI-D3. | Level: Default-OK
- **[UI-20] Date separator tiers**: Only one product has direct source-code evidence this round (low confidence). Option A: inserted across days; today, yesterday, weekday within a week, full date for older (with the year across years) / Option B: inserted across days; today, yesterday, weekday plus month and day within half a year, full date with the year for older. Recommended: A. Rationale: user understanding: a weekday beyond a week helps little with locating; it is the opposite of the only evidenced product's approach (B), so this is a user-understanding trade-off. Background: the current date floating at the top while scrolling has only one product's source code plus open-source client corroboration; if needed, raise it with Box as an open item. | Level: Default-OK
- **[UI-21] Bubble direction**: Only one product has direct source-code evidence this round (low confidence). Option A: own on the right, the other party on the left, the whole layout mirrored in RTL languages (see UX-31) / Option B: all on the left, with sender distinguished by avatar and nickname. Recommended: A. Rationale: user understanding: own and the other party are told apart at a glance; option B has no product evidence this round. | Level: Default-OK
- **[UI-29] Input bar composition**: Only one product has direct source-code evidence this round (low confidence). Option A: attachment entry → multi-line input box (including emoji entry) → a right-side mutually exclusive "Voice / Send" button, showing voice when the input box is empty and send when it has content / Option B: voice entry and send button are separate, with voice as an independent button or a separate mode switch. Recommended: A. Rationale: user understanding: few entries, and the primary action switches with input state. Background: another product's desktop client has a standalone "Send voice" entry; the attachment menu item list and order, and the voice hold-and-lock rules, must be written whichever is chosen (see module 06). | Level: Default-OK
- **[UI-11] List time tiers**: Option A: the nearer the more precise and the farther the coarser (time of day today, yesterday, weekday, date), and the year must be included across years / Option B: always show the full date and time of day. Recommended: A. Rationale: user understanding: recent messages read by time of day and old ones by date takes the least reading; Background: only one product has direct source-code evidence, and two others have only time words such as today, yesterday, weekday and year, with usage unconfirmed. If A is chosen, must define: the tier boundaries (consistent with UI-D4); whether 12 or 24-hour format and the order of weekday and date follow the system and region; whether screen readers read the full time. | Level: Default-OK
- **[UI-26] Reading-position protection**: Option A: when the user is at the bottom, new messages scroll in automatically; when the user has scrolled up to browse history, new messages do not grab the scroll position and instead accumulate in the "Back to bottom" entry / Option B: always scroll to the bottom when a new message arrives. Recommended: A. Rationale: user understanding: not interrupted while reading history; Background: one product has direct source-code evidence, and three others have only strings about new-message counts and back-to-bottom, with the behavior inferred. If A is chosen, must define: whether new messages that arrive while the user drags the list are held until scrolling stops and then inserted; whether the current reading position is kept after earlier history loads. | Level: Default-OK

## Must-ask states (specific to this module, supplements the general state matrix)
- Other party blocked or deleted account: how the chat row name, avatar, summary, status icon, and chat-page input bar are each presented.
- Other party left the group, was removed, or the group was dissolved: whether the chat row is kept, whether the chat-page input bar is replaced, whether history is readable.
- Multi-device: after another device has read, whether the unread count, divider and @ indicator on this device clear in sync; after another device unsends, how the list summary and quote block on this device update.
- Offline receiver / offline sender: how long the sending state is kept in the list and chat page, and the conditions for turning it into failed.
- Weak and lost network: status copy at the top of the list and in the chat top bar (see UX-15); how a history-load timeout is presented.
- The original message is unsent after it has been forwarded or quoted: what the quote block and forward card show.
- Group vs. one-on-one differences: nickname, @, read presentation, summary prefix and pin permission, marked item by item.
- Permission revoked midway (muted while typing, removed from the group, admin demoted): whether the draft is kept, when the input bar is replaced, whether an open menu refreshes.
- Draft and sorting: whether having a draft changes chat order, and whether it affects the position of a pinned chat.
- Receipts: what the bubble and list status icons show when read receipts are turned off, the counterpart is blocked, or only some people in a group chat have read; whether the status icon resets after the user's own message is edited.
- Over limits: the prompt and destination for each of the pin limit, attachment count and size limits, and input length limit.
- Empty chat and first entry: what guidance a new chat with no messages shows; how the divider and positioning are handled when entering a chat whose history has been cleared.
- Version too old: what placeholder an unsupported message type shows in the list, the chat page, and notifications.

## Anti-patterns
| Vague or wrong | Correct | Reason |
|---|---|---|
| "The chat list shows the last message" | State the summary priority, prefixes, type placeholders and unsend placeholder | The list summary has 6 levels of source, and a vague line misses drafts and typing |
| The summary of an unsent message still shows the original text | Show the unsend placeholder | Leaks unsent content, violating privacy and data integrity |
| Unread count shows the full number (such as 1234) | Show "{N}+" beyond the cap | Blows out the in-row indicator area and has no reading value |
| Always scroll to the very bottom on entering a chat | With unread messages, position at the first unread and show the divider | Users cannot find where to start reading |
| Force scrolling to the bottom when a new message arrives | When the user is not at the bottom, do not grab the position; accumulate in "Back to bottom" | Interrupts a user reading history |
| Failure retry placed only in the long-press menu | Show a failure indicator beside the bubble that can be tapped to handle | Users cannot discover the entry |
| System messages with avatar and bubble and long-press reactions | Centered, no bubble, no menu | Confused with user messages |
| Danger actions mixed with regular items or placed in the middle | A standalone group at the bottom, verb-object phrases | Accidental taps on irreversible actions |
| An entry that says "No permission" only after the unauthorized user taps it | Hide the entry, or gray it out with an explanation | Wastes a tap and is unrecoverable |
| A settings toggle that still needs a "Save" tap | Toggles take effect immediately | Conflicts with platform settings habits |
| Delivered and read distinguished only by tick color | Different shapes or counts, with screen readers reading "Delivered" and "Read" | Color-blind and screen-reader users cannot tell them apart |

## Calibration sample
The thing most easily written vaguely is the "chat-list row summary". This example has no must-ask items: summary priority, sender prefix, unsend placeholder and non-text drafts are all written into the body per recommendation and listed one by one under "Defaulted to recommendation" in the delivery draft. A compliant annotation card body:

Description:
1. Scope: the summary area of every row in the chat list (the first line is the chat name, status icon and time; the second line is the summary and indicator area)
2. Trigger: when the list refreshes or a chat has new activity, determine the summary content in this order, stopping at the first match:
   a. 1-Search state check: is the list currently in search-result state
      i. Yes: the summary shows the snippet containing the matched keyword
      i. No: go to the next check
   a. 2-Typing state check: is the other party typing
      i. Yes: the summary shows "Typing…", and when the other party stops typing it returns to the next check
      i. No: go to the next check
   a. 3-Draft check: does this chat have an unsent draft
      i. Yes: the summary shows "Draft:" plus the draft body; a non-text draft shows "Draft:" plus a type placeholder, such as "Draft: [Image]"
      i. No: go to the next check
   a. 4-Unsend check: has the last message been unsent
      i. Unsent by self: the summary shows "You unsent a message"
      i. Others unsent their own message: the summary shows "{nickname} unsent a message"
      i. Admin unsent a member's message: the summary shows "{admin nickname} unsent a member's message"
      i. Not unsent: go to the next check
   a. 5-Type check: the type of the last message
      i. System message or call record: show the system copy
      i. Non-text content: show the type placeholder "[Image]", "[Video]", "[Voice]", "[Location]", "[Contact card]"; a type unsupported by the current version shows "[This message is not supported in the current version]"
      i. Text: show the body, at most 2 lines, truncated with an ellipsis beyond that
3. Sender prefix: in a group chat, messages from others get a "{sender name}: " prefix, and type placeholders likewise carry the prefix, such as "{sender name}: [Image]"; in a group chat, the user's own messages get a "You: " prefix; one-on-one chats add no prefix; drafts, unsend placeholders and system messages carry no prefix
