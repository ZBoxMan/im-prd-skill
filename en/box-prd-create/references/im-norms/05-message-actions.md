# Message Actions (Reply/Quote, Forward, Unsend/Delete, Edit, Multi-select, Reactions, Pin, Favorites)

> Applies to: read this file when a PRD involves the long-press menu, reply/quote, forward, unsend, delete, edit, copy, multi-select, emoji reactions, pinned messages, favorites, or reporting a single message. Evidence: see evidence/05-message-actions.md.

## Baseline (follow by default, high confidence)
- **[ACT-01] Placeholder when the quoted original is missing**: A reply is sent with a quote block; when the original message has been unsent, deleted or no longer exists, the quote block does not disappear or go blank but shows placeholder copy. Must define: the placeholder copy and whether "has been unsent" is distinguished from "does not exist"; where tapping the quote block goes in the placeholder state; whether the media thumbnail in the quote block is cleared along with the original; whether the original text in the quote block is still kept after a disappearing message expires. | Magnitude: N/A | Confidence: High
- **[ACT-02] Count limit for multi-select and forwarding**: Multi-select forwarding has a count limit; when exceeded, the entry is not shown or the limit is prompted; the multi-select and forward count limit is defined only in this entry. Must define: the forward count limit and over-limit copy; whether bulk delete and bulk unsend have a separate limit and its value. | Magnitude: about 30 to 100 messages | Confidence: High
- **[ACT-03] Non-forwardable types and mixed multi-select**: Some message types cannot be forwarded, including content that is not downloaded or has expired; when a multi-selection mixes in non-forwardable messages, the entry must be disabled or the reason prompted, and they must not be silently dropped. Must define: the list of other non-forwardable types (whether each of the following can be forwarded: unsent or deleted messages, system event messages, payment messages (see PAY-07), view-once content, voice); in a mixed selection, whether the whole action is disabled or the non-forwardable items are skipped with the count prompted. | Magnitude: N/A | Confidence: High
- **[ACT-04] Unsend target and time limit**: Members can only unsend messages they themselves sent successfully (admins unsending others' messages see ACT-08); when a time limit is set, after it expires the entry disappears or tapping prompts that it has timed out. Must define: whether there is a time limit and its value (see ACT-16), the message types that can be unsent (unsend restrictions on payment cards see PAY-07), whether group and one-on-one share the limit, whether chat with oneself is exempt, timeout copy, whether the unsend takes effect when the other party's version is too old or sync fails. | Magnitude: minutes to several days (unlimited in some cases) | Confidence: High
- **[ACT-07] Feedback for unsend failure and partial failure**: Unsend depends on the network; failure on the user's own side must give a retryable prompt; when a bulk unsend partially succeeds, the user must be told that not all succeeded. Must define: network failure copy, timeout failure copy, partial success copy and whether it states how many succeeded and failed, the message stays unchanged after failure, whether the unsender is told when it has not taken effect on the other party's side (one product does not tell; this decides whether the unsender can know the other party can still see it, falls in the data deletion scope, treat as must-ask). | Magnitude: N/A | Confidence: High
- **[ACT-08] Group admin unsends others' messages**: Group admins can unsend or delete members' messages, usually leaving a visible trace (placeholder or admin log). Must define: whether it is a separate permission item and which role levels it is granted to, whether messages of the group owner or peers and higher can be handled, who can unsend whose, whether there is a time limit (same as the self-unsend limit or not), the subject of the placeholder copy (admin unsent vs self unsent), whether ordinary group members can see which admin handled it (some products show the admin log only to admins), whether the unsent user is notified, whether a reason can be attached when handling. | Magnitude: N/A | Confidence: High
- **[ACT-09] Delete for self only**: Deletion affects only this device (the other party and other group members are unchanged), needs a second confirmation and states its scope; it is clearly distinguished from "unsend for everyone" in the menu and confirmation dialog. Must define: confirmation copy, whether it syncs to the user's other devices, how the chat list summary falls back after deletion. | Magnitude: N/A | Confidence: High
- **[ACT-10] Bulk actions in multi-select**: Multi-select mode offers at least bulk forward and bulk delete; other bulk actions (copy, favorite) are added or dropped as the product needs. Must define: the list of bulk actions, whether the selected count is shown and its copy, the selection limit (see ACT-02), how to exit multi-select. | Magnitude: N/A | Confidence: High
- **[ACT-11] Emoji reactions**: Messages can be reacted to lightly; reactions are attached to the original message and add no chat entry. Must define: count per person per message (see ACT-20), the cap on the number of kinds per message, whether a reaction can be changed or removed and whether removal notifies, the entry to the reactor list, whether the reacted-to user is notified (see NOTI-32), whether reactions disappear together with a disappearing message, send-failure prompt. | Magnitude: 1 to 3 per person per message, the number of kinds per message is in the tens | Confidence: High
- **[ACT-12] Pinned messages: multiple allowed, with a persistent entry**: A chat can pin several messages at once, and the chat has a persistent entry to switch between or view all of them and jump to the original message. Must define: whether the current index and total are shown when there are multiple, the count limit and the policy when full (see ACT-21), who can pin (see ACT-22), handling when a pinned message is unsent. | Magnitude: — | Confidence: High
- **[ACT-28] General constraints for editing (if editing is offered)**: When editing is offered, an edited message must carry an "edited" mark, and some message types cannot be edited. Whether to offer editing see ACT-18. Must define: the list of non-editable types (whether each of the following can be edited: forwarded messages, stickers, voice, polls, location, the media itself; payment messages see PAY-07), the mark copy, whether to degrade the display and the degraded copy when the other party's version does not support editing, whether editing triggers a new notification, whether read receipts are reset after editing, handling when the original message is unsent during editing. | Magnitude: N/A | Confidence: High

## Conventions (default-OK, mark as suggested)

- **[ACT-13] Admission limits for favorites**: Expired, not downloaded, protected or oversized content cannot be favorited, and a reason prompt is given. Must define: the non-favoritable types and reason copy, the per-action count limit for favorites, the single-file size limit, whether the favorite is kept after the original message is unsent. | Magnitude: file limit on the order of 100 MB | Confidence: Medium (direct evidence from only two products)
- **[ACT-19] Limit on the number of forward target chats**: One forward can pick multiple target chats, but a single-digit limit is set to prevent mass-send harassment; when exceeded, further selection is disabled and a prompt is shown. Must define: the target limit, over-limit prompt copy, handling when targets include groups the user has left or blocked contacts. | Magnitude: single digits (about 5 to a dozen or so) | Confidence: Medium (three products set a limit, the single-digit value has direct evidence from only two products)
- **[ACT-05] Leave a placeholder after unsend**: After unsend, the original position is replaced with a system placeholder and does not simply disappear. Must define: whether the placeholder copy and subject differ between the user's own side and the other side (e.g. "You unsent…", "{nickname} unsent…"), whether the placeholder counts toward the unread count and the last-message summary, how long the placeholder is kept. | Magnitude: N/A | Confidence: Medium (four products leave a trace, one product leaves no trace after deletion as a counterexample)
- **[ACT-06] Downstream consistency after unsend**: An unsent message can no longer be forwarded; existing quote blocks show a placeholder per ACT-01. Must define: whether the server retains the unsent original content and for how long, used only for reports and compliance (a privacy and compliance trade-off, treat as must-ask; for a message already reported before unsend, the report ticket stores a separate snapshot of the original for review, unaffected by the retention option); whether the download, favorite and new-quote entries disappear in sync; whether already forwarded copies are unsent too, and whether content the other party has already downloaded locally or favorited is kept (these two decide who can still see the content after unsend, fall in the data deletion scope, treat as must-ask). | Magnitude: N/A | Confidence: Medium (non-forwardable has direct evidence from two products; non-downloadable and non-favoritable each have evidence from only one product, and another product's receiver may still keep a local copy; all moved into must define)

## Divergences (ask Box on must-ask; write default-OK per recommendation and list it)
- **[ACT-14] Combined forwarding**: Option A: forward one by one only / Option B: both one-by-one and combined (combined into one chat record card that can be opened again) / Option C: combined only. Recommended: B. Rationale: user understanding (multiple messages of context need to be presented as a whole) and one-by-one keeps recoverability. | Level: Default-OK
- **[ACT-15] Forward source mark and hiding**: Option A: show "Forwarded from {source}" and allow tapping through to the profile page, and the source user can turn off the display in privacy (once off it shows "This user is hidden" and is not tappable) / Option B: mark only "Forwarded" without exposing the source / Option C: no mark. Whether protected content (group admin or sender forbids forwarding and saving) is offered is decided separately; for the secondary mark on multiple forwards see ACT-27. Recommended: A. Rationale: privacy and data integrity first; the source stays traceable while respecting the source user's privacy switch. | Level: Must-ask
- **[ACT-16] Unsend time limit value**: Option A: minutes (about 2 to 5 minutes, mainly to prevent misdelivery) / Option B: 24 hours to several days (allows later correction, about 1 to 2 days) / Option C: unlimited in one-on-one chat, limited in groups and channels. Recommended: B. Rationale: recoverability over abuse prevention; a limit that is too short leaves users with no remedy after they discover a mistake. Background: B two products, A two products, C one product (unlimited in one-on-one, limited in groups), no majority. | Level: Must-ask (mainstream values range from minutes to days, directly determining product positioning)
- **[ACT-17] Re-edit after unsend**: Option A: give a "Re-edit" entry next to the unsend placeholder, with a minutes-level time limit, text-type messages only / Option B: not offered, correct through the editing feature (ACT-18). Recommended: B if ACT-18 is offered, otherwise A. Rationale: avoid two entries for the same need. When B is chosen, write the reason and cost (the user must retype after unsend) under "Not in this release". | Level: Default-OK
- **[ACT-18] Edit sent messages**: Option A: not offered (not seen in mainstream domestic products) / Option B: offered, with a time limit (on the order of 15 minutes to 48 hours), a count limit (single digits to tens, some products set none), and edit history viewable (one product offers it) / Option C: offered without a time limit (unlimited at the specification layer, only a few roles at the product layer). For the "edited" mark and non-editable types see ACT-28. Recommended: B. Rationale: privacy and data integrity, the other party needs to know the content was changed; the limit and count take values per the magnitude and are listed under "Defaulted to recommendation". | Level: Default-OK
- **[ACT-20] Reactions per person per message**: Option A: 1 per person per message, tapping again replaces it / Option B: multiple per person per message, with a limit (single digits; at the protocol layer only the same emoji must not repeat). Recommended: A. Rationale: simplest for users to understand, the reactor list is one person per row; two products have direct evidence of one per person (another has low confidence). | Level: Default-OK
- **[ACT-21] Pin count limit and policy when full**: Option A: single-digit limit (about 3 to 4), when full replace the oldest after confirmation / Option B: reject outright when full, requiring the user to unpin an old one first / Option C: no hard limit, only limit the number of visible items (unlimited at the protocol layer). Recommended: A. Rationale: recoverable, there is a confirmation before replacing and the originally pinned message itself is not lost. | Level: Default-OK
- **[ACT-22] Who can pin and whether to notify members**: Option A: group owner and admins only, and when pinning they can choose whether to notify everyone (default notify) / Option B: pinning is a separate permission item (may be merged into "edit group info"), default admins only, can be opened to members, and pinning leaves a "{operator} pinned a message" system message in the chat flow without a push / Option C: any member can pin (visible only to themselves). Whether one-on-one chat supports pin for oneself only is decided separately. Recommended: A. Rationale: pinning affects everyone's attention, so notification should be decided explicitly by the pinner. | Level: Default-OK
- **[ACT-23] Pin duration**: Option A: permanent, unpin manually / Option B: choose a duration tier when pinning (24 hours, 7 days, 30 days; some products also have a permanent tier, some have none, and it unpins automatically on expiry). When a burn-after-reading message is pinned, it unpins automatically on expiry and a prompt is needed. No duration concept at the protocol layer. Recommended: A. Rationale: timed pins are not introduced in the first release, reducing states; introduce B if chats have disappearing messages. | Level: Default-OK
- **[ACT-24] Favorites form**: Option A: personal favorites folder (separate entry, categorizable, searchable) / Option B: chat with oneself (forwarding to oneself is favoriting) / Option C: star only (mark in place, no copy). Recommended: B. Rationale: reuses chat capabilities, multi-device sync holds naturally, easy to implement with low user learning cost. | Level: Default-OK
- **[ACT-25] Entry for reporting a single message**: Option A: "Report" in the long-press menu, with selectable reasons and that message attached (reports by event at the protocol layer) / Option B: report only in the chat or profile page, allowing the user to tick recent messages (one product attaches the most recent several messages when reporting on leaving a group). Recommended: A. Rationale: user understanding, what you see is what you report; whether to also offer B is decided separately in module 09. | Level: Default-OK
- **[ACT-26] Short-term undo after "delete for self only"**: Option A: delete permanently right after confirmation, no undo / Option B: after deleting give a seconds-level "Undo" window, permanently deleted on timeout, and the deletion result syncs to all online devices. Recommended: A. Rationale: the second confirmation (see ACT-09) already guards against accidental deletion, and only a few products offer an undo window, so it is not a default. | Level: Default-OK
- **[ACT-27] Spread limits for multiple forwards**: Option A: do not mark the forward count / Option B: once the forward chain reaches a single-digit count, mark "Forwarded many times", and a message of this kind can only be forwarded to 1 chat at a time; the forward count is invisible to the server under end-to-end encryption. Recommended: A. Rationale: only one product uses it and it depends on forward-chain counting, there is no large-scale spread scenario in the first release, introduce B if spread problems appear. | Level: Default-OK

## Must-ask states (module-specific, supplements the general state matrix)
- Original message missing: quote block copy and tap destination when the quoted original has been unsent, deleted, expired, is beyond the loaded range, or the other party has deleted their account.
- Receiver at unsend time: how each of these displays: the other party offline, the other party's client version too old or sync failed (whether I am told when the unsend has not taken effect), the other party has blocked me, the other party has deleted their account, the other party unsends after reading.
- Unsend presentation and promises: when the receiver is viewing an image or video full screen, playing voice or previewing a file and the message is unsent, close or stop immediately and prompt; unsend confirmation and help copy must not promise "the other party definitely cannot see it" (low versions, unconfirmed encrypted chats, notifications already displayed, and screenshots may all retain it); write the edit time limit into "Defaulted to recommendation" and note that the server can configure it.
- Disappearing messages and quotes: after a disappearing message expires, whether the original text is still visible in replies that quote it; how the quoted placeholder displays after unsend.
- Unsend multi-device: another device has read, unsent or deleted the same message; the time limit expires mid-unsend; the unsend request times out on a weak network.
- Unsend linkage: the consequences when the unsent message has been quoted, forwarded, favorited, pinned, reacted to by others, or set as an announcement.
- Group vs one-on-one differences: whether the unsend time limit, admin unsend and unsend placeholder copy are consistent in groups and one-on-one; whether group members can see the handler and reason when an admin unsends.
- Editing state: the original message is unsent during editing; whether the other party gets a new notification and read receipts are reset after editing; whether already forwarded copies and existing quote blocks sync after editing; two devices editing at the same time; entering edit near the time limit and then submitting.
- Changes during multi-select: a selected message is unsent by the other party or deleted, the chat is cleared; the selection includes non-operable types; the selected count reaches the limit.
- Reactions: the original message is unsent after reacting; whether removing a reaction notifies; how reactions are handled when a disappearing message vanishes; the reactor leaves the group or is removed; whether a blocked user's reaction is shown; aggregation basis for the reactor list and notifications.
- Pin: a pinned message is unsent or expires; the pinner's permission is revoked; pinning on multiple devices at once; concurrent pinning when full.
- Forward: the source user has deleted their account or hidden the source; forwarded media has expired; the target is a group the user has left or a blocked contact; the original message is unsent after forwarding.
- Reply entry conditions: whether the reply entry is hidden or disabled when the message is sending, failed to send, unsent, the sender is blocked, or a non-admin is in an admins-only-can-speak group.
- Copy and restricted content: the copyable scope of a whole message, selected text, media and code blocks; how the copy entry is handled for protected content.

## Anti-patterns
| Vague/incorrect | Correct | Reason |
|---|---|---|
| "Messages can be unsent" | State who can unsend, the time limit, timeout copy, placeholder copy for both sides after unsend, failure and partial failure copy | Unsend involves three kinds of branches (object, time, network), and vague writing leaves developers to fill in on their own |
| "The message disappears after unsend" | After unsend, replace it in place with a placeholder, and existing quote blocks, forward entry and download entry change in sync | Disappearing directly breaks the chat flow and leaves quote blocks dangling |
| Quote block written only for when the original exists | Also write quote block copy for the original unsent, deleted and nonexistent | The missing state is a frequent boundary of quoting |
| "Delete" without distinguishing scope | "Delete for self only" and "unsend for everyone" get separate entries and separate confirmation copy | Users will think the other party's copy is deleted too |
| Multi-select written as only an entry | State the count limit, handling of non-forwardable items in a mixed selection, and a message being unsent mid-selection | Multi-select is the scenario with the most varied states |
| Pin written as only a "Pin" button | State the count limit, policy when full, who can pin, whether to notify, handling after unsend | Pins are shared state in the group, so permissions and impact must be defined |
| Forwarding erases the source outright | Define the source mark and the privacy switch as a pair | Erasing the source breaks data integrity and may evade reports |
| Editing without an "edited" mark | An edited message must carry the mark, and history visibility is defined separately | The other party cannot tell the content was changed |

## Calibration sample
Easiest to write vaguely: unsend for everyone. After tapping there are only two preconditions, "has it timed out" and "is there network", so no decision chain is used. The unsend time limit, placeholder copy and downstream entries are written as body text per recommendation; the values in the card are illustrative, actual values are set by the business and listed one by one under "Defaulted to recommendation" in the delivery draft; whether already forwarded copies and content the other party downloaded or favorited are cleared with the unsend, and whether the unsender is told when it has not taken effect on the other party's side, fall in the data deletion scope, are must-ask, and are left as placeholders in the card.

Description:
1. Long-press a message the user sent successfully less than 24 hours ago, and the menu shows "Unsend for everyone"; after 24 hours it is not shown, one-on-one and group chats share the same time limit
2. If the time limit is exceeded just while the menu is open, tapping "Unsend for everyone": Toast: "More than 24 hours have passed, cannot unsend", the message stays unchanged
3. Tapping "Unsend for everyone" with no network: Toast: "Network unavailable. Check your network and try again"; unsend request fails: Toast: "Network error, unsend failed. Please try again"; in both cases the message stays unchanged
4. After a successful unsend, the user's own side replaces it in place with "You unsent a message", and the other side replaces it in place with "{nickname} unsent a message"; when the other party is offline it syncs to the placeholder once they come online
5. After unsend the message can no longer be forwarded, and the download and favorite entries disappear in sync; a reply that quoted the message shows "The original message was unsent" in the quote block, and tapping the quote block does not jump; a pinned message is unpinned at the same time when unsent
