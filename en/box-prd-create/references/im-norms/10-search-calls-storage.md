# Search, voice and video calls, storage and sync, other general topics

> Applies when: PRD requirements for global and in-chat search, voice and video calls (including call records, incoming calls, multi-party calls, screen sharing, call links, picture-in-picture, call recording), cloud and local history with multi-device sync, backup and migration, storage cleanup, link previews, draft sync, and stickers and emoji. Evidence is in evidence/10-search-calls-storage.md.

## Baseline (follow by default, high confidence)
- **[MISC-01] Global search sections**: Results are sectioned by type (contacts and chats, groups, message history, etc.), each section with a title; an exact lookup by account identifier can find people not yet added. Must define: ordering within each section, default count and whether it can expand to show more; how the other party's privacy settings affect whether they can be found; whether deleted contacts are shown; the prompt when the account identifier format is invalid; whether ad entries in the chat list enter search results: see ADS-07. | Magnitude: — | Confidence: High
- **[MISC-02] In-chat search**: Users can search by keyword within the current chat. Must define: whether group chats support filtering by sender, whether jump-to-date is offered (see MISC-24); where a tapped result lands; how the result total or "n of m" is shown; whether unsent, deleted and expired messages can be found. | Magnitude: — | Confidence: High
- **[MISC-04] Call record trace**: When each call ends, leave a record in the chat that distinguishes the outcome: connected, declined, canceled, not connected; caller and callee see different copy. Must define: whether not connected is subdivided into missed, no answer, busy (see MISC-25); whether connected shows the duration; each side's copy for every outcome; whether it counts toward unread; whether tapping calls back. | Magnitude: — | Confidence: High
- **[MISC-07] Call gate**: When the other party has set a call restriction against this user, a call cannot be started and the caller gets an unable-to-call prompt. Must define: which situations count as a restriction (the other party has blocked, the other party's privacy setting disallows it, the other party has not accepted the message request, etc.); the prompt copy for each situation; whether the reason is disclosed (see MISC-26). | Magnitude: — | Confidence: High
- **[MISC-08] Participant limit and full prompt**: Calls have a participant limit; when full, joining fails with a clear prompt. Must define: limit {N}; whether the limit is the same across clients (mobile, desktop, web); whether a one-on-one call can be upgraded to multi-party and the limit that applies after upgrade; how participants are chosen when starting a call in a group whose member count exceeds the limit; the full-prompt copy. | Magnitude: a dozen or so to two hundred, with caliber varying by product | Confidence: High
- **[MISC-11] Multi-device sync**: When several devices of the same account are online, new messages sync to all devices in real time. Must define: whether read state, deletion and chat state (pin, mute, archive, etc.) sync and when; who wins on conflict (recommended: for toggle states such as pin and mute, the last operation received by the server wins; for one-time items such as contact requests and group invitations, whoever handles it first takes effect, and the device that arrives later shows "Already handled on another device", see ACC-12; never write it as the later operation being silently discarded); the explanation when history may be missing on a newly linked device. | Magnitude: — | Confidence: High
- **[MISC-13] Low-storage prompt**: When storage space is low, show a prompt, and pause or block download, backup and migration tasks until space is cleared and retried. Must define: whether there are levels and the threshold and copy of each; how paused tasks resume. | Magnitude: at least one level of prompt | Confidence: High
- **[MISC-14] Backup is a copy**: Backup does not remove data from the source device. Must define: whether migration is a copy (merge on both sides) or a move; whether the required space is estimated before running and the estimate copy; whether messages arriving during migration are included (see Must-ask states); when restoring a backup, how messages deleted or expired after the backup are handled. | Magnitude: — | Confidence: High
- **[MISC-16] Limit on saved items**: Saved emoji, stickers and GIFs have a count limit, and a prompt is shown when it is reached. Must define: each limit; the handling when reached (prompt to delete first, automatically replace the oldest, or guide to a paid tier) and the prompt copy; saved items exceeding the free limit after a paid tier expires: see PTS-25. | Magnitude: single digits to hundreds | Confidence: High
- **[MISC-17] Fallback for unsupported types**: Message types this version cannot recognize show fallback copy, and the chat-list summary likewise shows a fallback placeholder; never show blank or garbled text. Must define: the fallback copy (whether the list and the chat page use the same copy); whether to guide an upgrade and the upgrade entry. | Magnitude: — | Confidence: High
- **[MISC-33] An ongoing group call can be joined midway**: When a group has an ongoing call, the chat shows a status prompt with a "Join" entry, and members can join midway; when full, handle per MISC-08. Must define: the status prompt content (whether it includes participant count and duration) and entry copy; the entry's state for someone removed from the group; whether the incoming-call screen offers "Ignore"; how participants are displayed after joining. | Magnitude: — | Confidence: High
- **[MISC-36] State the network cause when the user's own network prevents a call**: When the user's own network is unavailable and a call cannot be started or established, the prompt states that it is a network cause and guides checking the network, rather than substituting a result such as "no answer" or "the other party is busy". Must define: whether a no-network condition detected before starting is blocked directly without entering the calling screen; prompt copy and carrier; whether a call record is left in the chat; reconnect and hang-up when the network drops during a call: see the must-ask state "Weak-network call". | Magnitude: n/a | Confidence: High

## Conventions (default-OK, mark as suggested)

- **[MISC-03] Search history**: Keep recent searches, which can be cleared as a whole. Must define: the number retained; whether single entries can be removed; whether clearing needs a second confirmation; whether it is cleared on logout. | Magnitude: not evidenced this round, value set by the PRD | Confidence: Medium (direct evidence from two products; single-entry removal and clear confirmation have evidence from only one product, so they appear only under must define)
- **[MISC-05] Incoming-call ring timeout**: An incoming-call ring has a timeout; after it, the caller side records "no answer" and the callee side records "missed". Must define: timeout duration {N} seconds and whether the server can adjust it; the callee-side notification and record after the timeout. | Magnitude: no value obtained this round, set by the PRD | Confidence: Medium (the timeout mechanism has direct evidence from two products; caller recording no answer and callee recording missed each from two products; the value is not evidenced)
- **[MISC-06] Calls are mutually exclusive**: When another call comes in or a new call is to be started during a call, they do not run in parallel; the current call ends and the new call is answered or started only after explicit user confirmation. Must define: confirmation dialog copy and options; what the caller sees when the callee has not confirmed; the prompt form for a second incoming call: see MISC-44. | Magnitude: — | Confidence: Medium (direct evidence from only two products)
- **[MISC-09] In-call status prompts**: During a call, states such as a poor network on the other end are shown as prompts. Must define: which states are prompted (other party muted, camera off, poor network, low battery) and the copy and carrier; whether a call can be started when the user's own network is unavailable (see MISC-36); whether to downgrade automatically on a weak network. | Magnitude: — | Confidence: Medium (direct evidence from two products; other party muted, camera off, and own no-network blocking a call each have evidence from only one product, so they appear only under must define)
- **[MISC-10] Missing permissions and devices**: When a call is started or answered without the necessary conditions, give guidance or a prompt, never fail silently. Must define: which missing conditions need a prompt (microphone or camera permission, no camera device, etc.); the prompt copy and destination for each (system settings, switch to voice); the general wording for a denied permission and the entry to settings: see DISC-02. | Magnitude: — | Confidence: Medium (direct evidence from two products, one each for permission missing and device missing)
- **[MISC-15] Draft retention**: See UI-31 (draft save, restore, clear timing and overwrite confirmation are defined only there); cross-device sync: see MISC-32, chat-list draft indicator: see LIST-05.
- **[MISC-12] Clearing cache and deleting records are two different things**: Clearing media cache and deleting chat history are different operations; before deleting chat history, state that it cannot be recovered after deletion. Must define: the dimensions for showing storage usage (by category, by chat); the cleanup entry and confirmation copy; whether media can be downloaded again after clearing cache (see Must-ask states); whether deleted records can still be recovered from backup, as an explanation. | Magnitude: — | Confidence: Medium (cache and records being separate has direct evidence from only two products; the cannot-recover prompt from three)
- **[MISC-37] Calling-stage status**: The caller side shows call status by stage, distinguishing at least "Calling", "Ringing" and "Connecting". Must define: copy for each stage; copy for "Joining", "Reconnecting" and "Waiting to be allowed in" (if approval exists) in group calls; the prompt when the other party's version is too old to support calls or video. | Magnitude: n/a | Confidence: Medium (direct evidence from two products)
- **[MISC-38] Conditions for starting screen sharing**: Only one person shares the screen at a time in a call; when someone else is sharing, starting another requires confirming a replacement or is not allowed; sharing and the user's own camera feed are mutually exclusive or one yields; the prompt and settings entry when system screen-recording permission is missing: see DISC-02. Must define: entry location (call controls or "More"); whether one-on-one and group calls both support it, and whether it is available only in video calls; whether the whole screen or a single window can be shared; who can share in a group call; the status prompt and way to stop while sharing; how the user views it when the other party shares; the prompt on a sharing error. | Magnitude: n/a | Confidence: Medium (each clause has direct evidence from two products)
- **[MISC-39] Prompt when a device disconnects or is unavailable during a call**: When the camera or microphone disconnects, becomes unavailable or is not detected during a call, the prompt names the specific device and cause and gives a way out (switch device, switch to voice, move to the phone and continue, go to settings). Missing permissions and devices at start or answer: see MISC-10. Must define: copy and way out for each situation; the prompt when a device is occupied by another app; whether to ask about switching when a new device is connected; whether the original state is restored automatically once the device recovers. | Magnitude: n/a | Confidence: Medium (direct evidence from two products)
- **[MISC-40] Call-link companions (if offered)**: Whether to offer call links: see MISC-34; if offered, it must also have an approval-to-join toggle, the creator's ability to remove or block participants, and an expiry period counted from long disuse. Must define: default of the approval toggle and waiting-room copy; the prompt after being rejected or removed and whether they can apply again; the expiry period value and copy after expiry; whether the creator can delete the link and how a call in progress is handled when it is deleted; to whom a joiner's profile (name, avatar, number) is shown, which concerns what the other party can perceive and is treated as must-ask. | Magnitude: expiry after a few dozen days unused | Confidence: Medium (direct evidence from two products)

## Divergences (ask Box on must-ask; write default-OK per recommendation and list it)
- **[MISC-20] History storage model**: Option A: the server stores full history, a new device pulls it on login, and cloud search is possible / Option B: stored only on the device, with the server temporarily holding only undelivered messages (on the order of a few dozen days), a new device has no history by default and must transfer from the old device / Option C: device-first, with the user actively backing up or migrating to a new device (copy and merge). Background: three products use the device-first model, two use full cloud. Recommended: C. Rationale: privacy and data integrity: the server does not hold plaintext history, while a recovery path is kept; if ZYMIX's server can read plaintext, option A is viable. | Level: Must-ask
- **[MISC-21] History scope on a new device** (depends on B or C of MISC-20): Option A: no history / Option B: at login the user can tick to import a recent period / Option C: full migration. Background: importing a recent period at login is supported by two products. Recommended: B. Rationale: user understanding: it cuts first-migration time and space use while still offering an optional way to recover. | Level: Default-OK
- **[MISC-22] Automatic cleanup**: Option A: no data is cleaned automatically / Option B: media cache is cleaned automatically by retention period (provided it can be re-downloaded from cloud or backup), and chat history is not cleaned automatically / Option C: chat history can also be trimmed permanently by retention period (on the order of 30 days to a year, or permanent) or by per-chat message count. Recommended: B. Rationale: privacy and data integrity: automatic deletion of chat history is irrecoverable and should be initiated explicitly by the user; cleanup under option C may also sync to other devices. | Level: Must-ask
- **[MISC-23] Chat content search scope**: Option A: only the history already on the device (including on-device recognition of text in images, which the user must turn on) / Option B: full cloud search. Background: on-device search in three products, cloud search in one; the on-device search index must be rebuilt after restoring a backup. Recommended: A. Rationale: privacy and data integrity: linked with MISC-20; when the server does not hold plaintext, search is not possible there. | Level: Default-OK
- **[MISC-24] Search filter dimensions**: Option A: keyword plus sender / Option B: add content type (image, video, file, link, voice) / Option C: add date and chat type. Background: content type, date and sender filters are each supported by two products. Recommended: B. Rationale: user understanding: content type is a commonly used way to narrow results. | Level: Default-OK
- **[MISC-25] Busy presentation**: Option A: the caller sees "The other party is busy" / Option B: the caller sees the same result as no answer, and the callee side records "Missed (busy)". Recommended: B. Rationale: privacy: does not expose the callee's call status to the caller; it is the opposite of the only evidenced product's approach (A), so this is a privacy trade-off. | Level: Must-ask
- **[MISC-26] Whether to disclose the reason when a call is restricted**: Option A: disclose (for example "The other party's privacy settings do not allow it") / Option B: a generic cannot-call prompt that does not distinguish a block from a privacy restriction. Recommended: B. Rationale: privacy: prevents the caller from using it to learn whether they are blocked; it is the opposite of the two evidenced products (which disclose the restriction reason), so this is a privacy trade-off. | Level: Must-ask
- **[MISC-27] Ringing when a call starts in a large group**: Option A: ring everyone / Option B: when the member count exceeds a threshold (on the order of a dozen or so), do not ring members, show only an in-chat status message, and members can join on their own (join entry: see MISC-33). Recommended: B. Rationale: user understanding: avoids a large-group call turning into harassment of everyone. | Level: Default-OK
- **[MISC-28] Switching devices during a call**: Only one product has direct evidence this round (low confidence). Option A: cross-device transfer not supported, hang up and redial / Option B: switch audio output and camera within the same device / Option C: cross-device call transfer. Recommended: A plus B. Rationale: privacy: cross-device transfer involves the risk of migrating session keys, and only one product has evidence; same-device switching is covered by system capabilities. | Level: Default-OK
- **[MISC-29] Upgrading a one-on-one call to multi-party**: Option A: not supported / Option B: others can be invited during a call, and the multi-party limit applies after upgrade (see MISC-08). Recommended: B. Rationale: user understanding: both products with direct evidence support it, and no counterexample was seen. | Level: Default-OK
- **[MISC-30] Data export cooldown**: Option A: no cooldown, download anytime / Option B: a cooldown period after the request (on the order of a few hours), with a reminder pushed to all devices, and cancellable during it. Recommended: B. Rationale: privacy: prevents bulk export when someone briefly holds a logged-in device. | Level: Default-OK
- **[MISC-31] Link preview default and turning it off**: Option A: generated by default, and users can turn it off globally in privacy settings (evidence for removing a single preview before sending is low) / Option B: not generated by default in private or encrypted chats, and the user must turn it on / Option C: group permissions can separately forbid members from sending links with previews. Whether the preview is fetched by the sender or the server: see RICH-57. Recommended: B. Rationale: privacy: generating a preview gives the generating party the link; option C can be layered onto group permissions (see 07-groups-channels.md). | Level: Must-ask
- **[MISC-32] Cross-device draft sync**: Option A: saved on the device only / Option B: cloud sync, cleared after sending, with a one-tap clear for all cloud drafts. Recommended: A. Rationale: privacy: an unsent draft is private content and should not be uploaded to the server first; mainstream products differ (one product syncs to the cloud, the rest not evidenced); the recommended option does not upload unsent content, which is conservative, and can be defaulted and then listed under "Defaulted to recommendation". | Level: Default-OK
- **[MISC-34] Call links and guests**: Option A: not supported, calls are limited to in-account members / Option B: call links are supported, a link holder joins as a guest, a guest can do voice, video and screen sharing but cannot add or remove people or send messages; if all in-account members leave while a guest is waiting, the call ends. Recommended: A. Rationale: privacy and data integrity: letting someone without an account into a call involves identity verification and harassment surface; it is the opposite of the two evidenced products (both support call links, one at medium confidence), so this is a privacy trade-off. Approval, removal and expiry when call links are offered: see MISC-40. | Level: Default-OK
- **[MISC-35] Upgrading a group voice call to video**: Option A: a group voice call cannot be upgraded directly to video and must be restarted after it ends / Option B: members in a group voice call can each turn on their camera. Recommended: A. Rationale: privacy: avoids being pulled passively into a video scenario mid-call; only one product has evidence (medium confidence, covering only group voice calls). Switching to video in a one-on-one call is out of scope for this entry and is not evidenced in this library; if needed, raise it with Box as an open item. | Level: Default-OK
- **[MISC-41] Call quality feedback**: Option A: not collected / Option B: a sampled rating pops up after a call ends, with an optional problem description and a "Not now" choice / Option C: an issue-category feedback entry (audio, video, dropped) during or after the call. Recommended: B. Rationale: recoverable: leaves a basis for diagnosing weak-network and device problems, and being sampled and skippable keeps interruption low. Background: one product each for B and C. | Level: Default-OK
- **[MISC-42] Privacy notice before screen sharing**: Option A: before sharing starts, warn that notifications, passwords and other content on screen will be seen by participants, and when the other party is not a contact, add "Only share with people you trust" / Option B: no notice. Recommended: A. Rationale: privacy: shared images cannot be taken back. Background: only one product has evidence (from a search summary). | Level: Default-OK
- **[MISC-43] Muting others in a group call**: Option A: not supported / Option B: a participant can mute others, the muted person receives "{nickname} muted you", and can only unmute themselves and cannot be unmuted by others. Recommended: B. Rationale: recoverable: the muted person can recover at any time on their own, used to deal with noise in group calls. Background: only one product supports it. | Level: Default-OK
- **[MISC-44] Prompt for a second incoming call during a call**: Option A: do not interrupt the current call, show a banner for the new call, with a choice of "End and answer" or "Decline" / Option B: handle it directly as busy, and the callee only gets a missed-call record. Whether the current call ends after answering: see MISC-06; what the caller sees: see MISC-25. Recommended: A. Rationale: user understanding: the callee can judge which call matters more. Background: two products prompt a new incoming call (one from a search summary), and one returns busy to the caller directly. | Level: Default-OK
- **[MISC-45] System call UI**: Option A: on mobile, integrate with the system call UI (full-screen incoming call on the lock screen, with mutual exclusion against system phone calls handled by the system) / Option B: use only the in-app incoming-call UI plus push. Recommended: A. Rationale: user understanding: lock-screen calls match system phone calls, with fewer missed calls. Whether to write into the system's recent-calls log is a privacy default and is treated as must-ask; whether integration is allowed in a launch region is not evidenced and is confirmed per launch region. Background: only one product has evidence (confirmed integrated). | Level: Default-OK
- **[MISC-46] Picture-in-picture for video calls**: Option A: when switching to another page or another app during a video call, it shrinks automatically into picture-in-picture / Option B: it shrinks only into an in-app floating window, and after leaving the app only audio is kept / Option C: not supported. Recommended: A. Rationale: user understanding: during a call people often need to check chats or other apps; when the system does not allow picture-in-picture, handle as B. Background: only one product has evidence (from a search summary). | Level: Default-OK
- **[MISC-47] Call recording**: Option A: not provided / Option B: provided, with confirmation before starting, a recording indicator visible to all participants while recording, and the file saved only with the initiator. Recommended: A. Rationale: privacy: recording others' voices requires everyone's awareness, and platform rules require explicit consent and a clear prompt; only one product offers recording in group voice calls, and another explicitly does not record. | Level: Must-ask

## Must-ask states (specific to this module, supplements the general state matrix)
- Other party blocked or deleted account: whether a call can be started; whether the call-record system message is kept; how that contact is displayed in search results.
- Left the group, removed from the group, or group dissolved: whether the call is interrupted when someone in a group call is removed; whether messages from before leaving can still be found by in-chat search after leaving the group.
- Multi-device: when another device has answered an incoming call, whether this device stops ringing and records "Answered on another device" or records it as missed; search results after another device has cleared cache or deleted messages.
- Offline callee: what the caller sees when the incoming-call push is delayed or fails; when calls missed while offline are recorded after coming online.
- Weak-network call: when to prompt, when to downgrade to voice, when to hang up automatically; whether the timer is continuous after reconnecting.
- Permission revoked during a call: the prompt when the microphone or camera is turned off by the system, and whether to mute automatically.
- The message behind a search result has been unsent, deleted or expired: whether the result disappears; where a tap lands.
- During migration or backup: behavior and recovery for newly arriving messages, network interruption, moving to the background, space exhaustion, and mutual exclusion with other tasks.
- After a backup restore: whether messages deleted, unsent or expired since the backup reappear; whether to prompt when search results are incomplete while the on-device search index is being rebuilt.
- Linked or new device: what explanation the user sees when history is more incomplete than on the phone; whether deleting and clearing sync to all online devices.
- Ongoing group call: the state of the "Join" entry when full, when removed from the group, or when blocked; guests waiting while all in-account members leave (if B of MISC-34 is chosen).
- Tapping media that has been cleared after clearing cache: whether it can be downloaded again; the prompt when it has expired in the cloud.
- Link preview fetch fails, times out, or the link is invalid: the message can still be sent and shows no preview; whether the preview is kept when forwarding or quoting.
- The message a draft quotes has been unsent or deleted: whether the draft is kept and how the quote card is displayed.
- Messages with specific content (stickers, polls, contact cards, payments): whether the limits on edit, forward and unsend are spelled out item by item (for payments see PAY-07).
- Group vs. one-on-one differences: whether the call participant limit, ring rules and call-record copy are defined separately.
- During screen sharing: the sharer loses network, moves to the background, is interrupted by an incoming call, or is removed from the group; someone joins during sharing; system screen-recording permission is revoked during sharing.
- Receiving a system phone call during a call: whether the in-app call is kept, put on hold or ended after answering; the prompt when the microphone is muted by the system in the background or on the lock screen.
- Call links (if offered): the link has expired or been deleted, the creator is not in the call, the call has ended while waiting, applying again after being rejected.

## Anti-patterns
| Vague or wrong | Correct | Reason |
|---|---|---|
| "Supports searching chat history" | State the search scope (device or cloud), sections, filter dimensions, handling of unsent and deleted messages, and where a tap lands | Unclear scope conflicts with the history storage model |
| "Show a call record after the call ends" | By outcome (connected, missed, declined, canceled, no answer, busy), state both sides' copy, whether to call back, and whether it counts as unread | Per-side copy is missing |
| "Auto hang up when a call rings too long" | State the timeout in seconds and both sides' record and notification after timeout | Value and destination are missing |
| "A new call comes in during a call" | State the confirmation dialog copy, options, and what the caller sees when unconfirmed | Concurrent-call handling is missing |
| "Supports multi-party calls" | State the participant limit, full prompt, upgrade path and ring rules | Limit and large-group harassment are undefined |
| "Supports backup and migration" | State copy or move, space estimate, messages arriving during the run, account ownership check, and interruption recovery | Data integrity and recovery path are missing |
| "Clear storage" | Distinguish cache from records, and state the consequence copy and whether it is recoverable | Irrecoverable content gets deleted by mistake |
| "Links automatically show a preview" | State the default state, who generates it, the failure state, and the turn-off entry | Privacy leak and missing failure state |
| "Drafts auto-save" | State save timing, clear conditions, whether it is cross-device, and overwrite confirmation | Drafts linger or get lost |
| "Supports screen sharing" | State the number of simultaneous sharers, the relation to the camera, guidance for missing permission, how to stop, and the pre-share notice | Sharing eligibility and privacy notice are missing |
| "Show network status during a call" | Distinguish own side from the other side, and state per-stage copy and the result when the user's own network drops | Users cannot tell which side the problem is on |

## Calibration sample
The feature most easily written vaguely: the "Answer" button on the incoming-call screen. This example has no must-ask items: the prompt when another device has already answered, the ring timeout duration, and falling back to voice when camera permission is missing are all written into the body per recommendation; the values in the card are illustrative and the actual values are set by the business, and each is listed one by one under "Defaulted to recommendation" in the delivery draft.

Description:
1. While an incoming call rings, the "Answer" button lights up
2. On tap, check in order:
   a. 1-Incoming call status check: can this call still be answered
      i. Caller canceled: the incoming-call screen closes, toast: "The other party canceled", flow ends
      i. Another device of this account has answered: this device stops ringing, the incoming-call screen closes, toast: "Answered on another device", this device's call record is set to "Answered on another device", flow ends
      i. Still answerable: go to the next check
   a. 2-Microphone permission check: is microphone permission granted on this device
      i. Not granted: dialog: "Microphone permission is required to make calls", buttons "Go to Settings" and "Cancel"; tap "Go to Settings": open system settings; tap "Cancel": the dialog closes and returns to the incoming-call screen
      i. Granted: go to the next check
   a. 3-Camera permission check: for a video call, is camera permission granted on this device
      i. Not granted: dialog: "Camera access is off. You can answer with voice first", buttons "Answer with voice" and "Go to Settings"; tap "Answer with voice": go to the next check, and after connecting the user's own camera stays off; tap "Go to Settings": open system settings
      i. Granted, or it is a voice call: go to the next check
   a. 4-In-call check: is this device already in a call
      i. Yes: dialog: "Answering the new call will end your current call", buttons "Answer" and "Cancel"; tap "Answer": end the current call and connect the new one, and other devices of this account stop ringing; tap "Cancel": the dialog closes and returns to the incoming-call screen
      i. No: connect the call, and other devices of this account stop ringing
3. Ring timeout: if the ring reaches 60 seconds without an answer, the incoming-call screen closes, this device records "Missed", and the caller side records "No answer"
