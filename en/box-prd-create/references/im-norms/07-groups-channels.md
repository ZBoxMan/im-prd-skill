# Groups and channels (types, member limits, role permissions, invites and joining, mentions, muting, leaving, dissolving, transferring)

> Applies when: read this file when the PRD involves creating a group chat or channel, member limits, roles and permissions, invites and join approval, @mentions, group announcements, muting, slow mode, removal, leaving, dissolving, transferring ownership, or editing group profile. Evidence is in evidence/07-groups-channels.md.

## Baseline (follow by default, high confidence)
- **[GRP-01] Member limit with a prompt near the limit**: A group has a member limit; show a clear prompt when it is near or reached, never fail silently. Must define: limit value, near-limit prompt threshold and copy, copy at the limit, and the unified behavior of every entry point (add members, link, approval) once the limit is reached. | Magnitude: regular groups roughly hundreds to thousands of members; special forms (read-only broadcast) can reach six figures | Confidence: High
- **[GRP-02] Admin-only posting mode**: Support setting a group to "only the owner and admins can post" (including mute-all, or announcement-style groups where only admins can publish); show members an explanation that they cannot post. Must define: toggle entry and who can use it, explanation copy and placement on the member side, whether the reply and forward entries are hidden, what members can still do (react, vote, view, contact an admin), and whether toggling leaves a system message in the chat flow. | Magnitude: n/a | Confidence: High
- **[GRP-03] Role tiers and admin appointment**: Distinguish at least admins from regular members; granting and revoking admin has a clear grantor; whether to add a single owner and how the owner's exit is handled: see GRP-11, GRP-28. Must define: whether there is an owner, whether the person appointed or revoked gets a prompt and its copy, whether the number of admins is capped and the value, confirmation copy for appointing and revoking, how admin actions in progress are handled when the admin is revoked, and what happens when the only admin leaves. | Magnitude: n/a | Confidence: High
- **[GRP-04] Admins cannot act above their rank**: An admin cannot act against the owner or against peers and higher-privilege roles (at minimum, removal). Must define: the list of actions subject to this limit (remove, mute, revoke), the scope of permissions that can be granted when promoting an admin, whether the entry for an out-of-rank action is hidden or disabled with a prompt, and the prompt copy. | Magnitude: n/a | Confidence: High
- **[GRP-05] Define the eligible role per permission item**: Group admin permissions are defined item by item, each stating "owner only / owner and admins / all members". Must define: the list of permission items (such as edit group profile, add members and invite, remove members, post and send media, pin and announce, manage invite links, approve new members, disappearing-message toggle) and their defaults, how member permissions and admin permissions overlap, and how operations in progress are handled after a permission change. | Magnitude: roughly 3 to 15 permission items | Confidence: High
- **[GRP-06] Adding members is configurable**: The owner or admins can restrict members from adding people. Must define: the restriction form (members cannot add at all / adding requires owner or admin confirmation), the default, and the entry behavior and copy on the member side when restricted. | Magnitude: n/a | Confidence: High
- **[GRP-07] Invite entries can expire**: Invite links and QR codes must have an expiry mechanism (expiration, revocation, reset, or a combination); after a reset or revocation the old link is permanently invalid. Must define: default validity period, copy after expiry (expired, revoked, group full, not allowed to join), second-confirmation copy before a reset, how the old link is handled after a reset, and the reminder and resend entry for pending invitations. | Magnitude: validity in days, or valid indefinitely | Confidence: High
- **[GRP-08] Join approval**: Provide "joining requires admin approval"; a request has a status chain (applied, approved, rejected); the approver, the status chain and the request validity period are defined only in this entry; the toggle form is in GRP-19. Must define: who can approve, whether the applicant can view the status and withdraw the request, the request validity period, the notification the applicant receives after approval or rejection, handling when the group is full at approval time, the interval before re-applying after rejection, how a new request reaches approvers (recommended: at least one push, or a push aggregated per group; do not show it only in an in-group entry, or requests pile up and quietly expire), whether the applicant is notified when a request expires (recommended: notify), where pending requests go when the group is dissolved, and whether the join system message for an approved request names the approver (recommended: name them, for traceability). | Magnitude: n/a | Confidence: High
- **[GRP-09] Remove members**: The owner and admins can remove members; the removed person can no longer post or receive new messages; the above-rank limit is in GRP-04. Must define: whether there is a second confirmation and its copy, whether the removed person gets a prompt and its copy, whether history is still readable after removal, and the batch removal cap. | Magnitude: batch cap from single digits to low tens | Confidence: High
- **[GRP-10] Leave group**: After leaving, the person can no longer post; handling when the owner leaves is in GRP-28. Must define: whether there is a second confirmation and its copy, whether the chat stays read-only or is removed from the list after leaving, whether group resources such as group files and announcements remain accessible after leaving, reminders for unfinished items (to-dos, calls), blocking when funds are unsettled see PAY-26, and whether a "Report this group" entry is offered on leaving. | Magnitude: n/a | Confidence: High
- **[GRP-12] Group profile edit permissions and length**: Edit permissions for group name, avatar and description are tiered (owner only / owner and admins / all members). Must define: default permissions (linkage with member count: see GRP-32), character limits and counting basis (grapheme or character) for name and description, over-limit prompt, and whether special groups (verified groups) are locked from edits. | Magnitude: group name tens to one hundred characters, description a few hundred characters | Confidence: High
- **[GRP-13] @mention members**: Members can be mentioned in a group; the mentioned person gets a recognizable marker in the chat list and in notifications. Must define: the scope of the mention picker (all members / recent speakers only), and the condition for clearing the marker; whether a mention still notifies under mute and the default: see NOTI-20. | Magnitude: n/a | Confidence: High
- **[GRP-19] Join approval is a toggle**: Join approval is a group-level toggle; when off, applicants join directly; when on, every join request needs an admin decision (approve or reject). Approver, application status chain and validity period: see GRP-08. Must define: the toggle default and entry, whether batch handling is supported, whether enhanced forms (answer questions, auto-approve on conditions) are included, whether the request page shows the application source (link, added by a member, etc.), and whether an admin can contact the applicant before approving. | Magnitude: n/a | Confidence: High

## Conventions (default-OK, mark as suggested)

- **[GRP-11] Transfer ownership (for products with an owner)**: The owner can transfer to another member, with a second confirmation stating that the owner role is lost immediately after transfer. Must define: eligibility conditions for the recipient, whether special groups (paid, verified) cannot be transferred, confirmation copy, acceptance on the recipient's side or automatic effect, and whether extra identity verification is needed (a transfer is irrevocable, and one product requires two-step verification; if not verifying, state the reason under "Defaulted to recommendation"). | Magnitude: n/a | Confidence: Medium (only three products have an owner, and confirmation and explanation copy is evidenced by only two products)
- **[GRP-14] Dissolve group**: Only the owner can dissolve, with a second confirmation stating it cannot be undone; after dissolving, all members get a prompt, and the chat becomes read-only or is removed. Must define: confirmation copy, all-member prompt copy, what happens to group files and history after dissolving, and whether special groups (enterprise, paid, verified) cannot be dissolved. | Magnitude: n/a | Confidence: Medium (owner dissolving has direct evidence from only two products)
- **[GRP-20] New-member history visibility is a group-level setting**: Whether new members can see messages from before they joined is configured by admins at the group level. Must define: setting entry and permission, available tiers, default (see GRP-30), whether a setting change applies retroactively to members already in, the prompt copy after a change, and the in-chat prompt when history is not visible. | Magnitude: n/a | Confidence: Medium (direct evidence from two products plus corroboration from specs)
- **[GRP-25] A removed member cannot rejoin on their own**: A member removed by an admin cannot rejoin by themselves through an invite link; the admin must first lift the restriction or invite them again before they can be restored. Must define: copy when a removed person uses a link again, the entry and permission for lifting the restriction, whether to offer two separate actions "Remove" and "Remove and ban", and the ban duration. | Magnitude: n/a | Confidence: Medium (direct evidence from two products plus corroboration from specs)
- **[GRP-31] Rate limits on adding members and applying**: Adding many people, creating groups or applying to join in a short time triggers a rate limit; when triggered, show a clear prompt stating when it recovers, never fail silently. Must define: trigger thresholds (may be undisclosed), cooldown duration, prompt copy, and the unified behavior of every entry point (add members, create group, apply) during the cooldown. | Magnitude: cooldown from hours to days | Confidence: Medium (direct evidence from two products plus corroboration from specs)

## Divergences (ask Box on must-ask; write default-OK per recommendation and list it)
- **[GRP-15] Group type system**: Option A: only one kind of group, tiered by member count / Option B: two levels, group and "supergroup" (large groups upgrade automatically, history is merged in display) / Option C: groups and channels coexist, with topics optionally on top (channel publishing identity and subscriber count: see FEED-10, subscriber list visibility: see FEED-30, comment area: see FEED-31, retention period and what new subscribers can see: see FEED-32). Whether to include the community form (several groups aggregated, including announcement groups where only admins publish) is discussed separately (group count and member limit: see FEED-14, exit semantics: see FEED-37). Recommended: A. Rationale: ZYMIX's existing rules center on a single kind of group; more types mean more states, so introduce channels only once there is a clear need. | Level: Must-ask | Framing: yes
- **[GRP-16] Member tiers and expansion**: Option A: a single fixed limit (around a thousand, raised by some products in recent years) / Option B: a soft limit (performance prompt when exceeded) plus a hard limit / Option C: tiers, with an upgrade prompt near the limit (including paid upgrade) / Option D: once full, the group can convert to a read-only broadcast group (one-way, irreversible). Recommended: B. Rationale: easy for users to understand (prompt first, restrict later) and recoverable, with no payment involved. If C is chosen with paid upgrade, see PTS-25 for groups whose size exceeds the free tier after membership expires. | Level: Default-OK
- **[GRP-17] Whether the invitee must consent first**: The rule that lets an invitee restrict direct adds via privacy settings: see REL-11 (baseline; no option below may bypass it); this entry only decides whether the invitee's consent is still required when direct adds are allowed. Option A: join directly when direct adds are allowed, and turn into a pending invitation to accept when the setting disallows it (pending invitations can be reminded or resent) / Option B: on top of A, always require the invitee's consent once group size exceeds a threshold / Option C: always require the invitee's consent. Recommended: A. Rationale: privacy: control is guaranteed by the invitee's privacy setting, while adding no step for acquaintances pulling each other into groups. | Level: Must-ask
- **[GRP-18] Invite link validity and use count**: Option A: valid indefinitely, relying on reset and disable (after a reset the old link is permanently invalid) / Option B: configurable validity period and use count, multiple links can be created and distinguished by creator / Option C: a QR code with a fixed short validity (days). Recommended: B. Rationale: recoverable and traceable; any single link can be revoked if abused. | Level: Default-OK
- **[GRP-21] @all members**: Option A: not provided / Option B: provided; in large groups only the owner and admins can use it (all members in small groups, with a member threshold of around a few dozen), with a daily count limit. Recommended: B. Rationale: group notices have a real reach need; limiting who can send and how often controls abuse. Whether recipients can turn off these reminders and whether they break through mute: see NOTI-21. | Level: Default-OK
- **[GRP-22] Group announcement and group description**: Option A: only a group description (a profile field; edits do not notify) / Option B: a standalone group announcement (publishing notifies everyone, can be pinned, can require members to confirm they have read it) coexisting with the group description. The announcement character limit and whether it is linked to unsend are discussed separately. Recommended: A. Rationale: fewer states, and notifying everyone can be handled by @all. | Level: Default-OK
- **[GRP-23] Mute an individual**: Option A: only mute-all is provided / Option B: also mute an individual, with selectable duration and a cap (within about 30 days, or permanent); admins cannot be muted, and whether newly joined members have a restriction period is discussed separately. Recommended: B. Rationale: dealing with a rule-breaking member affects fewer people than mute-all, and automatic recovery on expiry is recoverable. | Level: Default-OK
- **[GRP-24] Slow mode**: Option A: not provided / Option B: provided, with tiers from seconds to hours (for example 10 seconds, 30 seconds, 1 minute, 5 minutes, 15 minutes, 1 hour), admins unrestricted, and a countdown shown in the input area while active. Recommended: A. Rationale: there is no large-group flooding scenario in the first release; use mute as the fallback for now. | Level: Default-OK
- **[GRP-26] Whether to clear a removed member's messages**: Option A: do not clear / Option B: on removal, a checkbox "Also unsend their chat history" is available. Recommended: B. Rationale: users understand it directly when dealing with a spam sender, and the checkbox is off by default. When B is used, state: the unsend scope (all, or a recent period), whether a system message is left and who can see it, and whether deletion syncs across devices. | Level: Must-ask
- **[GRP-27] Whether leaving is announced to the group**: Option A: a one-line system message in the chat flow, no push / Option B: silent, not shown to members, with only admins seeing "{nickname} left", which cannot be turned off, and the leaver's profile kept in "Past members" for a few dozen days. Recommended: A. Rationale: users understand it, and group members need to know about membership changes; no push, to reduce exposure of the leaver. Note: from a privacy angle B is friendlier to the leaver; if Box prioritizes privacy, switch to B. | Level: Must-ask
- **[GRP-28] Owner leaving or ownerless handling**: Option A: the owner must transfer before leaving / Option B: the owner can leave directly, and the system designates a successor admin with an observation period (the owner can cancel by returning within it) / Option C: no owner concept, admins only / Option D: no owner concept; when the only admin leaves, the system immediately picks a random member to take over, and a re-joiner must be made admin again. Recommended: A. Rationale: recoverable and predictable, avoiding a group changing hands without anyone knowing; it is the opposite of what the evidenced products do (three known products take B, C and D respectively), so this is a predictability trade-off. | Level: Must-ask
- **[GRP-30] Default and tiers for new-member history visibility**: Option A: not visible by default from before joining / Option B: members see full history by default / Option C: not visible by default, admins can enable "only the most recent N messages" or backfill history for new members; tiers can also include "since invited" and "since joined". Recommended: C. Rationale: privacy and data integrity; old messages may contain content others do not want shown to new members; whether it is adjustable: see GRP-20. | Level: Must-ask
- **[GRP-32] Permission defaults vary with group size**: Option A: fixed defaults regardless of member count / Option B: in small groups (within a few dozen members) members can by default add people, edit group profile, send invite links and @all; once the member count exceeds a threshold (a few dozen to a few hundred), defaults tighten to admins only or owner only. Recommended: B. Rationale: abuse risk is higher in large groups; tightening by default protects members, and admins can still loosen it manually, so it is recoverable. | Level: Default-OK
- **[GRP-29] Whether changes to group profile, permissions and admins leave a system message**: Option A: changes to group name, avatar, description, permission toggles and admin appointments all leave a system message in the chat flow naming the actor / Option B: leave messages only for group name changes and admin appointments, with other changes shown only on the group profile page / Option C: no system messages; record only in a management log visible to admins. Recommended: A. Rationale: users understand it; members need to know about changes to group rules and admin identities. Background: A has direct evidence from only one product, and the other two are medium-confidence corroboration. If A is chosen, must define: the list of events that leave a trace, copy and subject for each event (you / {admin} / an admin of unknown identity), when the actor's identity is not shown, and whether it pushes; how member exits are traced: see GRP-27. | Level: Default-OK

## Must-ask states (specific to this module, supplements the general state matrix)
- Invitee state: deleted account, has blocked the inviter, privacy setting forbids being added to groups, already in the group, previously removed, previously left on their own; the result and copy of adding and of joining by link for each.
- Invite link: expired, revoked, reset, use count reached, group full, used by a removed person, used by someone already in the group; copy and destination for each.
- Approval concurrency: two admins approve and reject the same request at the same time; the applicant withdraws a request while it is being approved; the group is full at approval time.
- Member-limit boundaries: several people join at the same time when the group is exactly full; only some slots remain during a batch approval; adding members while the limit is being upgraded or converted.
- Permission revoked midway: an admin is revoked while editing group profile, approving a request or muting someone; who holds the permissions while an ownership transfer is in progress.
- Offline and multi-device: what a member sees on coming online after being removed, muted or the group being dissolved while offline; another device has already left the group or been removed.
- During mute: what restrictions apply to a muted member on reactions, forwarding, quoting, @, voice and media; typing in progress when the mute expires; whether an unexpired mute continues when the muted person leaves or is removed and then rejoins (recommended: continues, otherwise leaving and rejoining evades it).
- Owner account deleted or banned: how the owner role is handled, same question as GRP-28, not a separate question.
- Admin-only posting group: whether members keep the reply, reaction, pin and report entries; whether the admin side indicates the current mode.
- Mentions and notifications: the mentioned person has left, been muted, or set mute; the prompt when the @all count is used up.
- Leaving and dissolving: unfinished items exist before leaving; members are offline when the group is dissolved; whether history and files received are accessible after leaving.
- Group vs. one-on-one differences: whether the unsend, edit and forward rules in a group match one-on-one chat; how admin actions unique to groups are traced.
- Group profile: name and description too long, containing sensitive words, containing invisible characters; the final value when several people edit at once.
- New-member identity: the visibility to other members of a new member's nickname or account identifier when they join, and whether it can be hidden.
- Rate limits: the behavior of each entry point and the remaining-time prompt during the cooldown after the add-member, create-group or apply rate limit triggers.
- Only admin leaves: how succession works when no other admin exists and the prompt the new admin receives.

## Anti-patterns
| Vague or wrong | Correct | Reason |
|---|---|---|
| "Owner and admins can manage the group" | List permissions item by item and state who can use each: edit profile, add members, remove, mute, pin, announce, invite links | A vague line cannot tell what each role can do |
| "Member limit {N}" | Also write the near-limit prompt, copy at the limit, and the behavior of every entry (add members, link, approval) when full | A full group is a hotspot for concurrency and edge cases |
| "Can join via link" | Enumerate link states one by one: valid, expired, revoked, full, removed person, already in group | The link is the entry most prone to exception branches |
| "Admins can remove members" | State that the owner and peers cannot be removed, the confirmation copy, the prompt to the removed person, what happens to history, and whether they can rejoin | Overreach and later visibility are the core |
| Leaving written only as "leave group chat" | State the confirmation copy, the chat form after leaving, whether the group is notified, and owner-leaving handling | Owner and regular member leaving are entirely different branches |
| Muting written only as "mute {duration}" | State duration tiers and cap, who cannot be muted, what a muted person can and cannot do, and recovery and notification on expiry | Missing target boundaries cause overreach |
| Dissolving written as "delete group" | State owner only, the irreversible confirmation, the all-member prompt, the chat form, and that special groups cannot be dissolved | Dissolving affects every member and needs its own definition |
| Member permissions written as defaults only | How operations in progress wrap up when a permission is revoked | Permissions changing midway is a common state in groups |

## Calibration sample
The feature most easily written vaguely: joining a group chat through an invite link. The link's validity period and use count, and that a removed person cannot rejoin by link, are written into the body per recommendation and listed under "Defaulted to recommendation" in the delivery draft; whether new members can see messages from before they joined is a privacy default and is must-ask, so the card leaves a placeholder.

Description:
1. After the user opens the invite link, the "Join group chat" button lights up
2. On tap, check in order:
   a. 1-Removal restriction check: was the user ever removed by an admin of this group and not yet unrestricted
      i. Yes: dialog: "You were removed by an admin of this group and cannot join through a link", button "Got it", after closing return to the source page
      i. No: go to the next check
   a. 2-Link status check: is the link currently valid
      i. Expired: dialog: "This invite link has expired. Contact a group admin for a new link", button "Got it", after closing return to the source page
      i. Use count reached: dialog: "This invite link has reached its use limit. Contact a group admin for a new link", button "Got it", after closing return to the source page
      i. Revoked or reset: dialog: "This invite link is no longer valid. Contact a group admin for a new link", button "Got it", after closing return to the source page
      i. Valid: go to the next check
   a. 3-Membership check: is the user already in the group
      i. Already in the group: go straight to the group chat without joining again
      i. Not in the group: go to the next check
   a. 4-Member count check: has the group reached its member limit
      i. Full: dialog: "This group is full and cannot be joined", after closing return to the source page
      i. Not full: go to the next check
   a. 5-Join method check: does the group have join approval on
      i. On: submit a join request, toast: "Join request sent. Waiting for an admin to approve", the approver receives a request notification
      i. Off: join directly and enter the group chat, and a system message is added in the group: "{nickname} joined the group chat through an invite link"
3. History after joining: for the new member {TBD: whether a new member can see messages from before joining, recommended: not visible by default}; when not visible, the top of the chat shows "Messages from before you joined are not visible"
