# Common interaction (gestures, menus, feedback, states, badges, accessibility, internationalization, haptics and motion)

> Applies to: required reading when drawing prototype screens and writing annotation cards that involve gestures, long-press menus, multi-select, prompts and dialogs, offline and load failures, badges, accessibility or multi-language. In annotation cards, accessibility and motion get qualitative requirements only (e.g. "tap targets must meet the platform accessibility standard", "motion follows the system reduce-motion setting"), never pixels, durations or curves. For evidence see evidence/12-ui-interaction.md.
> Evidence boundary: the local clients yielded only static strings; official help centers cover feature rules only and almost never describe gestures or motion. Actual gesture and motion behavior follows open-source client code and platform and accessibility standards. Of the five products, entries with direct evidence from only two products go to conventions; entries with only one product or pure inference go to divergences; entries based mainly on platform or accessibility standards, with insufficient direct evidence across the five products, are placed in conventions for now, with the reason in parentheses.

## Baseline (follow by default, high confidence)

### Gestures, long-press and multi-select
- **[UX-07] Multi-select mode**: entry is the long-press menu item "Select"; once in, the bottom action bar shows the available items for the selected message types (forward, delete, etc.). Must define: where the selected count is shown, whether the mode exits automatically when the selection is emptied, whether merged forwarding is also provided (see ACT-14), the available scope of delete when own and others' messages are mixed; selection and forward count limits see ACT-02, how many chats one forward can target see ACT-19. | Magnitude: — | Confidence: High

### Feedback, prompts and confirmation
- **[UX-11] When to show a confirmation**: operations that are irreversible or affect others must be confirmed (unsend for everyone, clear chat history, leave group, block); whether deleting a chat uses a confirmation or a timed undo see LIST-26; whether "delete for me only" on a message is followed by a timed undo see ACT-26. Must define: whether each operation is "confirm" or "undo"; whether common recoverable operations (archive, mute, pin) skip confirmation and whether they show a snackbar with "Undo". | Confidence: High
- **[UX-13] Irreversible copy states the scope**: state the scope of the consequence and its recoverability (this device only / all devices / the other party also deletes; "This action cannot be undone"). Must define: the scope sentence for each irreversible operation (including the relation to backup: whether it can be recovered from backup after deletion); if both delete chat and a similar operation such as "hide chat" are offered, how the copy distinguishes "whether records are cleared" and "whether new messages reappear". | Confidence: High

### Offline, loading, empty, error
- **[UX-20] Pre-block states the specific reason**: when an action is unavailable, state the reason before executing rather than failing silently ("Content has expired and cannot be saved", "Image not downloaded and cannot be sent", "Cannot send an empty message", "Text is too long to send"). Must define: block conditions and copy. | Confidence: High

### Internationalization
- **[UX-33] Copy as whole sentences with variables**: copy uses whole sentences with variables ("{N} unread messages") and never concatenates fragments. Must define: whether time format, 12- or 24-hour clock, weekday and date order, and number separators follow the system and locale; how languages with plural forms handle plurals. | Confidence: High

## Conventions (default-OK, mark as suggested)

### Gestures, long-press and multi-select

- **[UX-01] Every gesture has an equivalent entry**: gesture-dependent operations such as swipe to reply, left/right swipe actions, drag to reorder and double-tap must have a non-gesture equivalent entry in the long-press menu, edit mode or a button; a gesture is only a shortcut, never the only entry. Must define: the equivalent entry for each gesture. | Confidence: Medium (direct evidence from only two products, plus accessibility-standard corroboration)
- **[UX-02] Edge back takes priority**: swipes starting at the left or right screen edge are reserved for the system back gesture; horizontal swipes on list rows and bubbles start from inside the row or bubble and do not conflict with edge back; top-level pages have no back. | Confidence: Medium (direct evidence from one product plus platform guidelines (system edge back gesture); the other product is inferred from source code)
- **[UX-03] Swipe to reply**: swipe the bubble horizontally toward the middle of the screen; releasing after passing the trigger threshold enters reply state; during the swipe the bubble follows the finger and the reply icon fades in; after release the bubble springs back; one haptic at the moment the threshold is crossed and the whole gesture triggers only once; in RTL the swipe direction is reversed. Must define: which messages cannot be swiped (system messages, sending messages, chats without speaking permission, etc., decided item by item). | Magnitude: the threshold is a short horizontal displacement, a full swipe is not required | Confidence: Medium (direct evidence from only two products; the non-swipeable scope has only corroboration, so it was moved into must-define)
- **[UX-04] Long-press message layer**: long-press opens "quick reaction bar + action menu"; the selected bubble separates from the background, the menu sits near the bubble and opens upward or downward depending on remaining space; one haptic at the moment it appears; the menu shows only currently available items, hiding unavailable ones rather than graying them out; few and well-chosen items, no more than about 3 groups, at most 1 level of submenu; items in the same group either all have icons or none do. Must define: the number of common emojis in the quick reaction bar and the "More" entry. | Magnitude: about 5-10 menu items | Confidence: Medium (reaction bar plus menu has direct evidence from only two products; hide-not-gray, grouping and icon rules come from platform guidelines and one product's source code)
- **[UX-05] Menu item order**: reply first; delete-type items last with destructive styling; report appears only on others' messages. Must define: the full menu item order (by message type), including the relative positions of copy, forward and edit; which menu items are also provided in the multi-select action bar. | Confidence: Medium (reply first and delete last have direct evidence from only two products; the middle order differs between the two, so it was moved into must-define)
- **[UX-06] Menu items vary by type and state**: long-press menu items are added or removed by message type and send state, showing only currently available items; view-once messages offer no forward, copy or save. Must define: the full menu item list for each type and state. For reference (the following clauses are mostly from one product; reference only, not default rules): text has reply, copy, forward, edit (own messages only, within the time limit), delete, select; image/video mostly "Save", with "Copy" only when there is a caption; voice has no "Copy"; files mostly "Save / Save as"; an unsent message keeps only "Delete" (own messages may include "Re-edit"); system messages have no menu; sending messages cannot be forwarded, pinned or reacted to; a failed message has "Resend" as the first item; poll "End poll" only for the creator; others' messages mostly have "Report", own messages mostly have "Unsend for everyone" and "Info" (receipt details, following the read-receipt tier ruling); timed messages can be forwarded and no longer disappear after being forwarded into a chat with no timer. | Confidence: Medium (the direction of type differences is consistent across multiple products; view-once messages being non-forwardable, non-copyable and non-savable has direct evidence from two products; the remaining clauses were moved into must-define as reference)

### Feedback, prompts and confirmation

- **[UX-08] Feedback component selection**: toast (a light prompt with no action, such as "Copied", "Saved", disappears automatically); snackbar (a bottom prompt bar that may carry one action such as "Undo" or "Retry" and can be swiped away); alert (a modal dialog, used only for questions that need a user decision or are irreversible); inline prompt (a local error on a field or list item); banner (persistent system status: offline, syncing, permission denied); skeleton screen (first-screen loading). iOS has no native toast, so it must be custom-drawn and readable by screen readers. Must define: the trigger condition of each prompt type and whether it carries an action. | Confidence: Medium (a prompt bar with "Undo" has direct evidence from three products, toast from two, and the division of labor of other components comes from platform guidelines; for alert usage, one product has a counterexample of a single-button notice dialog)
- **[UX-09] Do not use an alert for notification only**: information that only reports a result and needs no user decision uses a toast, inline prompt or banner; problems found at launch (no network) use a persistent banner rather than a dialog at launch; multiple options based on an intent the user already started (e.g. "Save draft / Discard changes / Keep editing") use a bottom action menu rather than an alert. Only account-level consequences that must be blocked use a single-button notice dialog. | Confidence: Medium (based on platform guidelines and one product's short-sentence prompts; another product's single-button "Got it" notice dialog is a counterexample)
- **[UX-10] Prompt bar duration and screen reader**: a prompt bar with an action stays longer and the user can extend it, while a pure prompt is shorter; only one is shown at a time, the later one replaces the earlier; status prompts must be readable by the screen reader without moving focus. | Magnitude: a pure prompt lasts seconds, one with an action longer, leaving enough time to act | Confidence: Medium (based on platform and accessibility guidelines; direct evidence across the five products covers only one product's duration of the "Undo" prompt bar)
- **[UX-12] Confirmation dialog copy and buttons**: the title is one sentence saying what will happen ("Delete this chat?"), with body text added only when a consequence needs stating; no more than 3 buttons; the primary action uses a verb phrase ("Delete", "Leave", "Don't show"), not a generic "OK"; the cancel button copy is fixed as "Cancel"; a destructive primary action uses destructive styling; the relative position of cancel and primary follows platform convention, and the PRD writes only the two roles "primary action" and "Cancel" without defining the order. | Magnitude: 2-3 buttons | Confidence: Medium (title phrasing, verb buttons and "Cancel" have direct evidence from three products, with one product still using "OK / Cancel" in some dialogs as a counterexample; the button count limit comes from platform guidelines)
- **[UX-14] Confirm discarding unsaved content**: closing or going back with changes in an edit or draft shows "Discard changes?", with buttons "Discard" and "Keep editing"; with no changes, exit directly. | Confidence: Medium (direct evidence from only two products)

### Offline, loading, empty, error

- **[UX-15] Offline state**: with no network use a persistent status prompt (status copy in the title area or a top banner, form see UX-D4), not a dialog, which disappears automatically when the network returns; the input bar remains usable. For queuing of unsent messages, automatic resend, lifetime and the presentation of turning into failure, see SEND-10. Must define: the status copy. | Confidence: Medium ("the input bar remains usable" has direct evidence from three products; "persistent status prompt, no dialog" has direct evidence from one product plus platform guidelines (information that only notifies does not use a dialog, see UX-09))
- **[UX-16] No network and service connection failure are prompted separately**: "Network unavailable" and "Failed to connect to server" use different copy, and the latter offers a "Retry" entry; rate-limit prompts have their own copy ("Too many actions. Please try again later"), stating the wait time where it can be given; server rejections (banned, must agree to terms first, usage exceeded) are prompted separately from network problems. | Confidence: Medium (separate rate-limit copy has direct evidence from three products; separating no network from connection failure only from two products; the server rejection classification has only corroboration)
- **[UX-17] Loading state**: show skeleton or placeholder rows first, not a full-page overlay; allow the user to continue other actions while loading; use a progress bar when duration is determinable and a spinner when not; paginated loading uses a small indicator at the list edge. | Confidence: Medium (mainly based on platform guidelines; direct evidence across the five products is one product's list-loading copy)
- **[UX-18] Empty state**: the first-time no-data empty state states guidance copy and gives one primary action, never leaving a blank page. Must define: whether filter-no-results, search-no-results and system-permission-denied are each separate, with their copy and primary action (for reference: search with no results reads "No results found for '{keyword}'" with a hint to change the keyword; the permission-denied prompt and the go-to-settings entry see DISC-02); the structure of the empty state (e.g. centered "title + one-line explanation + one primary action"). | Confidence: Medium (first-time no-data empty-state copy has direct evidence from three products; search-no-results and permission-denied have evidence from only one product, and the centered structure has only corroboration, all moved into must-define)
- **[UX-19] Error and retry**: page or list load failure → centered explanation + "Retry"; message send failure → resend beside the bubble; operation failure → toast or snackbar with "Retry"; copy states the cause and what can be done, avoiding generic words such as "Error" and "Warning"; every failure prompt maps to a retry entry or a clear explanation. | Confidence: Medium (failure prompts paired with a retry entry or explanation have direct evidence from three products; "no generic words" has one product's generic error sentence as a counterexample)

### Badges

- **[UX-21] Number and red dot**: the same entry does not show both a number and a red dot; the division of labor between number and red dot see UX-D7; the screen-reader label of a badge reads "{N} unread", not a bare number. | Confidence: Medium (not coexisting has one product's similar practice plus corroboration; the screen-reader phrasing follows accessibility standards)
- **[UX-23] Weakened badge for muted chats**: the unread count of a muted chat uses a weakened style, distinct from unmuted unread; the @ marker stays emphasized. Whether it counts toward the total badge see NOTI-26. | Confidence: Medium (the weakened style has direct evidence from only two products)
- **[UX-24] App icon badge**: represents only the unread message count and carries no number unrelated to messages; updates immediately after the user reads. | Confidence: Medium (badge counting only unread has direct evidence from two products; "update immediately after reading" comes from platform guidelines)

### Accessibility (annotation cards write qualitative requirements only)

- **[UX-25] Tap targets**: the tap target of every tappable element must meet the platform accessibility standard; dense areas (in-row icons, badges, menu items) must not shrink the target because the visual is small; adjacent targets need enough spacing to prevent mis-taps. | Confidence: Medium (based on platform accessibility standards; no direct evidence from the five products)
- **[UX-26] Dynamic type**: supports system font size enlargement; list row height grows with font size, the summary line cap stays unchanged, and core information and button verbs are not truncated. | Confidence: Medium (based on platform accessibility standards; of the five products only one has evidence of a summary line cap)
- **[UX-27] Screen reader labels**: icon-only buttons must have a text label ("Send", "Voice", "More"); stateful controls read out their state ("Muted", "Pinned"); abbreviated times provide a full reading ("3 minutes ago"); messages are read in the order sender, content, time, state; visible text is part of the accessibility name and is updated together when the design changes. | Confidence: Medium (direct evidence from two products, plus accessibility standards)
- **[UX-28] Contrast and non-color communication**: both dark and light modes must meet the accessibility contrast standard; state cannot be expressed by color alone (the failure state uses an icon plus text, mute uses an icon; delivered and read must not be distinguished only by tick color). | Confidence: Medium (based on platform accessibility standards; one product distinguishes delivered and read only by tick color as a counterexample, kept per the ruling gradient "accessibility and recoverability")
- **[UX-29] Reduce motion and autoplay**: when the system "Reduce Motion" is on, motion simplifies to a fade or an instant switch; autoplaying animated images longer than a few seconds need a pause control; no function is triggered by shaking or tilting. | Magnitude: autoplay beyond about 5 seconds must be pausable | Confidence: Medium (based on accessibility standards; no direct evidence from the five products)
- **[UX-30] Floating elements do not cover**: when the keyboard opens the input bar moves up and the list keeps the current reading position; the jump-to-bottom button, prompt bar and input bar must not fully cover the current focused element. | Confidence: Medium (based on accessibility standards; the jump-to-bottom button has direct evidence from one product, and the keyboard-open behavior is inferred)

### Internationalization

- **[UX-31] RTL mirroring**: the overall layout mirrors; own and other's bubble positions swap; the back arrow, swipe-to-reply direction, progress bars and sliders mirror; icons indicating forward or backward mirror; digits are not reversed, and photos, illustrations and brand marks are not mirrored; mixed text takes its paragraph direction from the first strong-direction character, and the time sits at the inner corner of the bubble. | Confidence: Medium (based on platform RTL guidelines; of the five products only one has direct evidence of direction following language)

### Haptics and motion (rules only)

- **[UX-34] Haptics**: each haptic has a unique meaning and is used only at confirmation or threshold moments: long-press menu opening, swipe-to-reply crossing the threshold (once), multi-select ticking, recording start / lock / cancel, send failure (optional); no haptic on ordinary taps; a haptic accompanies visual or sound feedback and does not exist alone. | Confidence: Medium (based on platform haptic guidelines and one product's threshold vibration source code; moments such as recording are inferred)
- **[UX-35] Motion**: motion serves only to help the user understand position changes: a sent bubble floats up from the input box position into the list; new messages animate in only when the user is at the bottom, and enter silently while the user browses history; on delete the row or bubble collapses and the gap closes smoothly; after jumping to a history message the landing bubble briefly highlights; the swipe-to-reply bubble follows the finger and springs back; the appearance and disappearance of "typing" must not make the list jump. Motion follows the system reduce-motion setting (UX-29). | Confidence: Medium (one product's source code plus corroboration; the reduce-motion fallback comes from platform guidelines)

## Divergences (ask Box on must-ask; write default-OK per recommendation and list it)
- **[UX-D1] Double-tap on a message**: Option A: quick reaction / Option B: edit your own message / Option C: reply to the message / Option D: not provided. Recommended: D. Rationale: it is opposite to existing product practice (two products are known to use double-tap for reply and for edit respectively, and quick reaction is only recalled from memory, not evidenced), a trade-off between accessibility and recoverability: double-tap is a hidden gesture with no hint and easily conflicts with multi-select and image zoom. | Level: Default-OK
- **[UX-D2] Message menu form**: Option A: floating list near the bubble / Option B: bottom action panel / Option C: horizontal icon bar above the bubble. Recommended: A. Rationale: two products have direct evidence of using A, and with few well-chosen menu items it is closest to the trigger point; C has only industry observation, not evidenced. | Level: Default-OK
- **[UX-D3] Whether a full swipe executes directly**: Option A: a full swipe executes the first action / Option B: only reveal buttons, a tap is required to execute / Option C: a full swipe executes only non-destructive actions, destructive actions require a tap. Recommended: C. Rationale: recoverability (delete-type actions are not executed by an accidental swipe); one product is known to execute the first action on a full swipe, and another does so only for non-destructive actions such as archive; the recommendation differs from the former, a recoverability trade-off. | Level: Default-OK
- **[UX-D4] Offline prompt form**: Option A: title-area status copy ("Connecting...") / Option B: persistent top banner / Option C: title-area copy first, upgraded to a banner after a period of persistence. Recommended: C. Rationale: user comprehension (brief flickers do not disturb, persistent disconnection gets a clear prompt); direct evidence shows only one product using A, and C is a combined scheme, a user-comprehension trade-off; the upgrade duration is set by the business. | Level: Default-OK
- **[UX-D5] Unread count cap**: Option A: 99+ / Option B: 999+ / Option C: no cap / Option D: compact abbreviation. Recommended: A. Rationale: two products use 99+ on a top-level entry or chat row, which is short and does not break the layout; another product uses no cap on chat rows and one uses abbreviation. | Level: Default-OK
- **[UX-D6] Whether muted chats count toward the total badge**: See NOTI-26 (defined only there).
- **[UX-D7] Use of red dot and number**: Option A: numbers only / Option B: a dot when a muted chat has unread / Option C: one-on-one and group chats use numbers, feed or discovery-type entries use a red dot. Recommended: C. Rationale: user comprehension (a number means count of items to handle, a red dot means there is an update); one product uses a red dot on a feed-type entry, and B has only corroboration. | Level: Default-OK
- **[UX-22] Whether the three unread counts follow the same rule**: Option A: chat rows, top-level entries and the app icon use the same cap rule (except where the app icon is rendered by the system) / Option B: top-level entries and the app icon are capped, chat rows show the full number. Recommended: A. Rationale: user comprehension (the same unread count reads the same in different places); one product is known to use B, and one uses abbreviation everywhere uniformly. For the cap form and limit see UX-D5; the counting basis (by message count or chat count) follows module 08. | Level: Default-OK
- **[UX-32] Adaptation for long languages**: Option A: button and label copy may wrap or grow in height in long languages and must not truncate the verb; chat names are single-line with ellipsis, summaries at most 2 lines; no reliance on fixed width / Option B: fixed width, over-long copy uniformly truncated with an ellipsis. Recommended: A. Rationale: accessibility and recoverability: truncating the verb leaves users unable to understand the button; background: no direct product evidence across the five products, based on general internationalization practice. When A is chosen, must define: the maximum acceptable character budget for key buttons. | Level: Default-OK
- **[UX-36] Time zone basis for rule-based times**: applies to times computed by rules such as day rollover, daily counter reset, expiry date, release time and processing deadline; timestamps of messages, calls and feed posts display in the device time zone and are not covered here; absolute times the user picks themselves (poll deadline, scheduled send, reminder time) are also not covered here, the server stores the absolute time and both selection and display use the device's current time zone. Option A: always compute and display in the account time zone (account time zone = the time zone the server records for the account, taken from the account region setting, or the registration region if unset, following ZYMIX's existing account fields), with cards uniformly writing "per the account time zone" / Option B: compute in the account time zone, display in the device time zone / Option C: always the device time zone. Recommended: A. Rationale: changing the device time or traveling across time zones cannot bypass counters, multiple devices display the same time, and cards have only one way of writing; no direct product evidence, an inference, derived from consistency in the conflict ruling gradient. Must define: the source of the account time zone and when a change takes effect; whether the displayed time carries a time zone note when the device time zone differs from the account time zone (for reference: append "({time zone})"). | Level: Default-OK

## Must-ask states (module-specific, supplements the general state matrix)
- Gesture conflicts: whether horizontal swipe to reply conflicts with the back gesture, list left/right swipe with top-level page switching, and swiping inside the image viewer, and the priority of each.
- Accessibility equivalent entry: whether the non-gesture entry of every gesture operation is marked.
- Other party blocked / account deleted / left the group: which items in the long-press menu (reply, forward, react, call, etc.) are hidden or grayed out.
- Multi-device: a message is unsent on another device while the menu is open; some messages are unsent during multi-select; when the badge updates on this device after the other device reads.
- Offline and weak network: which menu items are available offline, whether the undo bar is still valid after the network returns, the retry cap after a load timeout.
- Message already forwarded or quoted: how the quote block and forwarded content appear after the original message is unsent.
- Group vs one-on-one differences: availability of pin, report, unsend others' messages and @ items, marked item by item by role and chat type.
- Permission revoked mid-operation (muted, demoted, removed from group): whether an already open menu and multi-select refresh immediately, and how an in-progress send wraps up.
- While a confirmation dialog is open: the result and prompt when the dialog's target has been deleted or unsent and the primary action is tapped.
- System permission denied (notifications, photos, microphone): the empty state of the corresponding entry and the "Go to system settings" destination.
- Badges: when it clears (read when visible, or cleared on entering the chat), multi-device sync, whether muted counts, the cap value.
- Multi-language: the truncation strategy for key buttons and titles in long-copy languages such as RTL, German and Russian.
- Reduce motion and large font: the degraded form of jump highlight, send animation and the multi-select action bar once enabled.

## Anti-patterns
| Generic/wrong | Correct | Reason |
|---|---|---|
| After an operation completes, a dialog "Operation successful" + "OK" | toast "{Action} done" that disappears automatically | Notification-only needs no decision and should not interrupt |
| Left-swipe delete with neither confirmation nor undo | Delete gives a confirmation or a timed undo, at least one (chats see LIST-26, messages see ACT-26) | A mis-touch is irreversible, violating recoverability |
| Only write "Swipe to reply is supported" | Also write the equivalent entry (long-press menu "Reply") | A gesture cannot be the only entry |
| Confirmation dialog buttons written "OK / Cancel" | Primary action written as a verb ("Delete"), cancel written "Cancel" | Users cannot tell what will happen |
| Error prompt "Something went wrong, please retry" | State the cause and what can be done, and give a "Retry" entry | A generic phrase gives nothing to act on |
| An offline dialog blocks use | Persistent status prompt, input still usable; handling of unsent messages see SEND-10 | A dialog interrupts and cannot be recovered |
| Unavailable menu items all kept grayed out | Items currently unavailable are hidden directly | The menu gets long and users cannot understand why it is gray |
| The same entry has both a red dot and a number | Choose one | Duplicate semantics |
| Only write "Show unread count", with no overflow behavior | State the overflow behavior (see UX-D5) and whether the three places follow the same rule (see UX-22) | Overflow is bound to happen, and omitting it breaks the layout or makes places read differently |
| Copy concatenating "Total" + {N} + "messages" | A whole sentence with variables, handling plurals | Word order and plurals in multiple languages cannot be concatenated |
| Express failure with color alone | Icon plus text, color as support | Color-blind and screen-reader users cannot perceive it |
| Annotation card writes "button 44 px, animation 300 ms" | Write "tap targets meet the platform accessibility standard; motion follows the reduce-motion setting" | Annotation cards do not write visual specs |

## Calibration sample
The easiest to write too generically is the "message long-press menu". This example has no must-ask items: the menu when there is no speaking permission, menu items per type, unsend time limit, number of common emojis, menu order and no undo after delete are all written into the body per recommendation; the values in the card are illustrative, actual values are set by the business, and each is listed one by one under "Defaulted to recommendation" in the delivery draft. A compliant annotation card body:

Description:
1. Long-press a message; the pressed message separates from the background, and check in order to determine the menu items:
   a. 1-Speaking permission check: whether the current user has speaking permission in this chat
      i. No speaking permission: finally do not show the quick reaction bar or "Reply", go to the next check
      i. Has speaking permission: go to the next check
   a. 2-Unsend state check: whether the message has been unsent
      i. Unsent: show only "Delete for me only", no further checks
      i. Not unsent: go to the next check
   a. 3-Send state check: the current send state of the message
      i. Send failed: show only "Resend" and "Delete", "Resend" first, no further checks
      i. Sending: go to the next check, finally do not show the quick reaction bar or "Forward"
      i. Sent: go to the next check
   a. 4-Message type check: which type the message belongs to
      i. View-once message: base items are "Reply" and "Select", go to the next check
      i. Text: base items are "Reply", "Copy", "Forward", "Select", go to the next check
      i. Image/video: base items are "Reply", "Save", "Forward", "Select", add "Copy" when there is a caption, go to the next check
      i. File: base items are "Reply", "Save", "Forward", "Select", go to the next check
      i. Voice: base items are "Reply", "Forward", "Select", go to the next check
      i. Location, contact card and other types: base items are "Reply", "Forward", "Select", go to the next check
   a. 5-Ownership check: who sent the message
      i. Own: add "Delete for me only"; when sent and less than 24 hours have passed since sending, add "Unsend for everyone"; check ends, show the menu
      i. Others: add "Report" and "Delete for me only"; check ends, show the menu
2. Show the quick reaction bar and the action menu: the quick reaction bar shows 6 common emojis and a "More" entry; the menu shows only available items, and unavailable items are hidden
3. Menu item order: Reply, Copy, Save, Forward, Select, Report, Delete for me only, Unsend for everyone
4. Tap "Unsend for everyone": dialog prompt: title "Unsend this message for everyone?", body "After unsending, everyone in the chat will see this message replaced with an unsent notice", buttons "Unsend" and "Cancel"
5. Tap "Delete for me only": dialog prompt: title "Delete this message for you only?", body "Deleting affects only you; the other party is not affected", buttons "Delete" and "Cancel"; no undo is provided after deleting
6. Note: "Edit" and "Info" (receipt details) are outside this card; when provided, write a separate description and insert them following the order in item 3
