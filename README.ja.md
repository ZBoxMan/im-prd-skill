# im-prd-skill

[English](README.md) | [简体中文](README.zh-CN.md) | [繁體中文](README.zh-TW.md) | [日本語](README.ja.md) | [한국어](README.ko.md) | [Español](README.es.md) | [Português](README.pt.md) | [Français](README.fr.md)

メッセージング（IM）／ソーシャルプロダクト向けの PRD を書くための Claude Agent Skill です。主要なメッセージングアプリが各機能をどう扱っているかをまとめた 26 モジュールのライブラリを同梱しており、生成される仕様は既定で IM の慣例に沿います。主要アプリの間で実際に判断が分かれる点だけを、選択式の質問として意思決定者に提示します。Markdown の納品ドラフトのみを出力することも、注釈カードを Figma キャンバスに書き込むこともできます。

このスキルは ZYMIX チーム向けに作られました。公開版では、チームの Figma ファイルキー、デザインシステムの値、内部の裁定、元の証拠資料を取り除いています。ワークフロー、ルールライブラリ、テンプレート、スクリプト、評価ケースはそのまま残っています。

## 解決する課題

AI に IM 機能の仕様を直接書かせると、たいてい次の 3 つの問題が起こります。確定していないルールが確定事項のように書かれる。正常系しか扱われず、ブロック、アカウント削除、オフライン、マルチデバイス、グループと 1 対 1 の違いといった状態が抜ける。業界の慣例と、チームが本当に判断すべき少数の事項が混ざり、意思決定者が全文を読まないとそれを見つけられない。

このスキルの対処方法は次のとおりです。

- **3 段階のルールライブラリ**：ベースライン（主要アプリが一致。既定で従う）、慣例（多くのアプリがそうしている。既定は推奨案）、相違点（アプリごとに異なる。Must-ask（必須確認）または Default-OK（既定で可）のタグ付き）。
- **必須確認の質問だけを行う**：1 ラウンドあたり選択式の質問は最大 4 つで、推奨の選択肢を先頭に置きます。それ以外は推奨どおりに書き、確認用に「Defaulted to recommendation」（推奨どおりに既定とした事項）の下に 1 行ずつ列挙します。
- **状態カバレッジマトリクス**：成功、失敗、タイムアウト、オフライン、権限、マルチデバイス同期、そして「相手にブロックされた／アカウントを削除された／グループを退出した」といった状態を 1 つずつ確認します。
- **不確実な点を見えるままにする**：判断が必要な項目は `{TBD: topic, recommended: approach}`、不足している事実は `{TBC: what is missing}` と書きます。確定事項として扱うことはありません。
- **書き込みゲート**：Figma に触れる前に、作成するすべてのノードとバッチを一覧にします。意思決定者が承認した後にのみキャンバスへ書き込みます。

## ワークフロー

| ステップ | 内容 |
|---|---|
| 0 プロダクトの整理 | 会話タイプ（1 対 1／グループ／チャンネル／コミュニティ）、プラットフォーム、エンドツーエンド暗号化の有無、見知らぬ相手から連絡できるか、実現可能性の前提を確認する |
| 1 信頼できる情報源の固定 | Figma ファイルとノードを記録し、各要件を定義済み／要確認／提案としてタグ付けする |
| 2 IM 規範の確認 | 該当するモジュールを読み、ベースラインに従い、慣例を既定とし、相違点はレベルに応じて扱う |
| 3 競合の参照 | ライブラリがカバーしていない機能に限って外部調査を行う |
| 4 状態カバレッジマトリクス | 一般的な観点とモジュールの必須確認状態について、それぞれ対応済み／対象外／未定義を記す |
| 5 まずドラフト | Markdown の納品ドラフトを書き、`lint_card_text.py` を実行する。大きめのドラフトでは読者テストを追加する |
| 6 レイアウトと採番 | 画面の順序、行、番号を一度にまとめて計画する |
| 7 書き込みゲート | `lint_card_text.py --gate` に合格し、意思決定者が承認するまで何も書き込まない |
| 8 カードの書き込みとセルフチェック | バッチごとにセルフチェックし、最後に受け入れレシートを出す |

納品ドラフトの順序：Decisions for Box（Box への判断依頼）→ Defaulted to recommendation → Open items（未決事項）→ Role view summary（役割別サマリー）→ Cards（カード）→ Feature list（機能一覧）→ Acceptance checkpoints（受け入れ確認ポイント、≤ 12）→ Suggested follow-ups（今後の提案）。

## インストール

Claude Code（英語版の例。中国語版は `zh-CN/box-prd-create` を使います）：

```bash
git clone https://github.com/ZBoxMan/im-prd-skill.git
```

```bash
cp -R im-prd-skill/en/box-prd-create ~/.claude/skills/
```

claude.ai：`box-prd-create` フォルダを zip に圧縮し、「設定 → 機能 → Skills」からアップロードします。

## 使い方

機能を説明するだけです。例：

- 「グループチャットにグループお知らせ機能を追加して。PRD を書いて。今は納品ドラフトだけでいい。」
- 「設定に『自分のデータをダウンロード』を追加して。PRD を Figma に書いて：figma.com/design/<fileKey>、『設定』ゾーンに。」
- 「送信取消の制限時間はどのくらいが適切？ PRD に入れたい。」

## チームに合わせて調整する

- `references/design-system.md`：自分たちのデザインライブラリ、コンポーネントキー、色とタイポグラフィのトークン（プロトタイプ画面を描くときだけ使用）。
- `references/rulings.md`：チームの書き方の裁定と廃止したレイアウト。
- `scripts/brand_terms.txt`：カード文面に出してはいけないブランド名。
- SKILL.md 内の「ZYMIX」と「Box」はそれぞれプロダクト名と意思決定者です。必要に応じて置き換えてください。
- Figma への書き込みには [figma-console MCP](https://github.com/southleft/figma-console-mcp) の Desktop Bridge が必要です。Markdown のみのドラフトでは追加の準備は不要です。
- SKILL.md で触れている `box-figma-prd` と `box-prd-review` は、作者の非公開の補助スキル（キャンバスの検査と全体レビュー）です。これらがなくても生成フローは動作します。

## 評価

中国語版で実施しました。

- ブラインド比較：8 シナリオ（マルチデバイス、グループ管理、お年玉（紅包）、通報、グループ投票、友達フィード、新規ユーザーのオンボーディング、送信取消／編集）で、同じ要件に対する 21 の類似スキルと比較。出所を伏せた Opus の審査員が、IM の正確さ、エッジケースの網羅、判断の扱い、実装可能性、読みやすさを採点：94 ラウンド、90 勝、4 敗。
- 実際のトリガー：肯定・否定のプロンプト 31 件 × 3 回を `claude -p` で実行：31/31 が正しく判定され、否定プロンプトでの誤トリガーはなし。

記録：`zh-CN/box-prd-create/evals/trigger-results.md`。英語版は個別には評価していません。
