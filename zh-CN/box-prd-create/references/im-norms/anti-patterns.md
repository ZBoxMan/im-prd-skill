# IM 跨模块反模式总表

> 收尾自查用：草稿写完后逐条对照，命中即改。模块专属反模式在各模块文件末尾，本表只收跨模块、反复出现的问题。

## 目录
- 状态与终态
- 多端、离线与时序
- 关系、权限与隐私
- 群与私聊
- 反馈与文案

## 状态与终态

| 泛写/错写 | 正写 | 原因 |
|---|---|---|
| 只画图标不定义状态机，如「发送状态：单勾、双勾」 | 每个状态先一行定义语义，再写进入条件、退出条件和终态；失败是终态还是可重试态写明 | 图标是表现，状态机才是开发要实现的东西 |
| 只写成功路径 | 至少补齐服务等待、可恢复失败、阻断、超时、未知结果五类出口 | 主流产品的大部分文案都花在失败与边界上 |
| 「操作失败，请重试」一句覆盖所有失败 | 按网络失败、权限不足、对象已失效、频控分别给文案与去向 | 原因不同，用户能做的补救不同 |
| 能开不能关、能发不能撤、能进不能退 | 每个「创建」配对写出撤销、查看、退出的路径；不提供时写明「不提供」 | 断链是一票否决项 |
| 异步动作没有中间态 | 写出等待中的表现、可否取消、取消后的状态 | 弱网下中间态会持续数秒到数分钟 |
| 举报、申诉、钱包争议、意见反馈各写一套状态名与流转，结果有的通知有的不通知 | 统一映射到通用工单状态机，需补充、重开、撤销与结果通知只定义一次，各类型只配入口、资格、次数与时限（见 SUP-10、SUP-04） | 用户在不同入口看到不同叫法，研发重复实现，状态与通知口径互相矛盾 |

## 多端、离线与时序

| 泛写/错写 | 正写 | 原因 |
|---|---|---|
| 只考虑当前这台设备 | 写明同一账号其他设备上的表现：已读、已撤回、已删除、设置变更是否同步、多久同步 | 多设备是主流产品默认能力 |
| 默认接收方在线 | 写离线接收方上线后看到什么，推送是否已经展示过原内容 | 撤回、编辑、删除最容易在离线接收方处穿帮 |
| 消息顺序按本地时间 | 写明排序依据与离线排队消息恢复网络后的发送顺序 | 本地时间不可信，乱序会改变语义 |
| 「拉黑前的消息照常送达」「超时后不可撤回」只写结果 | 写判定口径：以服务端接收时间还是客户端发送时间为界，多端以哪端为准 | 分界口径不写，研发两端各自实现，边界消息行为不一致 |
| 「实时更新」 | 写触发、刷新、停止、重开四段（信令类规则四段式） | 「实时」无法唯一实现 |
| 用户操作期间对象被他人改变不处理 | 写中途变化：对方撤回、被移出群、权限被收回、会话被清空 | 并发是 IM 的常态 |

## 关系、权限与隐私

| 泛写/错写 | 正写 | 原因 |
|---|---|---|
| 不定义被拉黑、已注销、非好友对象的表现 | 每个涉及「对方」的功能都写这三种对象下的发送结果与提示 | 关系状态改变的是能力边界 |
| 隐私开关只写「可关闭」 | 写默认值、可选范围档位、关闭后的对等规则（我关了是否也看不到别人的） | 默认值决定绝大多数用户的体验 |
| 被拉黑方得到明确的「你已被拉黑」反馈 | 是否向被拉黑方暴露拉黑事实，作为分歧点交 Box 裁决 | 暴露与否是隐私取舍，主流做法不一 |
| 权限只写「管理员可以」 | 写权限项清单、谁能授予、能否处置同级或更高角色、权限收回后已在进行中的操作如何处理 | 权限冲突是群功能高发缺陷 |
| 撤回同意、关闭同步或关闭个性化只写「已关闭」 | 写撤回后功能的状态，以及已收集数据是停止处理、删除还是让用户选择（见 PRIV-13；通讯录见 DISC-21） | 用户以为数据已删，实际仍在服务端，属不实告知 |
| 陌生人与好友同一套能力 | 写陌生人首次触达的限制、接受前不可用的高打扰动作、拒绝与举报入口 | 陌生人可达性决定骚扰面 |
| 年龄未确认的账号只写「部分功能受限」 | 逐项写限制了什么（陌生人接触、动态默认受众、付款与开户、年龄限制内容、个性化推荐）、入口隐藏还是点击后提示、怎么解除（见 AGE-07、AGE-02） | 各模块对「受限」各自理解，用户也不知道如何解除 |

## 群与私聊

| 泛写/错写 | 正写 | 原因 |
|---|---|---|
| 写了私聊规则就默认群里一样 | 逐项写群与私聊的差异或明确「与私聊一致」 | 回执、撤回、通知、@ 在群里普遍不同 |
| 群人数只写一个上限 | 按人数分档写规则，各档写在同一张卡内 | 大群的回执、通知、邀请规则通常降级 |
| 退群、被移出、群解散后不处理历史与入口 | 写历史是否保留、能否再发言、会话列表如何显示、能否再加入 | 成员关系终止后的状态最容易漏 |
| 系统消息随手写 | 群资料变更、成员变动、权限变动的系统消息逐字给出，并写谁能看到 | 系统消息是群内事实记录 |

## 反馈与文案

| 泛写/错写 | 正写 | 原因 |
|---|---|---|
| 「提示用户」 | 写载体（toast／弹窗／行内提示／横幅／系统消息）与逐字文案 | 载体决定是否打断与是否可撤销 |
| 危险操作一步完成 | 删除、退出、解散、清空、拉黑走二次确认，确认文案写明作用范围与可否恢复 | 不可逆操作必须可预期 |
| 撤回、删除用同一个词 | 「仅自己删除」与「为所有人撤回」分词、分入口、分确认 | 用户会误以为对方也被删除 |
| 计数只写「显示数量」 | 写计数口径、上限显示方式、不清零条件、静音会话是否计入 | 计数口径是角标与未读的高频争议 |
| 处罚或受限提示只写「账号已受限」，不给申诉入口与期限 | 写受限范围、仍可用的功能、解除时间或「永久」、申诉入口与申诉期限（见 ENF-01、ENF-02、ENF-07；钱包受限见 WAL-21） | 用户无从判断何时恢复、如何救济，只会反复试探与咨询 |
| 广告或推荐条目插进会话列表、信息流后按普通条目处理 | 写清带广告标识、不计未读与角标、不触发推送、不进搜索、不响应会话操作（见 ADS-01、ADS-07） | 未读、角标与搜索口径被污染，用户分不清「有人找我」 |

## 资金、位置、内容外送与第三方读取

| 泛写/错写 | 正写 | 原因 |
|---|---|---|
| 支付、分摊的状态混写成一套「已付／未付」 | 每个状态先标「受监管资金流」或「记账」：资金流以持牌机构确认为准、卡片只映射；记账可改可删、不动钱 | 两类状态的权威来源、可否改写与监管责任都不同，混写会把对账口径写乱 |
| 动态、故事默认对所有人可见，不区分账号年龄 | 写默认受众、发布页显式展示当前受众；未成年或未完成年龄确认的账号收紧档位（年龄判定口径见 AGE-07） | 默认值决定绝大多数内容的曝光面，上架地区通常对未成年账号有合规要求 |
| 会话内容交给翻译、AI 或机器人处理却不告知 | 写首次使用须知、每个入口提交的内容范围、处理位置、是否用于训练，加密会话中的可用性 | 他人消息被外送时原发送者无从知晓，加密承诺可能因此失效 |
| 实时位置只写「开始共享」 | 写有限时长档位、到期自动结束、手动停止与「全部停止」、结束后对方看到什么 | 无到期、无统一停止入口，用户会忘记自己仍在共享行踪 |
| 注销账号或注销钱包只写「注销后数据删除」，不处理余额 | 写余额、处理中的提现、待收款与未结争议是拦截还是去向，积分与会员剩余期是否作废，注销前给提现与下载明细入口（见 WAL-18、WAL-20） | 资金不随账号删除而消失，「注销后钱去哪」是高频客诉 |
| 「机器人可读取群消息」不定义范围 | 写默认读取范围（只收与它相关的还是全部）、谁能放开、成员在哪里看到读取范围 | 群内读取范围关系到全体成员的隐私，不只是加机器人的人 |
| 发图、发链接时只写内容本身 | 写图片的拍摄位置等元数据是否抹除、链接预览由谁抓取、是否默认生成 | 元数据与预览抓取会在用户不知情时泄露位置与网址 |
| 写「充值送积分」「现金购买积分」「积分抵现」「兑换话费或余额」却不标可行性 | 与现金挂钩时，对应的资金动作按受监管资金流处理，可行性写 {待查} 与持牌机构项合并，现金部分的退款路径见 PAY-21；积分本身仍按记账（见 PTS-13） | 积分可能被认定为储值或支付工具，绕开资金合规与退款规则 |
| 邀请奖励只写「填写邀请码，双方各得积分」 | 写发放条件与时点、锁定期、使用上限、自邀判定、发放失败与撤回（见 INV-11、INV-14 至 INV-18） | 奖励规则不写全，上线即被刷 |

## 规范库使用

| 泛写/错写 | 正写 | 原因 |
|---|---|---|
| 把 `级别：必问` 的分歧点按推荐直接写进卡，或把它塞进「已按推荐默认」 | 按条目末尾的级别处理：`必问` 先问 Box，卡内写 `{待定：议题，推荐：做法}`；`可默认` 按推荐写进卡并列入「已按推荐默认」 | 必问项涉及隐私、不可逆处置或主流程走向，推荐只是建议 |
| 给 `可默认` 的分歧点或惯例留 `{待定}` | 直接写推荐值或量级内的取值，在「已按推荐默认」列一行 | 占位过多会卡住写入闸门，也浪费 Box 的注意力 |
| 照抄规范库量级里的数值 | 取值由 ZYMIX 业务定，量级只用来判断是否离谱 | 2026-09-15 裁决：不照抄竞品数值 |
| 说明卡里写「与主流产品一致」代替规则 | 规则本身写全，必要时在 `注：` 补一句「与主流即时通讯产品一致」（Box 认可的改写词） | 开发看不到规范库，卡必须自足 |
| 说明卡里写规范库 ID | ID 只在技能、评审与评测内部使用 | 画布已废止规则 ID |
| 把持牌机构、监管或研发才能回答的取值（限额、手续费、到账时效、开放地区、能否在途冻结）写成 `{待定}` 问 Box | 写 `{待查：缺什么}` 进未决项，同一答复方的多项合并为一组；只把产品取舍留给 Box | Box 拍不了这些板，占用提问名额，答复后还得再改一遍 |
| 推荐写「以 ZYMIX 既有规则为准」的条目，事实源已有答案仍留 `{待定}` 提问 | 先查事实源，查到即按事实源写成正文，可在卡内注明「以现行条款为准」 | 浪费 Box 的注意力，同一事实在不同需求里还会出现两种口径 |
