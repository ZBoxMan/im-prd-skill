# IM 规范库（im-norms）

主流即时通讯产品的功能规则、交互方式与页面结构，按功能模块拆分。用途：让 ZYMIX PRD 默认符合 IM 惯例，并把「惯例不统一」的地方显式交给 Box 裁决。

## 怎么用

1. 生成流程第 0 步定型后，按 SKILL.md「IM 规范」一节的路由表只读命中的模块文件，不整库加载。
2. 每个模块的规则分三档（定义见下一节）：**基线**默认遵循；**惯例**可按推荐默认写进卡并列入「已按推荐默认」清单；**分歧点**按条目末尾的级别标处理——`级别：必问` 的用选择题问 Box，`级别：可默认` 的按推荐写进卡并列入「已按推荐默认」清单；末尾另有 `｜定型：是` 的形态类分歧点在第 0 步产品定型时一起问（级别定义见「分歧点级别」）。
3. **指针条目**：正文以「见 XX-nn」开头的条目（各模块都有），表示该概念归属另一模块（见「跨模块概念归属表」）；只留「见 归属 ID」与一句范围说明，不带选项、推荐、量级与级别，留在原小节，读到时按归属条目的档位与级别处理。只有一个子句涉及归属概念的条目（如 GRP-13、UX-11、LIST-10、GRP-17），只把该子句改为「见 归属 ID」，其余子句照常。
4. **必问状态**：该模块在通用状态覆盖矩阵之外必须逐项标 `覆盖`／`不适用`／`未定义` 的维度。
5. **反模式**：生成后逐条对照，命中即改。
6. **量级**：只用来判断 ZYMIX 的取值是否离谱，**不照抄**任何竞品数值（2026-09-15 裁决）。

## 三档定义与判定纪律

| 档 | 判定门槛 | 置信度 | 生成时怎么用 | 偏离时 |
|---|---|---|---|---|
| 基线 | **每个子句**都单独满足「五家中 ≥ 3 家直接证据一致、无主流反例」 | 只能是「高」 | 默认遵循，不问 | 卡内写 `注：` 说明偏离理由，列入交付稿「待 Box 裁决」；未说明即触发一票否决「偏离基线」 |
| 惯例 | **每个子句**都满足「≥ 2 家直接证据一致」，或「1 家直接证据 + 平台设计规范、平台审核规则或无障碍标准明文」；可以有一家反例，但不能只靠推断 | 「中」 | 可按条目做法默认写进卡，并列入交付稿「已按推荐默认」清单、在工作底稿标 `建议`（卡内正文不写「建议」字样） | 不触发「偏离基线」一票否决；Box 改判后按裁决改卡 |
| 分歧点 | 主流做法不一致（两种以上做法各有两家左右），或只有一家产品证据、或全靠推断 | — | 按条目末尾级别：`必问` 用选择题问 Box（推荐项放第一）；`可默认` 按推荐项写成卡内正文，列入「已按推荐默认」 | `必问` 未裁决前用 `{待定：议题，推荐：做法}` 占位（推荐只是方向，裁决前不算定论）；`可默认` 的 Box 改判后按裁决改卡 |

- **子句单独计家数**：一条规则含多个子句时（如「A，且 B，且 C」），每个子句都要有自己的 ≥ 3 家直接证据。**禁止把不同子句的单家证据拼成「三家一致」**；任一子句不达标，整条降为惯例，或把该子句拆出去另立条目。
- 「直接证据」= 客户端字符串、开源源码、官方帮助中心或开发者文档原文。检索摘要、媒体转述、常识推断都不算直接证据。
- 五家指 evidence 里重判时使用的五个主流产品；协议规范与开源 SDK 只作旁证，不计家数。
- 惯例同样**子句单独计家数**：任一子句只有一家证据且无平台规范（含平台设计规范与平台审核规则，如应用商店审核指南、开发者政策）或无障碍标准明文、或只有推断，就把该子句移入必定义（可写成「可参考」），或整条改为分歧点。依据平台规范的，置信度括号写明（如「中（一家直接证据加平台规范）」）。一句话：基线每子句 ≥ 3 家，惯例每子句 ≥ 2 家或 1 家 + 规范，其余都是分歧点。
- 基线只能降不能自动升：拆子句后剩余主体够格升基线的，要在 evidence 写明逐子句家数，复核后再移。
- 推荐理由里出现「多数」「三家」「五家」等家数表述时，必须与 evidence 该行的家数一致；推荐与证据相反时（如所有已知产品都选 A 而推荐 B），理由必须写明「与现有产品做法相反，属 ×× 取舍」。

## 分歧点级别

每个分歧点条目末尾都有 `｜级别：必问` 或 `｜级别：可默认`，由规范库维护者按下表五类预先标好。**必问以规范库标签为准**：标 `级别：必问` 的分歧点，以及条目里写明「按必问处理」的子句；标 `可默认` 的照标签按推荐执行，生成时不按五类重新判定。运行时只在两种情况额外升级为必问：④ 与 ZYMIX 既有规则冲突或偏离基线；规范库没有覆盖的新议题落在五类之内。

| 级别 | 判定（五类用于维护规范库与判断库外新议题；库内只预标 ①②③⑤，④ 见下） | 生成时 |
|---|---|---|
| 必问 | ① 隐私默认值、对等规则、对方能感知到什么；② 不可逆处置或数据删除的范围；③ 二选一会让主流程走向不同、不定下来卡就写不下去；⑤ 受监管资金流的可撤销性：付款后能否撤销、资金能否追回（退回路径与时效取决于持牌机构能力，属下一行事实源缺口；「该不该退、退给谁」本身不自动属 ⑤，涉及隐私或不可逆处置时按 ①② 判） | 本需求说明卡会写到时，汇总成选择题问 Box；卡内写 `{待定：议题，推荐：做法}` |
| 可默认 | 其余全部（取值、文案、次要分支、谁能操作、是否留痕、是否提供某个次要功能等） | 按推荐项写成正文，交付稿「已按推荐默认」列一行 |
| 事实源缺口（不问 Box） | 取值或可行性取决于持牌机构、监管或研发能力的（限额取值、开放地区清单、能否在途冻结、退回路径与时效、年龄判定口径、各上架地区的商店支付规则） | 条目内写明「属事实源缺口，写 {待查} 进未决项」；卡内写 `{待查：缺什么}`，不占提问名额；未决项按答复方合并计数（如「持牌机构：限额、手续费、到账时效」算一组），最多 5 组；`{待定}` 须在写入闸门前清零，`{待查}` 若外部答复未到，可在写入申请块逐条列出（答复方、影响哪张卡），经 Box 同意后原样上画布，答复到后补；同一条目里需要 Box 取舍的部分照常按级别处理 |

- **形态类分歧点**：条目末尾在级别后另标 `｜定型：是`（如实时位置形态、分摊走记账还是真付款、群类型体系、频道评论区、默认加密范围、群内 AI 调用形态），决定的是「做成什么形态」。这类在生成流程第 0 步产品定型时与会话形态一起用一轮选择题问齐（每题一个维度，≤ 4 题），**不计入提问预算的 4 题**；超过 4 个定型维度说明需求过大，先问 Box 是否拆分；定型后在样例与卡内写「已在定型时确定为 ××」，不再留 `{待定}`。
- 提问预算的第 ④ 类「与 ZYMIX 既有规则冲突或偏离基线」只有运行时才知道，不在库里预标：标 `可默认` 的条目、惯例或基线若与 ZYMIX 事实源冲突，运行时升为必问。除 ④ 与库外新议题外，运行时不因条目「看起来涉及」某一类而升级。
- 基线、惯例的「必定义」里个别参数也可能落在 ①②（如撤回后对方已下载的内容是否保留）；这类参数在条目内写明「按必问处理」，其余必定义参数按推荐或常识取值并列入「已按推荐默认」。
- 推荐项写着「以 ZYMIX 既有规则为准」的条目，运行时先查事实源，查到即按事实源写，不再问。

## 条目格式

```
- **[ID] 规则名**：做法。必定义：PRD 必须写清的参数或分支。｜量级：区间（仅判量级）｜置信度：高/中
- **[ID] 议题名**：选项 A：…／选项 B：…。推荐：X，理由：…。｜级别：必问/可默认
- **[ID] 议题名**：选项 A：…／选项 B：…。推荐：X，理由：…。｜级别：必问｜定型：是
```

- ID 形如 `SEND-03`，只在技能、评审与评测内部引用，**不写进画布**（2026-08-26 已废止 PRD 内规则 ID）。ID 一经分配不改名；条目换档（基线 ↔ 惯例 ↔ 分歧点）时 ID 不变，只移动位置；废弃时标 `（废弃）` 保留占位。
- 置信度：高 = 满足基线门槛；中 = 满足惯例门槛；低 = 推断或单家，只能出现在分歧点的取舍背景里。
- 分歧点条目必须以 `｜级别：必问` 或 `｜级别：可默认` 结尾（`lint_skill.py` 检查）。
- 量级只写次数、条数、人数、时长档位这类可写进说明卡的产品约束，或定性描述；**像素、逻辑像素、毫秒等视觉与动效数值只放 evidence**，模块文件不出现。
- 模块文件**不出现任何品牌名**（含产品线名称）。
- 「主流产品」「多数产品」「部分产品」「国内主流产品」「隐私优先类产品」「一家产品」这类分类词**只供技能内部判断取舍**，不得写进说明卡正文或 `注：`；卡里要写的是规则本身。例外：「与主流即时通讯产品一致」是 Box 认可的改写词（见 SKILL.md 说明卡写作规范），不在禁列，可在 `注：` 里补一句，但不能代替规则本身。模块措辞也不得整句照搬进卡，按说明卡写作规范重写。

## 校准样例写法

每个模块末尾的校准样例是 agent 最强的模仿对象，统一遵守：

- 只有 `必问` 级的取值写 `{待定：议题，推荐：做法}`（如 `{待定：已转发副本是否一并撤回，推荐：保留副本}`）；取决于持牌机构、监管或研发能力的取值写 `{待查：缺什么}`，同一答复方的多个 `{待查}` 在开头与 `注：` 里合并成一组表述；推荐写「以 ZYMIX 既有规则为准」且事实源已有答案的，按事实源写成正文；`定型：是` 的形态在样例开头写「已在定型时确定为 ××」；惯例、`可默认` 级分歧点与必定义里的普通参数，直接写推荐值或示意取值（落在量级内），样例开头一句说明哪些按推荐写、哪些必问。运行时变量照常写 `{昵称}` `{N}`。
- 判断必须是点击后、结果出现前的**前置校验**；每个判断的分支成对穷举、结果互不相同，末支写明去向；不得出现「不展示的开关被点击」一类矛盾。
- 判断少于 3 个时不起判断链，直接按步骤写，不硬凑判断。
- 判断顺序：冷却、频控、锁定、黑名单一类过滤放第一步；不依赖服务端的判断（权限、锁定、网络）放在依赖服务端返回的判断（服务端状态、余额、资格）之前；过滤本身依赖服务端时（如是否已有进行中的请求、限兑次数），排在网络判断之后、其他服务端判断之前。
- 统一叫法：规则类时间写「按账号所在时区」（口径见 UX-36）；隐私页写「设置」-「隐私与数据」（见 PRIV-21）；系统通知载体写「平台系统会话」（见 BOT-09）。
- 判断链硬格式：判断用重复的 `a.`，出口用重复的 `i.`；`1-判断名` 前缀紧贴 `a.`；每个出口独占一行；有必问项时末尾必有 `注：` 列出待裁决项（不编号），没有则不写。
- 按钮卡固定两条开头：`1. <输入条件>后按钮亮起`、`2. 点击后进行以下判断：`；需要交代入口时，把 `入口：` 写在第 1 条开头、与亮起条件同一条，其余规则放在判断链之后。
- 用词与 `anti-patterns.md` 一致：「仅自己删除」「为所有人撤回」；多值并列用 `/`，不用 `|`；按钮或选项并列写成「A」/「B」，每个值各自加引号，不写成「A / B」。
- 样例必须过 `scripts/lint_card_text.py` 0 命中。

## 外部调研资料（公开版未附）

模块文件只放精简规则；各家具体取值、证据原文与证据冲突说明放在规范库之外的调研资料里（作者本地 Wiki，公开版不含）。需要判断取值量级或向决策人讲各家做法时，查你自己的调研资料；带品牌名的内容写进交付稿前按品牌名禁用规则改写。
