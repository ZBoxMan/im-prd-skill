# box-prd-create ｜ ZYMIX IM 产品 PRD 生成

**本技能管**：生成什么（IM 规范库）、怎么生成（流程与门禁）、怎么写（说明卡写法）、长什么样（版式与设计系统，见 references）。`box-figma-prd` 管画布读写、取证与验证；`box-prd-review` 管审核与验收。生成或续写时与 box-figma-prd 同时加载，冲突时红线优先。

**同源规则只在本技能定义一次**：状态覆盖矩阵、IM 规范库、Box 写法六规则、文案与符号、品牌名禁用、设计系统 token 与组件表、说明卡正文不写视觉规格。其他技能只放指针；不一致时以本技能为准，并把差异登记到对应技能的待同步项。其他技能引用本技能时按**章节名**引用（「写入闸门」「交付自检」等），不按步骤号；旧指针里的「六步、第五步写入闸门」即本版「写入闸门」一步。

**Figma 通道**：一律走 figma-console MCP（Desktop Bridge），读写经 `figma_execute`，截图经 `figma_capture_screenshot`；不用官方 Figma MCP 的 `use_figma` 等工具。连接与只读纪律见 `box-figma-prd`。

**三层不要混**：

| 层 | 内容 | 规格来源 |
|---|---|---|
| 原型屏内容层 | 402×872 帧内的界面 | 设计系统库 → `references/design-system.md`；页面结构惯例 → `im-norms/11-ui-structure.md` |
| PRD 标注层 | 标题条、说明卡外壳、徽标、连线 | 本技能版式色（`#00C8B3` / `#18A0FB` / `#F6F8FD` / `#00C3D0`）→ `references/canvas-layout.md` |
| 说明卡正文 | 需求文字 | **不写任何视觉规格**，见下文 |

## 生成流程

从需求到画布共九步（第 0–8 步），跳步就会返工。第 0–6 步不写画布，第 7 步是写入闸门。

0. **产品定型**：确认本需求涉及的会话形态（单聊／群／频道／社区）、IM 模块、端（iOS／Android／桌面）、是否端到端加密、陌生人是否可达；以及命中模块里标「定型：是」的形态类分歧点（如实时位置是单向还是多人同图、分摊走记账还是真付款、群类型体系）。PRD 与事实源已写明的不问；缺的用一轮选择题问齐（每题一个维度，≤ 4 题；超过 4 个定型维度先问 Box 是否拆分），定型题不占「提问预算」的 4 题。同时核对**功能可行性前提**（如钱包与支付资质、持牌机构能力、第三方服务是否接入），未确认的作为阻断性未决项置顶，写 `{待查}`。据此决定读哪些 `im-norms` 模块、哪些维度直接标「不适用」并留一行理由。
1. **锁事实源**：记 fileKey、规范化 nodeId（`123-456` → `123:456`）、目标大区、保护范围。需求逐项标 `已定义`／`待确认`／`建议`。`待确认` 不落正文：缺事实源（现网规则、研发或合规答复）的写 `{待查：缺什么}` 并列入「未决项」，需 Box 拍板的写 `{待定：议题，推荐：做法}` 并列入「待 Box 裁决」；`建议` 只有两类可落卡——规范库惯例与按推荐默认的取舍，且必须列入「已按推荐默认」清单，Box 在写入闸门同意即视为采纳；其余 `建议` 不落卡。
2. **IM 规范对照**：读命中的模块文件。**基线**默认遵循，PRD 要偏离必须写 `注：` 并列入「待 Box 裁决」；**惯例**按推荐默认采用并列入「已按推荐默认」；**分歧点**只取本需求说明卡会写到的那些，按条目上预标的级别处理——`必问` 汇总成选择题一次问 Box（推荐项放第一），`可默认` 按推荐写进卡并列清单；**必问状态**只取与本需求对象相关的行并入下一步矩阵。Box 对本功能的裁决写进当前需求的 STATE 或审核档案；只有对所有 PRD 都适用的写法裁决才登记 `references/rulings.md`。
3. **判定是否需要外部竞品参照**：只有规范库没有覆盖、属「新用户能力或新主流程」、且交互或状态架构仍有事实缺口时才做，见「竞品参照」。
4. **列状态覆盖矩阵**：通用维度——入口、默认、输入/选择、客户端校验、服务等待、成功、后置动作失败（主操作成功但附带的奖励、通知、同步失败）、可恢复失败、阻断、取消、返回、重试；相关时加权限、离线、超时、未知结果、审核、冻结；再加命中模块的必问状态（对方已拉黑/已注销/已退群、多端同步、离线接收方、弱网、已被转发/引用、群与私聊差异等）。逐项标 `覆盖`／`不适用`／`未定义`，`未定义` 先判断能否按惯例或推荐写成正文；只有必须由 ZYMIX 事实源、研发或合规回答的才进交付稿「未决项」（按答复方合并计数，最多 5 组，如「持牌机构：限额、手续费、到账时效」算一组；超出说明需求还没准备好，先告知 Box），不为凑矩阵制造需求。
5. **先写草稿再上画布**：说明卡正文与功能清单先写成 Markdown 草稿（与 STATE 或审核档案同目录，结构见下面「草稿结构」），跑 `lint_card_text.py` 归零，再对照命中模块的「反模式」逐条过一遍。卡数 ≥ 6 或命中 ≥ 3 个模块时，加做一次**读者测试**：派一个不带本次上下文的子 agent 只读交付稿的说明卡，列出开发实现时会问的问题；卡里答得上的划掉，答不上的补进卡或「未决项」（没有子 agent 能力时，自己只看交付稿、按开发视角逐卡列问题）。交付稿是画布文字的唯一来源。
6. **排屏与编号规划**：定屏序、行分组、x 步长、每屏说明卡数与编号，一次规划到位（`references/canvas-layout.md`）。
7. **写入闸门**：交付稿须先过 `lint_card_text.py --gate`（`{待定：}` 清零；`{待查：}` 清零，或在申请块逐条列出并经 Box 同意带着上画布）。一次性向 Box 提交写入申请——目标文件与大区、拟新建节点清单、批次划分、是否覆盖既有节点、预计还需的确认点。Box 明确同意后才动画布，不分批打断。续写另附保护范围。
8. **落卡与自检**：每批写完跑「交付自检」一节，通过才进下一批；收尾给验收回执。

### 提问预算

Box 的注意力是最贵的资源。分歧点、惯例、未定义状态、默认值按三级处理，**一次提问最多 4 道选择题**（选择题工具单次上限）：

| 级别 | 判定 | 处理 |
|---|---|---|
| 必问 | **以规范库标签为准**：标 `级别：必问` 的分歧点，以及条目里写明「按必问处理」的子句。运行时只在两种情况下额外升级：④ 与 ZYMIX 既有规则冲突或偏离基线；规范库没有覆盖的新议题落在下面五类。五类定义（维护规范库与判断新议题用）：① 隐私默认值、对等规则、对方能感知到什么；② 不可逆处置或数据删除的范围（含历史消息保留/清除、拉黑或撤回后是否补发、本地或云端内容是否删除、未上报状态是否丢弃）；③ 二选一会让主流程走向不同、不定下来卡就写不下去，或主流取值相差极大、直接决定产品定位（如撤回时限）；④ 与 ZYMIX 既有规则冲突或偏离基线；⑤ 受监管资金流的可撤销性：付款后能否撤销、资金能否追回（退回路径与时效取决于持牌机构能力，写 `{待查}`）。取值取决于持牌机构、监管或研发能力的（限额、开放地区、能否在途冻结）不是 Box 能拍板的，写 `{待查}` 进未决项，不占提问名额 | 选择题问 Box，推荐项放第一；卡内写 `{待定：议题，推荐：做法}` |
| 按推荐默认 | 规范库「惯例」与基线以外的默认做法；标 `级别：可默认` 的分歧点（即便内容涉及可见性或退回，标签已经过五类判定，照标签执行）；按冲突裁决梯度得出、又不属于上面五类的新取舍 | 按推荐项写成卡内正文（不留 `{待定}`），交付稿「已按推荐默认」清单列一行（议题：采用的选项），Box 不改即生效；清单按决策点计、最多 8 条（同一决策点的多个参数合并为一行）；超出说明范围外延，把外延议题移入「建议后续」，不得溢出到底稿 |
| 本期不涉及 | 用户没点到、也不是本功能必备状态的议题（如做开关时的备份恢复、旧版本兼容；做拉黑时的邀请入群、黑名单管理页） | 不问、不写卡；需要时在交付稿末尾「建议后续」列一行。规范库对本功能标为必问的议题、本功能的必备配套（如导出的冷却与频次、订阅的续费提醒）不得放进「建议后续」 |

**范围**：只覆盖用户点到的议题、这些议题的必备状态与必备配套入口（如拉黑必有的黑名单管理、开关必有的设置入口），不顺手扩展相邻功能。排序：隐私与不可逆 > 改变主流程 > 其余。**标签优先**：条目或子句标了「按必问处理」的一律按必问；其余照条目级别执行，不在运行时按五类重新判定（避免同一议题不同次生成口径不一）。推荐偏离主流做法时（如为隐私不公开红包金额），题干必须写明「与主流做法相反，属 ×× 取舍」，不能只写「做法不一」。必问超过 4 道时，说明需求范围过大，先问 Box 是否拆分；Box 不拆分，则分轮提问，每轮 ≤ 4 道。**采纳时点统一为写入闸门**：Box 同意写入申请，即视为采纳当次「已按推荐默认」清单。必问不得改写成 `{待查}` 或塞进「未决项」来绕开题数上限。Box 不在线或非交互运行（评测、定时任务）时不等待：必问项在卡内写 `{待定：议题，推荐：做法}` 占位，交付稿照常产出，停在写入闸门之前。

### 草稿结构

草稿分两个文件，Box 只需要读交付稿。模板见 `references/draft-template.md`。

- **交付稿**（`<功能名>-交付稿.md`）：说明卡（按屏、按编号）、功能清单、「待 Box 裁决」（≤ 4 道选择题）、「已按推荐默认」清单。说明卡必须自足：开发只看卡就能实现，**卡内不出现「Q1」一类议题编号、规范库 ID、「偏离惯例」「国内主流产品」一类规范库措辞**。必问未裁决的取值写 `{待定：议题，推荐：做法}`（带上推荐，研发与评审能先看懂方向；与运行时变量 `{昵称}` 区分），同一议题全稿只挂一次，其他卡写「同 帧名-编号」；按推荐默认的直接写成正文。交付稿顺序固定为：待 Box 裁决 → 已按推荐默认 → 未决项 → 角色视角速览（如需）→ 说明卡 → 功能清单 → 验收要点 → 建议后续，让 Box 先看到要拍板的事。**同一取值只在一张卡里写**，裁决区、默认清单、功能清单只写议题并引用卡号，不重复写数值与文案。同一组前置校验在多张卡出现时，只在第一张卡写完整判断链，其余写「校验同 {帧名-编号}」。
- **体量**：单个功能通常 6–10 张卡；交付稿明显长于此时，先查是否范围外延、同一规则是否在多张卡重复展开（应只在一张卡定义、其余引用），不靠删必备状态来压篇幅。
- **验收要点**：交付稿末尾写可执行的验收断言（给测试，不上画布），只写单看一张卡读不出来的：跨卡或跨角色对照、时序与多端；隐私类功能必须含一条「对方无法区分」的对照断言（如被拉黑方发送与对方离线时界面一致）。单卡已写明的规则不复述，总数 ≤ 12 条。功能清单描述只写一句「触发—结果」加卡号，不复述卡内文案与数值。涉及两个以上角色的功能，在说明卡前放一张「角色视角速览」表（行为场景、列为各角色看到什么）。
- **工作底稿**（`<功能名>-底稿.md`）：产品定型、事实源标注、规范对照、状态覆盖矩阵、自检记录。供复核，不给 Box 逐条看。

## 说明卡正文不写视觉规格

**核心规则（Box 2026-09-17 裁决）：说明卡只讲行为与规则，视觉一律以设计稿为准。**

正文里**不出现**：

- 像素尺寸与坐标：`宽 370`、`高 72`、`40 × 40`、`圆角 12`、`x = 12`、`y = 220`
- 色值与颜色 token：`#F5F6F7`、`B7`、`S7 #0E0E0F 80%`、`A1`
- 字体 token 与字号行高：`Noto Sans SC Bold 14/20`、`Body_S_700`、`Caption_S_500（12/16）`
- 对比度数值：`9.69:1`、`低于 4.5:1`
- 素材的具体宽高比与热区数值：`16:9`、`不小于 44 × 44`

需要表达视觉差异时，**写定性关系**而不是数值：

| 不要写 | 改写为 |
|---|---|
| 卡槽 370 × 72，圆角 12，B7 #F5F6F7 底 | 卡槽左右内缩、有圆角、有独立背景色 |
| 缩略图 40 × 40，圆角 8 | 缩略图为方形圆角，不使用圆形头像 |
| 角标宽度：中文 32、英语 25、越南语 63、菲律宾语 62 | 四种语言的角标文案长度不同，由短到长依次为英语、简体中文、菲律宾语、越南语 |
| 标题可用宽度 226 / 233 / 195 / 196 | 角标越宽，标题可用宽度越窄；同一条广告在越南语下能放的字数明显少于英语 |
| 点击热区不小于 44 × 44 | 点击热区需满足平台无障碍标准 |
| 实测对比度 2.28:1，低于 4.5:1 | 设计系统既有的主按钮配色在无障碍对比度上不达标 |
| 素材按 16:9 上传 | 素材按设计稿规定的宽高比上传 |

**保留的数值**——这些不是视觉规格，是产品约束，照常写：

- 截断行数：如「摘要最多 2 行」「超过 5 行折叠」（Box 2026-10-31 裁决：行数是内容规则）

- 时间：冷却 24 小时、曝光停留不少于 1 秒、动图 1 至 4 秒
- 计数：每天曝光上限、两次曝光最小间隔、帧数 5 至 20 帧
- 内容：字符数上限——**随 locale 或版式变化的**写「按 locale 分别配置」不写数字；**全局硬上限**（如昵称最多 32 字符、群名最多 64 字符）是产品约束，照常写
- 业务阈值：群成员数分档、错误次数上限

**判断标准**：这个数字变了，是改需求还是改设计稿？改设计稿的不写。

需要精确规格时，说明卡写「见设计稿」「以切图规范为准」，把数值留在设计稿和交接 spec 里。token 与色值只用于**画屏**本身和向设计/开发口头交底，不落进说明卡正文。

同一条规则适用于 **FigJam 功能清单的描述列**——它也是说明性文字。

## 说明卡写作规范

每个标注点先过语义检查表决定**问什么**：显示/触发、默认值、用户操作、客户端校验、服务端判断、成功结果、异常与恢复、精确文案、副作用、平台/权限/数据/异步差异。

**句式**

1. 主干是「条件/对象 + 全角冒号 + 结果」的键值短句
2. 判断分支**成对穷举**，正反都写、不省略，末支写去向
3. 按钮类卡固定开头两条：`1. <输入条件>后按钮亮起`、`2. 点击后进行以下判断：`
4. 兜底/降级单列一条，固定句式「无法匹配时…」
5. 风控/限流写成四段式：`<时间窗>内<比较符><次数>：<处置>，<冷却时长>，提示「<原文>」`。**比较符用半角 `>` `<` 与 U+2264 `≤` / U+2265 `≥`，两侧各留一个半角空格**
6. 计数规则写明**口径维度与不清零条件**；时间分界类规则（在途、时限、生效时点）写明**判定口径**：以哪个时间戳、哪一端为准（如「服务端接收时间 ≤ 拉黑生效时间的消息照常送达」）
7. 复用既有规则不重复展开，写「与…保持一致 / 参见…」
8. 补充风险、例外、设计取舍另起一条，以 `注：` 开头
9. 本期范围与后续规划同卡对举
10. 服务端链路可用 ➡️ 压成一行；但**判断出口必须逐行**
11. 常用条目前缀：`触发：` `入口：` `出口：` `默认：` `规则：` `适用范围：` `点击行为：`。不要用 `交互：`
12. **视觉相关只写定性关系与约束，不写规格数值**，见「说明卡正文不写视觉规格」

**跨卡规则边界必须限定**：同一个量在不同卡里出现时，只有一张卡给定义，其余引用它。绝对表述（「均为单行」「宽度自适应」）只有在**所有形态下都成立**时才能写；只要存在例外形态，就要么加限定语，要么改成引用。这类矛盾是复核里最高发的一类。

**Box 写法六规则**（与上面句式冲突时以本节为准）

1. **状态语义逐条定义**：状态机里每个状态先各用一行说清含义，再写规则。
2. **分档规则合并进单卡**：同一功能按人数/条件分档时，各档写在同一张卡内逐行列出。
3. **图标编码用图例条**：状态图标的形与色用图例条表达，不写「单勾=发送成功」式文字描述条。
4. **交互卡固定骨架**：`适用范围：` → 计数口径 → `数据按需拉取：` → `加载中：` → `加载失败：` → 数据明细 → 点击去向。
5. **信令类规则四段式**：`触发` → `刷新` → `停止`（列出全部停止条件）→ `重开`。
6. **口语化短句可用**：含义唯一的口语短句合法。判断标准是开发能否唯一实现。

**判断链形态（唯一合规写法）**

多重前置校验才升级为判断链：判断在 `a.` 层逐条展开并加 `N-` 步骤前缀，**每个出口各占一行，包括通过时的下一步**：

```
说明：
1. 输入手机号后按钮亮起
2. 点击后进行以下判断：
   a. 1-格式判断：手机号是否符合所选国家的号码规则
      i. 不合法：行内提示「无效的手机号码」
      i. 合法：进入下一个判断
   a. 2-校验请求合法性：该号码是否已经注册
      i. 已注册：弹窗提示登录
      i. 未注册：进入下一步
```

判断少于 3 个时可不起判断链。**没有第三种写法**——不用 `①②③`、不用 `→`、不把出口并到判断行上。

**判断链要包含过滤步**：凡是有冷却、频控、锁定、黑名单一类前置过滤的功能，过滤必须作为判断链的第一步显式写出；不依赖服务端的判断（权限、本地锁定、网络）放在最前；需要服务端判定的过滤（频控、冷却、服务端锁定状态）紧随网络之后；其余服务端判断（对象状态、余额、资格）最后。否则「被过滤掉的那条是否让位给次优先级」这类问题无法唯一实现。

**文案与符号**

- UI 文案、按钮、提示一律**逐字给定**并用中文直角引号 `「」`（禁用 `【】` 和弯引号）
- **禁止出现其他品牌名称**，含竞品产品线名称。例外：Apple、Google 作为 ZYMIX 支持的登录方式名称可以出现；「与主流即时通讯产品一致」是认可的改写词
- 提示载体显式点名：`toast 提示：` `弹窗提示：` `按钮显示 loading 状态`
- 数字、英文与中文之间加半角空格
- 变量占位用半角 `{}`
- 多值并列用 `/`
- 跨区引用用 `「」` 不用 `【】`

**通知模板卡**（短信/邮件成品文案）：不带 `说明：` 前缀，直接给成品文案。短信一行；邮件用 `邮件主题：` / `邮件正文：` / `Foot：` 三段骨架。

## 竞品参照

规范库是第一参照。只有**规范库没有覆盖**、且任务属于**新用户能力或新主流程**、交互或状态架构仍有事实缺口时，才做外部竞品研究（2–4 个直接同类的主流即时通讯产品，调研默认用 `product-management:competitive-brief`）。补状态、修文案、派生表格/流程、视觉整理一律不触发。

- **外部结论先标 `建议`**，只有 Box 或当前事实源明确采纳才升级为 `已定义`。
- **不照抄竞品的具体数值**：竞品的字数上限、尺寸、时长是在它自己的版式与业务下定的，只用来判断量级。
- 新调研结论记入当前需求的 STATE 或审核档案，并在验收回执里提示 Box 是否补进规范库；规范库更新是独立的维护任务（改完跑 `lint_skill.py`），不在生成流程中顺手改。

**PRD 正文一律不得出现其他品牌名称**，含竞品的**产品线名称**，不只是公司名和 App 名：

| 不要写 | 改写为 |
|---|---|
| 与 Telegram、WhatsApp 一致 | 与主流即时通讯产品一致 |
| 不采用 iMessage / Signal 的做法 | 直接描述被排除的方案本身 |
| 参考微信的处理 | 与主流即时通讯产品的处理保持一致 |

竞品调研的来源、对比表、差异结论放规范库 `evidence/` 或独立调研文档，**不进 PRD 画布**。

## 交付自检

**一票否决项**（任一命中即不交付，先改）：

1. 状态机缺终态，或有状态只有入口没有出口
2. 创建了却无法撤销、查看或退出的断链（发出后无撤回/删除说明、入群后无退群、开启后无关闭）
3. 涉及消息或会话的功能没定义多端一致性，或涉及群的功能没定义与私聊的差异（与本功能无关时在底稿写一行理由即可）
4. 隐私相关默认值未定义（谁可见、谁可达、默认开或关）
5. 离线、重试、超时三者有任一未定义且未标「不适用」
6. 偏离 IM 基线却没有 `注：` 说明，或必问级分歧点未经 Box 裁决就落卡（惯例与按推荐默认项不在此列）
7. 说明卡或功能清单出现品牌名或视觉规格
8. 同一议题在两张卡里做法矛盾；确认弹窗、toast 里的范围词（「不再」「全部」「所有」）与各场景卡的实际规则不符

其余逐项检查（结构版式、设计系统合规、说明卡正文、功能清单、IM 合规）见 `references/self-check.md`。帧尺寸、卡宽、帧名唯一、默认图层名、禁用符号、品牌名、手打序号、编号成对八项跑 box-figma-prd 的版式自检脚本；交付稿跑 `lint_card_text.py`（写入闸门前加 `--gate`）；其余靠人工。
